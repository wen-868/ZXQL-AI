## 1. 幂等键的来源、构成与 TTL

### 1.1 来源（谁生成）

| 优先级 | 来源 | 取值 | 覆盖场景 | 是否需要改调用方 |
|---|---|---|---|---|
| **P1（主）** | **确认令牌** | `toolCall.id` 形如 `confirm-<写审核令牌>`（`confirmation.service.ts:427`） | 人工确认后执行（生产唯一真实落单通道） | 否（**已存在**） |
| P2 | 调用方显式键 | 新增 `options.idempotencyKey`（agent 计划：`planId:stepId`；v2/MCP：调用方自报） | 计划编排 / 外部系统集成 | 是（AI-21 实现单） |
| P3（兜底） | **业务参数规范化哈希** | `sha256(canonical_json(business_args))` | 无令牌、无显式键的残余路径 | 否 |

### 1.2 构成

```
idem_key = sha256( tenant_id + '|' + tool_name + '|' + key_material )
key_material =
   ① 显式键（优先）：`confirm-<token>` 或调用方 idempotencyKey
   ② 否则：canonical_json(business_args)          # 键排序 + 去除易变字段
```

`canonical_json` 规则（消除"同义不同形"）：对象键按字典序排序；数值统一（`Number`、去掉 `-0`）；字符串 trim；**剔除易变/流程字段**：`confirm`、`force`、`idempotencyKey`、`requestId`、`sessionId`、`timestamp`、`remark`（仅当工具声明 `idempotencyKeyFields` 时以该白名单为准，见 §6）。

> ⚠️ 纯 payload 哈希的**假阳性风险**：`create-payment-reconciliation` 必填仅 `customerId`、`create-customer` 必填仅 `name`（`required` 实测见 §6）——同一参数在短时窗口内的两次**合法**操作会被判为重复。故 ① 优先、② 仅作短 TTL 兜底，且允许工具用 `idempotencyKeyFields` 收窄字段集。

### 1.3 TTL 与依据

| 层 | TTL | 依据 |
|---|---|---|
| Redis NX 前置闸门 | **600s（10 分钟）** | 覆盖 LLM/客户端/网关重试与人工确认后的即时重发窗口；远小于写审核令牌 24h（`CONFIRM_TTL_MS`），key 空间可控；长于撤销窗口 3min（`REVOKE_TTL_MS`）留足余量 |
| MySQL 幂等行 | **保留 30 天**（每日 03:00 批量清理） | 对账/追溯窗口；30 天 ≫ 任何重试窗口，清理后不影响防重能力；单行约数百字节，30 天量与写操作量同阶 |
| payload_hash 兜底键 | **60s**（仅 P3 路径的 Redis TTL） | 兜底键精度最低（假阳性风险最高）⇒ 只用于"传输层秒级重试"，不用它做分钟级业务去重 |

## 2. 闸门插入点与论证

### 2.1 精确插入点

`executeToolCall` 内、**熔断门通过之后、`tool.execute` 之前**——即 `tool-executor.ts:139`（熔断块结束）与 `:142`（执行 try）之间，落在 `:141` 注释之前。

```ts
// 3.5 熔断通过（:131-139）
// 3.6 【新增 R101-AI-21】幂等闸门（仅写工具的真实执行）
const idem = tool.isWriteOperation && args.confirm === true
  ? await this.idempotencyGate.check(toolName, args, context, options)
  : null;
if (idem?.decision === 'replay') return idem.result;   // 幂等成功：回放既有结果
if (idem?.decision === 'in_flight') return { success: false, error: '...', suggestion: '...' };
// 4. 执行工具（:142+）
const result = await tool.execute(args, context);
// 4.5 回填幂等行（成功/失败都写，供重放与审计）
await idem?.complete(result);
```

**闸门条件 `tool.isWriteOperation && args.confirm === true` 是硬要求**：

- 写工具的**预览调用**（`confirm !== true`）是纯计算/预览，不产生副作用 ⇒ 不得消耗幂等键，否则用户确认后真正执行会被自己判成重复（自锁）。
- `confirm === true` 已被 `:73-87` 收口为"仅确认通道/显式 allowConfirm 可达" ⇒ 闸门天然只覆盖真实落单。

### 2.2 为何不放进各工具内部

1. **唯一收口、不可绕过**：36 个工具各自实现必然漏改（新增工具默认无防护），入口层一处生效，与既有治理链（审核门/customerScope/熔断）同构。
2. **不重复 36 份**：键计算、Redis/MySQL 两层的失败兜底、指标与死信只需一份；工具内部实现会把"重试语义"散布到 36 处，口径必然分叉。
3. **顺序不可搬**：闸门必须晚于 tenantId（键含 tenant_id）、晚于 customerScope（越权调用不该占用幂等键）、晚于熔断（熔断期不应写入幂等行，避免"未执行却被标记已处理"）。
4. **保留工具自治**：工具只声明"我的业务键字段有哪些"（`idempotencyKeyFields`，可选），不承担并发/存储细节。

## 3. Redis SET NX 行为 + 两层失败模式与兜底顺序

### 3.1 正常路径（两段式：Redis 快筛 → MySQL 认领）

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | `SET ai:idem:{tenant}:{tool}:{key} "1" NX EX 600` | 成功（未命中=首次）⇒ 进入步 2 |
| 2 | MySQL `INSERT ... (status='in_flight')` | 成功 ⇒ 步 3；**唯一键冲突** ⇒ 步 4 |
| 3 | `tool.execute()` → `UPDATE status/result_json/completed_at` | 返回本次真实结果给 LLM |
| 4 | 读既有行 | `succeeded` + `result_json` ⇒ **回放**；`in_flight` ⇒ **处理中**（见 §5） |

> Redis **未命中 ≠ 直接放行**：必须以 MySQL 认领为准（Redis 只省一次 DB 往返与提供快速重复应答）。Redis 命中重复 ⇒ 直接进 4（查既有行回放），无需尝试认领。
> 使用共享 provider：`redisProvider.getSharedClient('stop-after-3')`（`src/common/redis.provider.ts`），**不得新建连接**。

### 3.2 两层失败模式与兜底顺序（验收 #4）

| 故障 | 行为 | 兜底顺序 | 后果与观测 |
|---|---|---|---|
| Redis 不可用/超时 | **fail-open**：跳过 NX，直接走 MySQL 认领 | MySQL 唯一键成为唯一防线 | 仍保证"至多一次落单"（并发时由唯一键裁决：1 个认领成功、其余读既有行）；记 warn + 指标 `idem_redis_degraded` |
| Redis 命中但 MySQL 无行（TTL 过期/被清理/键漂移） | 以 MySQL 为准：尝试认领，成功则执行 | — | 不误判重复（宁可重放为首次，也不丢用户操作） |
| **MySQL 不可用**（认领 INSERT 连接失败，≠ 唯一键冲突） | **fail-open**：放行执行 + `logger.error` + 死信（复用 `error-semantics` bestEffort 口径） | 无第三层 ⇒ 退化为无幂等 | ⚠️ 残余风险：该窗口内可能重复落单；必须靠告警（死信/指标）驱动人工核查；**不选 fail-closed** 的理由：写工具是业务主链路，DB 抖动时全量拒绝写操作（用户无法下单/退款）比"可能重复"伤害更大，且本仓已有 `bestEffort` 语义先例 |
| MySQL 唯一键冲突（并发/重复） | 读既有行 → 回放或"处理中" | — | 正常重复路径，非故障 |
| 两层皆不可用 | fail-open + 双告警 | — | 同上，属可观测的降级窗口 |
| `tool.execute` 抛异常/失败 | 幂等行置 `failed` + `error_text` | 允许同键重试（**不**回放失败结果） | 失败重试是期望行为；仅 `succeeded` 才回放 |

## 4. MySQL 表设计与"为何需要它"

### 4.1 表设计（草案见 `migrations/016_ai_idempotency.sql`）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK AI | 主键 |
| `tenant_id` | VARCHAR(36) NOT NULL | 租户域（键第一段，多租户隔离） |
| `tool_name` | VARCHAR(64) NOT NULL | 工具名（键第二段） |
| `idem_key` | CHAR(64) NOT NULL | sha256 hex（键第三段） |
| `key_source` | VARCHAR(16) NOT NULL | `confirm_token` / `explicit` / `payload_hash`（可观测键质量） |
| `status` | VARCHAR(16) NOT NULL DEFAULT 'in_flight' | `in_flight` / `succeeded` / `failed` |
| `result_json` | MEDIUMTEXT NULL | 首次执行结果（供重复请求回放，含 `ToolResult`） |
| `error_text` | VARCHAR(512) NULL | 失败摘要（脱敏，仅排障） |
| `first_seen_at` / `completed_at` | DATETIME | 认领时刻 / 完成时刻（时延与卡死排查） |
| `created_at` / `updated_at` | DATETIME | 审计与清理依据 |

索引：`UNIQUE KEY uk_ai_idempotency (tenant_id, tool_name, idem_key)`（**最终防线 + 并发互斥**）；`KEY idx_ai_idempotency_cleanup (created_at)`（清理扫描）。
清理：每日 03:00 `DELETE ... WHERE created_at < NOW() - INTERVAL 30 DAY LIMIT 5000`（批量循环，避免长事务）。

### 4.2 为何必须有它（不是"Redis 够用"）

1. **Redis 是易失层**：宕机/重启/主从切换/被 FLUSH ⇒ NX 状态全丢；唯一索引在磁盘上，是"至少不重复落单"的最后保证。
2. **并发互斥只能由唯一键承担**：两个并发请求可能同时通过 Redis（或 Redis 降级期间）⇒ `INSERT in_flight` 的**唯一键冲突**是唯一可靠的仲裁点。
3. **可回放**：重复请求要"回放既有结果"必须有落地存储（Redis 只存键，不存结果；且 TTL 短）。
4. **可审计**：谁在何时认领/完成/失败，是生产事故复盘的唯一凭据。

## 5. 重复请求返回什么给 LLM（验收 #3，明确回答）

**建议：`succeeded` 的重复 ⇒ 幂等成功回放既有结果**（`success: true`，`data` 为首次结果，附加显式标记 `idempotent_replay: true` 与 `originalCompletedAt`）；**`in_flight` 的重复 ⇒ 显式"处理中"**（`success: false` + `suggestion`，不阻塞、不重试执行）。

理由：

1. **契合重试语义**：重试方（LLM/客户端）的真实诉求是"我上次没拿到结果"，回放让它把对话闭环（"销售单 SB2026… 已创建"），而"拒绝"会让 LLM 误判为失败，可能**换参重试**（真重复）或向用户播报错误。
2. **不产生第二次副作用**：回放路径不触碰 `tool.execute`。
3. **可区分、可审计**：显式标记让前端/审计能区分"首次创建"与"重复回放"；`key_source` 落库便于事后评估键质量。
4. **`in_flight` 必须区别对待**：此时首次尚未完成，回放会把"未完成"当"成功"（假成功比重复更危险）⇒ 返回"处理中，请勿重复提交"（并可用 ≤2s 短轮询等待首次完成后再回放；实现单可决定是否加）。
5. **`failed` 不回放**：失败可重试，回放失败结果等于永久阻断业务。

> 供业主确认的替代口径：若业务希望"重复一律拒绝"（更保守、但 LLM 体验差），仅需把 §3.1 步 4 的 `succeeded` 分支改为返回 `success:false` + `AI_012`（写操作被拒）；**代价**是用户会看到"操作失败"而实际单据已存在。

### 6.1 总览

- **零改动的部分**：闸门在入口层 ⇒ 36 个工具**全部自动获得防护**，无需逐个改造；读工具（`isWriteOperation=false`）完全不受影响；预览调用（`confirm!==true`）不消耗幂等键。

| 类别 | 判定标准 | 工具（实测 `required`） | 适配建议 |

| **C 类：需评估是否纳入** | 副作用弱/幂等本身安全 | `stock-check`、`calculate-commission`、`auto-generate-collections` | 纳入无副作用；但若其"写"只是生成报表/计算，可置 `idempotencyExempt`（实现单再定） |

### 6.2 与既有机制的关系（不破坏）

- **写全审核门**（`:77-87`）：闸门在其后，不影响 `confirm` 降级语义。
- **P0-2 同源绑定**（密钥↔端点 + WARN 降级）：本方案不触碰 provider 配置解析，零影响。
- **撤销窗口**（3min）：幂等行与撤销记录是不同对象；重复回放不改变撤销语义。
- **bestEffort/死信**：MySQL 不可用走既有 `error-semantics` 口径（logger.error + 指标 + 死信）。

## 7. 风险、回滚与建索引预检

### 7.1 风险清单

| # | 风险 | 等级 | 处置 |
|---|---|---|---|
| R1 | payload_hash 假阳性（B 类同参合法操作被去重） | 中 | ①确认令牌优先；②兜底键 TTL 仅 60s；③工具可用 `idempotencyKeyFields` 收窄；④`key_source` 落库 → 可量化假阳性 |
| R2 | Redis 降级期并发重复 | 中 | MySQL 唯一键仲裁；`idem_redis_degraded` 指标告警 |
| R3 | MySQL 不可用 ⇒ 无幂等（fail-open） | 中 | 死信 + 指标告警 + 人工核查；**不选 fail-closed**（阻断业务链路代价更大，见 §3.2） |
| R4 | `in_flight` 行残留（进程崩溃）⇒ 该键永久"处理中" | 中 | `completed_at`/`first_seen_at` 超时看护（如 >10min 的 `in_flight` 允许再次认领/由清理任务置 `failed`） |
| R5 | `result_json` 含敏感数据 | 中 | 仅存 `ToolResult`（工具已按约定不返回密钥）；必要时按 `AUDIT_MASK_MESSAGE` 口径脱敏（实现单确认） |
| R6 | 表增长 | 低 | 30 天清理 + `idx_cleanup`；必要时按月分区 |
| R7 | 幂等键误用为"业务锁"（长事务占用） | 低 | 文档明确：仅防"重复提交"，不做分布式锁；TTL 短 |

### 7.2 回滚

1. **代码回滚**（实现单）：移除闸门调用即回到现状；幂等表保留不影响任何链路（无读取方）。
2. **数据回滚**：`DROP TABLE IF EXISTS t_ai_idempotency`（草案末「文档·勿执行」段给出，**不在本次执行**）。
3. **降级开关**（建议实现单加）：`IDEMPOTENCY_ENABLED=false` ⇒ 闸门整体旁路（不改表结构），用于线上止血。

### 7.3 建唯一索引的存量预检（验收要求的"脏数据"处置）

`016` 是**新建表**（`CREATE TABLE IF NOT EXISTS`）⇒ 建表时无存量行，**不存在**"存量重复导致加唯一键失败"。仍给出通用预检与处置，供"往已有表补唯一键/重跑变体"时使用（**只出方案，不执行**）：

```sql
-- 预检：是否存在会与新唯一键冲突的重复组（应返回空集）
SELECT tenant_id, tool_name, idem_key, COUNT(*) AS c
FROM t_ai_idempotency
```
