## 四、验收中发现并已补上的问题

### 发现 1（已修）：并发封堵缺测试证明

原 `evolution-version.service.spec.ts` 的 mock 固定返回 `affected: 1`，**没有一条用例覆盖 `affected: 0`（并发抢先）**。这意味着「并发双激活被封堵」这个 P2 级安全承诺**代码正确但无测试证明**——若有人把条件更新的where 去掉退回 `save()`，测试仍会全绿。

已补 2 条反测用例（`src/evolution/evolution-version.service.spec.ts`，17 → 19 例）：
- 条件更新 `affected=0` → 必须抛「激活冲突」，不得静默成功；
- 激活那条 where 必须带 `status = 'staged'` 约束。

**反测验证**：临时移除 `AND status = :status` 约束后，用例立即变红（19 例中 1 例红）；还原后 19/19 全绿。断言有真实信号。

### 发现 2（需记档，不阻塞）：存量 MCP Token 仍永久有效

新兜底只覆盖**新建** Token。`verify()` 的判定是：
```
if (entity.expiresAt && entity.expiresAt.getTime() <= Date.now()) return null;
```
数据库中 `expires_at IS NULL` 的**存量 Token 仍无时间底线**。若要闭合需一条数据迁移回填（如按 `created_at + 90 天` 回填）。建议随下个迁移一起做——与已搁置的 `superseded` 状态改造合并。

### 发现 3（需记档，不阻塞）：graph 超时是"放弃等待"而非"取消"

`Promise.race` 超时后图节点不再等待，但底层工具 Promise **仍在后台跑**（真实取消需工具侧支持 `AbortSignal` 透传）。对「防止图挂死」这个目标已达成；对「工具仍在消耗资源」需后续在工具执行层引入取消。

### 发现 4（需记档）：E4 清洗会修剪尾部反斜杠

`clean()` 含 `.replace(/\\+$/g, '')`，对以 `\` 结尾的样本内容（少见，但含 Windows 路径片段时可能出现）会改变原文。判断为可接受的取舍（Modelfile 转义正确性优先），记档备查。
