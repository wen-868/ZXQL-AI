### A2 · `listTasksFor` 补 `tenantId`

**位置**：`src/brain/employee/employee.service.ts:479-492`（b52a39c 实测）

```typescript
async listTasksFor(employeeUid: string, employeeId: number) {
  return this.taskRepo.createQueryBuilder('t')
    .where('t.employee_id = :eid OR t.dispatched_by = :uid', {
      eid: employeeId, uid: `employee:${employeeUid}`,
    })
    .orderBy('t.id', 'DESC').take(50).getMany();
}
```

**缺陷**：方法自身**零租户过滤**，安全性完全依赖调用方先校验。

**当前唯一调用点**（`employee.controller.ts:132-135`）确实先做了校验：
```typescript
const tenantId = this.tenantContext.requireTenantId();
return this.employeeService.getById(id, tenantId)
  .then((e) => this.employeeService.listTasksFor(e.employeeUid, e.id));
```
⇒ **当前无实际越权路径**，所以定为「一般」而非「严重」。

**但风险是真实的**：这是**约定而非机制**。将来任何人新增调用点而忘了先校验，
就是跨租户泄露（且 `OR dispatched_by` 写错会更糟）。
**这正是第九轮根因 2「一致性靠人工纪律」的典型样本。**

**实施要求**：
1. `listTasksFor` 增加 `tenantId: string` 参数，SQL 加 `AND t.tenant_id = :tenantId`
2. 同文件 `completeTask`（`:338`）/ `markTaskRated`（`:358`）**已经**是正确做法
   （`update({ id: taskId, tenantId }, ...)`），照它们对齐
3. 唯一调用点同步改传`tenantId`

**测试要求**：跨租户调用 `listTasksFor` → 返回空数组（不是别人的数据）。

### A3 · `billing.consume` 判据下沉（**优先级最高**）

> 这一项是阶段 0 验收时查出的**残留缺陷**，我在报告里标了"Blocker 降 Major 但不可关闭"。
> 上一轮 P1-B 子代理**没有做这条**（它只处理了错误分级，没动判据）——
> 这是我上一轮表述不清留下的口子，现在正式立卡。

**位置**：`src/tenant/billing.service.ts:61-113`（b52a39c 实测）

```typescript
const billing = await this.getOrCreate(tenantId);      // ← 内存快照
if (billing.enabled !== 1) { recordBillingConsume('skipped'); return; }

if (billing.freeChatCount > 0) {                       // ← 用快照判分支
  await this.repo.query(
    `UPDATE t_tenant_ai_billing
        SET free_chat_count = GREATEST(free_chat_count - ?, 0)
      WHERE tenant_id = ? AND free_chat_count > 0`, [chatCount, tenantId]);
  this.metrics.recordBillingConsume('ok');              // ← 不看 affectedRows
  return;
}
```

**并发保护关键字实测全为 0**：`transaction` / `FOR UPDATE` / `setLock` /
`pessimistic` / `QueryRunner` / `VersionColumn` / `DataSource` 全部无命中。

**后果**（并发，`free_chat_count = 1`）：
1. req1 与 req2 同读快照 `freeChatCount = 1`，**都进入第一个分支**
2. req1 UPDATE 命中 1 行 → 扣成 0，记 `ok`
3. req2 UPDATE 因 `WHERE free_chat_count > 0` 不匹配 → **实际影响 0 行，代码不检查，照记 `ok`**
4. ⇒ **第二次请求被免费放行且从未扣减**，指标显示 `ok` 而账上少扣一次

**为什么不可关闭**（即使降为 Major）：
- 方向是**少收费**（对平台不利，不损坏数据），窗口窄 ⇒ 这是降级理由
- 但 `recordBillingConsume('ok')` **是假的** —— 它统计的是"代码走到了这一行"，
  不是"确实扣了"。**计费指标的可信度正是这次修复的核心价值，假的 `ok` 比没有指标更危险**
  （会掩盖真实漏费）

**实施要求（治本方向：判据下沉到数据库）**：

关键是把「是否还有免费次数」这个判据交给数据库，**用 `affectedRows` 决定是否落入余额分支**，
而不是用内存快照提前分流：

```sql
-- 先只扣免费次数
UPDATE t_tenant_ai_billing
   SET free_chat_count = GREATEST(free_chat_count - ?, 0)
 WHERE tenant_id = ? AND free_chat_count > 0
```

- `affectedRows > 0` ⇒ 免费次数扣成功 ⇒ 记 `ok`，结束
- `affectedRows === 0` ⇒ 免费次数已耗尽 ⇒ **此时才**读`planType` 决定是否走余额扣减

这样无论多少并发，免费次数只会被正确扣减 N 次，且每个请求都落到正确分支。

**约束**：
- ⚠️ **不要用事务包一层来"解决"这个问题** —— 事务不解决「判据读的是快照」这个本质
- ⚠️ 阶段 3 才是并发/幂等基础设施的全局方案。本卡只解决 `consume` 这一处的判据下沉，
  **不要顺手引入 `@VersionColumn` / `createQueryRunner` 之类全局设施**（越界到阶段 3）
- `getOrCreate` 的并发双写（`:142` `save(repo.create({tenantId}))`）
  **本卡不处理**（它属于阶段 3）。但请在报告里说明：`consume` 改造后是否**加剧**了双写风险
- `recordBillingConsume` 建议按 `affectedRows` 记录，让"命中免费/落入余额"可区分

**测试要求**（这是关键）：
- 新增用例必须能证明 **「UPDATE 未命中时不应记 `ok`」**
- **反测**：把判据改回内存快照 ⇒ 用例必须立即变红

## 四、通用纪律（每个任务卡都要遵守）

### 4.1 派发前必跑 `git status`

**第九轮实测教训**：阶段 0 与 P1-B 的目标文件天然重叠
（billing / service-client / usage.controller / weekly-plan / task-runner），
派下去必冲突。**开工前跑 `git status`，若目标文件已被他人改动，先回报。**

### 4.2 门禁必须在纯净 HEAD 的独立 worktree 上一次性跑全量

```bash
git worktree add --detach "C:/Users/XIONG/AppData/Local/Temp/<你的目录>" HEAD
# 用 PowerShell New-Item -ItemType Junction 建 node_modules 联接
# ⚠️ Git Bash 的 ln -s 对 TypeScript 无效（报 TS2307）
```

⚠️ **分批 + 后台跑会被 SIGTERM 中断而漏文件**（历史上造成过假绿）。

### 4.3 门禁命令（四条都要）

```bash
npx eslint "src/**/*.ts" --max-warnings=0      # 通过时零输出 + exit 0
npx tsc -p tsconfig.build.json --noEmit        # CI 配置
npx tsc -p tsconfig.json --noEmit              # 🔴 含 spec，CI 不含，必须单独跑
npx jest --ci# 全量，前台完整跑完
```

🔴 **CI 绿灯 ≠ 类型干净**：`tsconfig.build.json` 的 `exclude` 含 `**/*spec.ts`，
spec 的类型错误永远不会让 CI 变红。

### 4.4 改代码必须同步改 spec

否则 spec 会把死锁固化成"正确断言"。

### 4.5 反测是验收标配

**反测方向必须是「修复不存在」**，不是「让守卫走另一分支」。

我踩过的坑：想把三重守卫条件改成 `if (false) ? parsed : 60000` 来"禁用守卫"，
结果 15 个用例全绿 —— 因为那等价于"强制走 fallback"= **守卫仍在工作且拒绝坏值**。

### 4.6 grep 零命中有三种可能

真没有 / 被 SIGTERM 打断 / **pattern 没覆盖写法变体**。
我曾 `grep 'degrade('` 报 0，实际代码是 `await degrade<X | null>(`（带泛型+空格）。
**先换 pattern 复核，再怀疑人没做。**

### 4.7 禁止事项

- ❌ 禁止 `it.skip` / `describe.skip`
- ❌ 禁止为转绿放宽断言
- ❌ 禁止 `as SomeType[]` 断言（`eslint --fix` 会删掉它）
  → 用 `const raw: unknown = await ...` 再收窄
- ❌ 禁止越界到阶段 3（并发/幂等基础设施）或阶段 5（前端）
- ❌ **不要 git commit / push** —— 推送由我统一执行
