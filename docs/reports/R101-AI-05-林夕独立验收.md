### ③ 规则 c（IP 字面量网段，含 172.16/12 两端 + IPv6 变体）—— **通过**

### ④ 规则 d（同源解析 / 防 DNS 重绑定）—— **通过**（措辞需精度修正）

本体实跑 `createGuardedLookup()` 解析 `localhost`：

```
WARN 出站目标被拒 rule=dns-blocked-address-connect host=localhost
     detail=域名 localhost 解析到受限地址 ::1（连接期校验，防 DNS 重绑定）
callback: err=BadRequestException address="" family=0
```

关键点两个，都成立：
1. `lookup` 是 **Node 真正建连时调用**的钩子 ⇒ 校验的就是连接要用的那次解析；
2. 被拒时 `callback(reject(...), '', 0)` —— **不回传地址**（实测 `address=""`）⇒ Node 拿不到地址，连接真正中断，不是"记一笔继续连"。
3. 放行时回传的是**已校验过的那份** `addresses`（`guard:154` / `:157`），而非重新解析 ⇒ rebinding 风险已消除。

**⚠️ 措辞精度修正（不影响判定）**：`guard:13` 注释称「连接期用**同一个** lookup 再校验，使"校验的解析"与"连接用的解析"是同一次解析」。严格说，`assertPublicResolvableTarget`（出站前）与 `createGuardedLookup`（连接期）是**两次独立的 DNS 查询**，并非"一次查询两处复用"。真正防住 rebinding 的是上面第 3 点（回传校验过的地址），而不是"只查一次"。**结论通过，但建议把注释改成「连接期校验的就是建连所用地址，且被拒时不回传地址」**，避免后人误以为无 TOCTOU 窗口。

### ⑧ 平台端点信任边界是否符合裁定 —— **通过 + 观察项**

符合裁定的部分，逐条取证：

| 位置 | 行为 | 判定 |

| spec | `平台 defaultEndpoint 非 https → 不抛错，落 WARN，strictEgress=false`、`平台端点连 http://127.0.0.1 也不被守卫拦截` | ✅ |

**⚠️ 观察项：一条条件性误接路径**

`ai-config.service.ts:186`：

```ts
baseUrl: resolved.providerConfig.baseUrl || external.baseUrl,
```

resolved 优先。若同时满足：
1. `resolved.provider`（平台或租户解析出的 provider 名）**命中外部模型库** ⇒ 走 `registerExternal` 创建的 `OpenAICompatProvider`；
2. `resolved.providerConfig.baseUrl` 是**平台 defaultEndpoint**（`strictEgress=false`）；

⇒ 此时 baseUrl 取平台端点，但 `OpenAICompatProvider` **无条件**挂守卫（第 ⑦ 项的不对称）⇒ **平台端点被按 strict 口径严格校验**，若其非公网 HTTPS 会被 400 拒绝，**与「平台端点只 WARN 不拒绝」的裁定不符**。

- **可达性**：`ai-config.external-merge-priority.spec.ts:167` 已确认「外部模型命中 ⇒ `strictEgress` 仍透传自 resolved」（即平台路径为 false），说明该组合路径被实际走过 ⇒ 路径可达。
- **触发条件**：还需平台端点非公网 HTTPS。按业主 2026-10-09 补充事实（各端点都有各自域名、均为公网 HTTPS），**当前生产不触发**。
- **判定**：主体通过；此路径**判为观察项，不判红**。建议阿坚/凌舟决定是否在 `OpenAICompatProvider` 上也按 `strictEgress` 收口（需确认外部模型库是否应一律严格——它本身是平台级资源，一律严格也说得通，那就应把裁定口径写进注释）。
