## 四、🟡 B-3 残留缺陷：判据仍在应用层，UPDATE 结果被丢弃

### 4.1 缺陷描述

`consume()` 在扣减前先`getOrCreate(tenantId)` 读**内存快照**，用快照决定走哪个分支：

```typescript
// billing.service.ts:67-86
const billing = await this.getOrCreate(tenantId);   // ← 内存快照
if (billing.enabled !== 1) { ...recordBillingConsume('skipped'); return; }

if (billing.freeChatCount > 0) {                    // ← 用快照判定
    await this.repo.query(
    `UPDATE t_tenant_ai_billing
          SET free_chat_count = GREATEST(free_chat_count - ?, 0)
        WHERE tenant_id = ? AND free_chat_count > 0`,
      [chatCount, tenantId],
    );
  this.metrics.recordBillingConsume('ok');           // ← 不看 affectedRows
    return;
}
```

扫描该文件的并发保护关键字，**全部为 0**：

```
transaction = 0    setLock = 0    pessimistic = 0
FOR UPDATE = 0     QueryRunner = 0    VersionColumn = 0    DataSource = 0
```

### 4.2 后果

并发场景（快照 `free_chat_count = 1`）：

1. req1 与req2 同时读到快照 `freeChatCount = 1`，**都进入第一个分支**；
2. req1 的 UPDATE 匹配 1 行 → 扣成 0，记 `ok`；
3. req2 的 UPDATE 因 `WHERE free_chat_count > 0` 不匹配 → **实际影响 0 行，代码不检查，照样记 `ok`**；
4. ⇒ **第二次请求被免费放行且从未扣减**，指标显示 `ok` 而账上少扣一次。

方向是**少收费**（对平台不利，但不会凭空多扣），金额有界（≤ 一次 `chatCount`）。

### 4.3 定性：Blocker → Major

**降级理由**：原缺陷是"每次并发都丢失更新"（无WHERE 约束，N 个并发请求最多只扣 1 次）；现缺陷需要**恰好在最后一次免费次数的瞬间并发**才触发，窗口窄一个数量级。且数据不会损坏，只是少扣。

**但仍不可关闭**，理由有两条：

1. `recordBillingConsume('ok')` 是**假的**——它统计的是"代码走到了这一行"，不是"确实扣了"。计费指标的可信度是这次修复的核心价值，假的 `ok` 比没有指标更危险（会掩盖真实漏费）。
2. 它与阶段 1 的三级语义直接相关：`consume` 的 catch 目前是 `logger.error` + 指标，属手工实现的"半套 bestEffort"。等 P1-B 迁移到 `bestEffort` 时会顺带碰到这段代码，届时应一并把判据下沉。

### 4.4 建议修法（不在本轮实施）

治本是**把判据下沉到数据库，让应用层不看快照**：

```sql
-- 单条 UPDATE 完成判据 + 扣减，返回是否命中
UPDATE t_tenant_ai_billing
   SET free_chat_count = GREATEST(free_chat_count - ?, 0)
 WHERE tenant_id = ? AND free_chat_count > 0
-- affectedRows === 0 ⇒ 免费次数已耗尽，此时才按 planType 判断是否走余额扣减
```

即：**先用 `affectedRows` 判定"是否还有免费次数"，据此决定要不要落入余额分支**，而不是用内存快照的 `freeChatCount > 0` 提前分流。这样无论多少并发，免费次数只会被正确扣减 N 次，且每次请求都落到正确分支。

配套：`recordBillingConsume` 应改为按 `affectedRows` 记录（命中记 `ok`，未命中且走了余额分支记 `ok` 但打独立标签），保证指标与账目一致。

## 五、A-3 答复核实：⚠️ 部分属实，且发现了新事实

用户答复原文："`employee_id` 是 PrimaryGeneratedColumn（MySQL 自增，跨租户全局唯一），且 `tasks()` 端点先经 `getById(id, tenantId)` 校验归属"。

我上次核实时路径猜错（`src/database/entities/ai-employee-task.entity.ts` 不存在），这次定位到真实路径 `src/database/entities/ai-employee.entity.ts`（Employee 与 EmployeeTask 两个实体**同文件**）。

| 答复项 | 核实结果 |
| --- | --- |
| `employeeId` 自增全局唯一 | ✅ 属实。`AiEmployeeTaskEntity.employeeId!: number`，实体主键 `@PrimaryGeneratedColumn({ type: 'int', unsigned: true })` |
| `tasks()` 先经 `getById(id, tenantId)` | ✅ 属实。`employee.controller.ts:132-135` 先取 `tenantContext.requireTenantId()` → `getById(id, tenantId)` → 才`listTasksFor` |

**但我顺带查出了两条报告和答复都没提的事实**：

1. **`listTasksFor` 自身没有任何租户过滤**（`employee.service.ts:479-492`）：

```typescript
async listTasksFor(employeeUid: string, employeeId: number) {
  return this.taskRepo.createQueryBuilder('t')
    .where('t.employee_id = :eid OR t.dispatched_by = :uid', { eid: employeeId, uid: `employee:${employeeUid}` })
    .orderBy('t.id', 'DESC').take(50).getMany();
}
```

它**完全依赖调用方先做归属校验**。这在当前唯一调用点成立，但这是**约定而非机制** —— 与第九轮根因 2「一致性靠人工纪律」同型。将来任何人新增一个调用点而忘了先校验，就是跨租户泄露（且 `OR dispatched_by` 这个条件写错还会更糟）。

2. **`getOrCreate` 有并发双写窗口**（`billing.service.ts:115-121`）：`findOne` 未命中 → `save(create(...))`。两个并发请求同时未命中 → 双写。是否有唯一键约束我没查（不在本次范围），若无约束则会产生重复计费行。

⇒ **A-3 维持建议级，不升级**（当前无实际越权路径），但 `listTasksFor` 缺租户条件这条建议记入阶段 2（数据访问收敛）：应把 `tenantId` 作为参数下沉到方法内部，与 `completeTask` / `markTaskRated` 的做法对齐（那两个方法已经带`{ id, tenantId }` 条件，做法是正确的）。
