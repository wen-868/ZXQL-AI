## 六、风险与自我报备

1. ⚠️ **新增两张 AI 域表，部署需先跑迁移**：`024_ai_reminder_delivery.sql` 若未执行，
   补偿器的投递状态读写会报 `Table ... doesn't exist`，导致所有条目都被判"通知失败"
   （不会误标成功，但会持续重试且不推送）。**部署顺序：迁移 → 重启**。
   已按仓规范用 `CREATE TABLE IF NOT EXISTS`，可重复执行。
2. ⚠️ **`CAST(s.id AS CHAR)` 与 `occurrence_at` 的精度匹配**：投递表 `occurrence_at` 为
   `DATETIME(3)`，而 `t_ai_schedule.remind_at` 若为 `DATETIME`（无毫秒）也能精确匹配；
   若两者精度不同可能漏匹配。已在 SQL 里用同列比较，未做显式截断 ——
   **需在真实库验证一次**（本单未执行迁移，无法自证）。
3. ⚠️ **quiet 时段的"08:00 摘要"实现方式变更**：F1 按派单卡要求把摘要改成
   由批次指纹幂等控制（`t_ai_reminder_digest_sent`），不再有独立的"08:00 积压查询"路径。
   08:00 之后的下一次 cron（非 quiet）会把安静时段已入箱但未推送的条目重新选中，
   **按 >3 规则发一条摘要**（若 ≤3 则逐条推）。这满足"08:00 汇总只发一次"，
   但语义上是"恢复推送"，与卡中"08:00 生成聚合摘要"的措辞略有差异 —— 如实报备。
4. ℹ️ 未改 `backend/**`、`migrations` 既有文件、MS 仓、AI 工具、tabBar；未触碰主工作树 AI-48 改动。
5. ℹ️ 上一轮 P2-3 的 18 例 spec 被**重写为 20 例**（去掉失真的拆分 mock，新增 ⑫~⑱）。
   全量从 1999 → 2001（+2），符合"基线不减"。
