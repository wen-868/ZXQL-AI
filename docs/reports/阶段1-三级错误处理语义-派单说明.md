## 一、为什么必须有这一层

第九轮查明：全库 **96 处** `catch` 块采用同一个反模式 ——

```typescript
} catch (err) {
  this.logger.warn(`xxx失败（非致命）：…`);
  // 然后返回降级值 / undefined / false / []
}
```

**问题不是"写了 catch"，而是这个模式不分场合地覆盖了三类语义完全不同的操作**：

| 操作类别 | 失败后应该怎样 | 现在实际怎样 |
|---|---|---|
| **旁路增强**（记忆/RAG/规则注入） | 降质即可，无需追回 | ⚠️ 恰好合适 |
| **最终一致**（计费/审计/推送） | 允许延后，但必须最终到达 + 失败可观测 | ❌ 直接丢弃，无痕 |
| **写路径真值**（计费真相/用户可见状态/写工具结果） | **绝不能谎报成功** | ❌ 谎报成功 ← 灾难 |

7 个"虚假成功"缺陷（第九轮 Blocker/Major 中的一类）本质是**同一模型的 7 个实例**：
逐个修会一直修不完，建好这一层才是一次性收口。

## 二、三级语义契约（实施方按此实现）

### 2.1 判据：如何决定某个 catch 属于哪一级

```
问：如果这个操作失败了，用户最终看到的"成功"是不是假的？
├─ 是（真相被掩盖）→ mustSucceed
└─ 否，再问：这笔数据丢了会不会造成业务账目不平/合规证据缺失？
   ├─ 会 → bestEffort（必须可靠投递 + 失败可观测）
   └─ 不会，只是回答质量下降 → degrade
```

### 2.2 三级语义定义

| 级别 | 函数 | 失败行为 | 日志 | 观测 | 典型场景 |
|---|---|---|---|---|---|
| **必须成功** | `mustSucceed(op, ctx)` | **上抛**（包装为 AIError，带稳定错误码） | `error` | 告警 + 指标 | 写令牌注册、计划步骤挂起、计费真相、清隐私操作回执 |
| **尽力可靠** | `bestEffort(op, ctx)` | 记录到持久死信（表/Redis），**不阻断主流程** | `error` | 告警 + 指标 + 死信队列 | 计费落账、审计留痕、用量汇总、推送广播 |
| **可降级** | `degrade(op, fallback, ctx)` | 返回 fallback | `warn` | 指标 | 长期记忆检索、RAG 增强、规则注入、向量库装载 |

### 2.3 关键约束（防止实施走偏）

1. **`mustSucceed` 不许静默**：必须 `throw`，绝不允许内部 catch 后返回默认值
2. **三级都要带指标**：`ai_error_semantics_total{level,op}`，否则未来无法观测失败率
3. **错误码稳定**：沿用 `src/common/ai-errors.ts` 既有体系，不新造一套
4. **`ctx` 必填**：至少含 `{ op: string, tenantId?: string }`，日志与告警要能定位
5. **不得改变现有函数的对外签名**：迁移是内部行为变化，不能破坏 119 个 spec

### 🔴 P0 发现（2026-10-07 10:35，林夕独立复现确认）

P1-C 收尾时发现 **`bestEffort` 的「永不抛」契约在实现层是破的**，
我已用**真实源码**（非等价逻辑复现）端到端确认：`P0_PROBE_ESCAPED = true`。

`src/common/error-semantics.ts:276-284` 的 `messageOf`：

```typescript
function messageOf(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (typeof error === 'string') return error;
  try {
    return JSON.stringify(error) ?? String(error);
  } catch {
    return String(error);   // ← catch 块本身不是保护边界
  }
}
```

**本质**：`catch` 块里的 `String(error)` 会调 `error.toString()`，而 `toString()`
是**用户代码**，可以抛。`catch` 块不是保护边界 —— 这是这个 bug 的真正成因。

触发需三条件同时满足：抛出的不是 `Error` 也不是字符串 + 值循环引用 +
该值 `toString()` 自己抛。11 种抛出物边界实测中，**仅「循环引用 + toString 抛」会冒泡**；
`Error` / `TypeError` / 字符串 / `undefined` / `null` / `{}` / `Symbol` / `BigInt` 全部安全。

**当前不触发**（审计真实路径抛的是 TypeORM `Error` 实例，走 `instanceof Error` 分支），
**但风险在未来**：`audit-logger.ts:537` 的 `void bestEffort(fn, ctx)` 是
**不 await 不挂 catch** 的高危形态 ⇒ 一旦某个 op 包装了抛非 `Error` 值的第三方 SDK，
就把「静默降级」升级为 `unhandledRejection`。

⚠️ 同一缺陷还波及 `toCriticalError`（:289 也调 `messageOf`）⇒
**修法必须是「让 `messageOf` 永不抛」，不能是在 `bestEffort` 外再包一层 catch**
（后者只把问题往后挪，`mustSucceed` 路径同样中招）。已按此派发修复。

> 💡 **这条是「契约测试有价值」的最强证据**：如果当初没要求写
> 「`bestEffort` 永不抛」的契约测试，这个破口会一直躺着 —— 因为
> 现有 96 处catch 的业务行为测试**全都绿**（degrade/bestEffort 类迁移
> 不改变业务行为，冒泡与否对现有断言不可见）。

#### 🔴 派单本身的盲区：契约测试测错了对象（2026-10-07 10:50，林夕）

P1-C 交了 21 条契约用例、全绿。我反测发现**它们对 `messageOf` 破口零信号**：

|反测 | 手法 | 结果 |
| --- | --- | --- |
| 我的反测 | `messageOf` 的 `catch { return String(error) }` → `catch { throw error }` | **21 条全绿，一条没红** |

原因：**用例测的是「调用方 `bestEffort` 是否冒泡」，不是「被调方 `messageOf` 是否健壮」**。
缺陷藏在被调方时，调用方测试天然看不见 —— worker 的反测 A/B 都动的是下游
（sink 的 catch、bestEffort 的 catch 首行），所以能测出下游的保护，却测不出上游的漏洞。

⇒ **派单时必须明确「测被调方，不只测调用方」**。凡是要保证「永不抛」的底层工具函数，
都要有一条**直接针对它**的用例，且对它单独反测。

**验收标准随之更新**：新增的 `messageOf` 用例在「修复前红、修复后绿」，
且对它单独反测（catch 改 `throw`）时必须变红；`mustSucceed` 路径
（`toCriticalError` :289 也调 `messageOf`）同样要覆盖并反测。

> 💡 这条与教训第 11 条（批量替换静默失败）同源：
> **工具/测试层的错误会系统性地给出关于被测对象的错误结论**。
> 21 条全绿在这里不是"覆盖到位"，而是"测不到点子上"——
> 但它看起来和"覆盖到位"一模一样。
