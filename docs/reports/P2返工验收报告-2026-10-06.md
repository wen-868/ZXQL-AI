## 三、P1：NX 锁 owner + Lua CAS —— 缺陷彻底封堵 ✅

### 实现核实

```typescript
const owner = randomUUID();                    // crypto.randomUUID，非 Math.random
const ok = await this.redis.set(`ai:wg:lock:${token}`, owner, 'PX', 5000, 'NX');
return ok === 'OK' ? { ok: true, owner } : { ok: false };

private static readonly LOCK_RELEASE_LUA =
  "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
// 释放：this.redis.eval(LOCK_RELEASE_LUA, 1, key, owner)
```

- ✅ 锁值存随机 owner（`crypto.randomUUID()`，真随机）
- ✅ 释放走 Lua 原子脚本比对 owner 才删（`get==owner then del`）
- ✅ `acquireTokenLock` 返回值改为 `{ok, owner}` 结构，三处调用点（`confirm` / `cancel` 及降级分支）**全部适配**
- ✅ 降级口径保持一致：Redis 不可用时返回 `{ok: true, owner: 'memory'}`，且 `releaseTokenLock` 遇 `owner === 'memory'` 直接 return，不做无意义的 Redis 调用

### 缺陷封堵验证（模拟 Redis + Lua CAS 跑完整时间线）

**修复前（上一轮的 `无条件 del`）**：
```
0ms     A 获锁（锁值 uuid-A）
5100ms  锁自然过期
5110ms  B 获锁（锁值 uuid-B）← A 还在跑
5300ms  A 的 finally del → B 的锁被误删
5400ms  C 获锁成功 ← B 还在跑，互斥失效 ✗
```

**修复后（本轮 Lua CAS）**：
```
0ms     A 获锁（锁值 uuid-A）
5100ms  锁自然过期
5110ms  B 获锁（锁值 uuid-B）
5300ms  A 的 CAS 释放：get(key)=uuid-B ≠ uuid-A → 返回 0，不删
5400ms  C 获锁失败 ← 正确拒绝，互斥保持有效 ✓
```

**结论**：上一轮指出的"慢请求下互斥退化为无锁"缺陷**已彻底封堵**。
