## 一、`affectedRows` 语义的确认方式与结论

### 结论（先说结论）

> **`CLIENT_FOUND_ROWS` 默认是开启的**（mysql2 的默认 flag 列表里就有它），
> 因此 TypeORM `repo.query()` 拿到的 `affectedRows` 是**「匹配行数」**而不是
> 「实际变更行数」。
>
> **这对本卡是有利的**：`UPDATE ... WHERE free_chat_count > 0` 未命中时
> `affectedRows = 0`，命中时 `affectedRows ≥ 1`。
> 即「值是否恰好变化」这一不确定性**完全不影响本卡的判据**——
> `GREATEST(free_chat_count - ?, 0)` 在 `free_chat_count = 1, chatCount = 1` 时
> 值确实会变（1 → 0），但即便值不变（如 `chatCount = 0`），因FOUND_ROWS
> 按匹配计数，仍会返回 1。**判据在两种语义下都成立**，比任务卡假设的更稳健。

### 确认方式：**读驱动源码 + 实执行 mysql2 自己的代码**（非"想当然"）

本机 **无可用 MySQL**（实测：`netstat` 无 3306 监听、无 `mysql`/`mysqld` 客户端、
无 mysql/maria 服务；实为MariaDB 11.4.5 未启动，生产是 MySQL 8.0）。
⇒ **本条未经真实库验证**，采用下面两级可核证的方式确认。

**第1 级 · 源码取证**

| 事实 | 出处 |
|---|---|
| `FOUND_ROWS` 在 mysql2 **默认 flags 列表**中 | `node_modules/mysql2/lib/connection_config.js:230` |
| flag 合并逻辑：默认列表逐个 OR，用户 `-XXX` 才剔除 | 同文件 `mergeFlags`（`:199-225`） |
| `FOUND_ROWS` 常量值 = `0x2` | `mysql2/lib/constants/client.js:11` |
| `affectedRows` 从 OK 包直接读线缆值 | `mysql2/lib/packets/resultset_header.js:29` |
| TypeORM 仅在 `useStructuredResult` 时才把它映射为 `affected`；<br>`repo.query()` 走 `result.raw`，即OkPacket 本体 | `typeorm/driver/mysql/MysqlQueryRunner.js:173-180` |

**第 2 级 · 实跑驱动代码（决定性证据）**

不连库，直接调用 mysql2 自己的 `ConnectionConfig`，模拟 TypeORM
`MysqlDriver` 的默认路径（`options.flags` 未配置 ⇒ `undefined`）：

```bash
$ node -e "

const ClientFlags = require('./node_modules/mysql2/lib/constants/client.js');

合并后是否含PROTOCOL_41: true
FOUND_ROWS 位值        : 2
```

**⚠️ 这一条纠正了任务 brief 的前提假设**，且方向对本卡有利（见结论）。

### 顺带确认的一个真实坑：字段名是 `affectedRows`，不是 `affected`

TypeORM 有两个容易混淆的返回形态：

- `repo.update(...)` ⇒ `UpdateResult`，字段名 **`affected`**
- `repo.query(...)` ⇒ mysql2 **OkPacket**（本卡使用），字段名 **`affectedRows`**

写错的后果是**静默的**：`undefined > 0` 为 `false` ⇒ 每次都判为"未命中"
⇒ 每次都错落余额分支。已用独立用例锁死（见 §三 用例 5）。

### 遗留不确定项（诚实标注）

- **未经真实 MySQL 8.0 验证**。虽然 `FOUND_ROWS` 语义是 MySQL 协议层标准行为、
  且驱动源码路径已实测，但严格来说未在生产同版本库上跑过。
  建议验收时在真实库执行一次：
  `UPDATE ... WHERE free_chat_count > 0` 分别在「有剩余」与「已耗尽」下确认
  `affectedRows` 分别为 `1` 与 `0`。
- 唯一残余边界：`chatCount = 0` 时 `GREATEST(x-0,0)` 值不变。因FOUND_ROWS
  按匹配计数，仍返回 `≥1` ⇒判据仍正确（会记 `ok`）。此时"扣了 0 次"记`ok`
  语义可接受（未超扣）。**当前唯一调用点 `orchestrator.service.ts:1342`
  未传 `chatCount`，走默认值 1**，故生产不会触发。

## 二、改造后的判据逻辑

### 改造前（用内存快照提前分流 + 不看 affectedRows）

```typescript
const billing = await this.getOrCreate(tenantId);   // ← 内存快照
if (billing.enabled !== 1) { recordBillingConsume('skipped'); return; }

if (billing.freeChatCount > 0) {                     // ← 快照判分支
  await this.repo.query(
    `UPDATE t_tenant_ai_billing
        SET free_chat_count = GREATEST(free_chat_count - ?, 0)
      WHERE tenant_id = ? AND free_chat_count > 0`, [chatCount, tenantId]);
  this.metrics.recordBillingConsume('ok');            // ← 不看 affectedRows
  return;
}
if (billing.planType !== 'monthly') { /* 扣余额 */ recordBillingConsume('ok'); return; }
recordBillingConsume('skipped');                     // 月费套餐
```

### 改造后（判据下沉到 SQL，用 affectedRows 裁决）

`src/tenant/billing.service.ts:135-147`（核心）：

```typescript
const freeResult: unknown = await this.repo.query(
  `UPDATE t_tenant_ai_billing
      SET free_chat_count = GREATEST(free_chat_count - ?, 0)
    WHERE tenant_id = ?
      AND free_chat_count > 0`,
  [chatCount, tenantId],
);

if (affectedRowsOf(freeResult) > 0) {
  // 免费次数确实扣减到了（命中 ≥1 行）——此时记 ok 才是真的
  this.metrics.recordBillingConsume('ok');
  return;
}

// affectedRows === 0 ⇒ 免费次数已耗尽（并发下同样准确，因为判据在 DB 侧）
// 此时才读快照的 planType 决定是否走余额扣减
if (billing.planType !== 'monthly') { /* 扣余额 */ recordBillingConsume('ok_balance'); return; }

recordBillingConsume('skipped');                     // 月费套餐
```

配套的边界收敛函数（`:24-40`）：

```typescript
function affectedRowsOf(result: unknown): number {
  if (typeof result !== 'object' || result === null) return 0;
  const value = (result as { affectedRows?: unknown }).affectedRows;
  return typeof value === 'number' ? value : 0;
}
```

### 逻辑对比

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 「是否还有免费次数」判据来源 | 应用层内存快照 `billing.freeChatCount` | **数据库**（`WHERE free_chat_count > 0` + `affectedRows`） |
| UPDATE 未命中时 | 照记 `ok`（**假 ok**） | 不记 `ok`，落入余额分支 |
| 分流时机 | 快照判据**提前分流** | 先扣免费次数，**事后按 affectedRows 裁决** |
| `ok` 的含义 | "代码走到了这一行" | **"确实扣减到了"** |
| 命中免费 / 落入余额 | 都记 `ok`，**不可区分** | `ok` / **`ok_balance`** 可区分 |
| 并发下正确性 | N个并发可全部免费放行 | 免费次数**只会被正确扣减 N 次** |

### 遵守的两条硬约束

1. **未用事务包一层**✅ — grep 实测 `transaction|FOR UPDATE|setLock|pessimistic|QueryRunner|VersionColumn|DataSource` 在 `billing.service.ts` 中**命中 0**。
   判据已下沉到 SQL，单条 UPDATE 的原子性由 InnoDB 行锁保证，不需要事务。
2. **未引入全局并发设施**✅ — 未引入 `@VersionColumn` / `createQueryRunner`，
   不越界到阶段 3。

## 八、补充：补齐 `render()` 输出（团队负责人裁决后追加）

这是**收口**，不是扩大范围。

### 改动（`metrics.service.ts`，+5 行）

**不是 spec 断言过时**，且**未放宽任何断言**。
