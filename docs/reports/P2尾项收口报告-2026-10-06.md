## 一、逐项核查过程

### 1. `activate` 并发冲突抛通用 Error —— ❌ 从未修

**核查依据**：`grep -rn "激活冲突" src/` → `src/evolution/evolution-version.service.ts:184`。

原代码：
```typescript
if ((result.affected ?? 0) === 0) {
  throw new Error(`版本激活冲突：id=${id} 已非 staged 状态...`);
}
```

**问题**：并发激活被抢先时抛通用 `Error`，全局过滤器兜成 **500**。前端无法区分「服务端真故障」与「有人抢先激活了」，前者应告警、后者只需提示重试。

**讽刺之处**：同一文件的 `assertStatus`（:499）已经在用 `ConflictException` 抛 409，且 `ConflictException` **已在 import 列表里** —— 只有这一处漏了。

**修复**：改抛 `ConflictException`，与 `assertStatus` 口径一致。
```typescript
throw new ConflictException(
  `版本激活冲突：id=${id} 已非 staged 状态（可能被并发操作抢先激活）`,
);
```

**补充测试**：原有用例只断言消息文本（`toThrow(/激活冲突|已非 staged/)`）—— 抛任何 `Error` 都绿，属零信号断言。补了一条显式断言类型与状态码的用例：
```typescript
expect(err).toBeInstanceOf(ConflictException);
expect((err as ConflictException).getStatus?.()).toBe(409);
```

### 3. 计划卡多步同名工具一次全标 done —— ❌ 从未修（本轮最实质的缺陷）

**核查依据**：`chat-planning.ts` 的 `matchPlanStepsByTool` 精确匹配分支。

原代码：
```typescript
const hits: number[] = [];
steps.forEach((s, i) => {
  if (s.tool === toolName && !doneIds.has(s.id)) {
    doneIds.add(s.id);
    hits.push(i);
  }
});
if (hits.length > 0) return hits;
```

**我用脚本实测构造了缺陷**（不是看代码猜）：
```
计划：[s1 → queryInventory（查杭州仓库存）, s2 → queryInventory（查北京仓库存）]
第 1 次调用 queryInventory → 返回 [0,1]，两步全标 done
第 2 次调用 → 返回 []（第 2 步仍未完成，但已无法再推进）

三步同名场景 → 第 1 次调用返回 [0,1,2]，计划卡瞬间显示 3/3 完成
```

**影响**：用户说「先查杭州仓库存，再查北京仓库存」，planner 拆成两步同名工具。LLM 执行第 1 步后前端计划卡已显示「2/2 完成」，而业务动作只做了一半。**这是进度虚报**，与该函数自身注释反复强调的「避免虚报完成」目标直接冲突。

**更严重的是注释与实现自相矛盾**：函数头注释写「计划内已声明过该工具 → 判为重复调用（同一工具查两次），不算推进」，但 `forEach` 实现恰恰是「一次标完所有同名步骤」。

**测试盲区**：原有 20 个用例的 `STEPS` 只有**1 个** `queryInventory` 步骤，`toEqual([0])` 恰好成立 ⇒ 测不出多步场景。

**修复**：改为 `findIndex` 命中第一个即止：
```typescript
const hitIdx = steps.findIndex(
  (s) => s.tool === toolName && !doneIds.has(s.id),
);
if (hitIdx >= 0) {
  doneIds.add(steps[hitIdx].id);
  return [hitIdx];
}
```
同步修正函数头注释（原文描述的是旧的全量语义）。

**补测试 2 条**：两步同名逐步推进 + 三步同名「每次返回长度恒为 1」。

### 4. `saveHistory` 读改写竞态 —— ❌ 从未修

**核查依据**：`memory-manager.service.ts` 的 `saveHistory`；`grep -c "watch\|multi\|pipeline"` → **0**。

原代码是纯分离的读改写：
```typescript
const raw = await this.redis.get(key);        // 读
const combined = [...existing, ...newMessages]; // 改（内存）
await this.redis.setex(key, TTL, JSON.stringify(truncated)); // 写
```

**问题**：同会话并发（用户快速连发两轮、或前端重试）时两个请求都读到同一份`existing`，后写的覆盖先写的 ⇒ **整轮对话丢失**。TTL 只有 1 小时，历史丢了无法恢复。

**修复**：改为 Redis 乐观锁 `WATCH/MULTI/EXEC`：
```typescript
for (let attempt = 0; attempt <= WATCH_CONFLICT_MAX_RETRIES; attempt++) {
  await this.redis.watch(key);
  const raw = await this.redis.get(key);
  // ... 拼装 ...
  const res = await this.redis.multi().setex(key, TTL, json).exec();
  if (res === null) continue;  // WATCH 检测到冲突 → 重试
  return;
}
```
设计要点：
- `exec()` 返回 `null` 是 Redis WATCH 的标准冲突信号（`ioredis` 语义）
- 重试上限 3次（`WATCH_CONFLICT_MAX_RETRIES`），超限则 warn 后按最后一次快照写入 —— **降级保对话不中断**
- `unwatchQuietly()` 在 `finally` 中清理，避免连接残留 WATCH 状态污染后续命令
- 保持原有的 try/catch 非致命降级口径不变

**补测试 3 条**：冲突自动重试不丢消息 / 冲突超限不抛错且有重试上限 / `watch` 确实被调用。

> 补测试时我犯了一个桩错误并当场发现：初版桩在 `setex()` 调用时就写 store，而真实 Redis MULTI 是 `exec()` 时才落盘 —— 导致重试时读到已写入的值又拼一次，消息重复。已修正为「`exec()` 时才落盘」。

### 5. 桌面端 `data-uid` 未转义 —— ❌ 从未修

**核查依据**：`desktop/app/index.html:457`。

```javascript
`<div class="sess ..." data-uid="${e.employeeUid}">`+
  `<i></i><div><div style="...">👤 ${esc(e.name)}</div>`+
  `<div style="...">${esc(e.post)} · ${esc(e.status)}...</div></div></div>`
```

**问题**：同一模板里 `e.name` / `e.post` / `e.status` **都用了 `esc()`**，唯独 `data-uid="${e.employeeUid}"` 漏了。是遗漏而非有意为之。

**核实 `esc` 能否用于属性上下文**：`const esc=s=>String(s??'').replace(/[&<>"']/g, ...)` —— 覆盖 5 个字符，**包含属性定界符 `"`**，可用于属性值。✔

**修复**：`data-uid="${esc(e.employeeUid)}"`。

> 说明：`employeeUid` 是内部生成的标识符，实际注入风险低。但这是上一轮 P1-6 协议白名单修复的同类遗漏，属收口不彻底。

## 四、踩坑记录（两条，都是我自己犯的）

### 1. 测试桩制造了假缺陷
初版 `multi` 桩在 `setex()` 调用时就写 `store`，而真实 Redis MULTI 是**`exec()` 时才落盘**。结果重试时读到已写入的值又拼一次，测出「消息重复」这种**不存在的缺陷**。
⇒ 写 Redis/ioredis 桩必须对齐真实语义（`MULTI` 内命令只入队，`EXEC` 才生效）。已抽成 `makeTx` 并在注释中标注该坑。

### 2. 用例报错暴露了断言零信号
`activate` 冲突的原有用例只断言消息文本（`toThrow(/激活冲突/)`）—— 抛**任何** `Error` 都绿。这正是本项目反复出现的「零信号断言」模式。
⇒ 断言异常类型必须用 `toBeInstanceOf` / `getStatus()`，不能只断言消息。
