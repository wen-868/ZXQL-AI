## 四、`cleanupExpired` 无调度 —— ✅ 属实，且我发现了报告漏掉的**虚假保证**

### 核实结果

```
cleanupExpired 定义：  confirmation.service.ts:509（会 delete executedMap 过期项）
                     write-guard.service.ts:538
调用方：            仅 spec（confirmation.service.spec.ts:386/445/453）
生产代码调用方：     ❌ 零命中
```

⇒ `executedMap`（`confirmation.service.ts:229`，`new Map<string, ExecutedOperation>()`）
在生产进程中**只增不减，无界累积**。报告属实。

### ⚠️ 报告未提的问题：代码里有"虚假保证"注释

```typescript
// confirmation.service.ts:664
* 记录最终仍由 cleanupExpired() 在窗口到期后清理，不会泄漏。
```

这句注释**承诺的兜底并不存在** —— `cleanupExpired()` 没有任何生产调用方。

**这比"缺调度"更危险**：后来者读注释会认为泄漏已被处理，不会再去补调度。
建议修调度时**同时修正这句注释**（若不修调度，注释就是错的）。

## 五、RAG 口径分裂 —— ✅ 属实，但"静默无效劳动"表述过重

### 分裂确认

| 门 | 位置 | 判定条件 |
|---|---|---|
| 上传门 | `rag.controller.ts:96` | 只查 `EMBEDDING_MODEL` 非空 |
| 注入门 | `context-builder.service.ts:254-255` | 只查 `ENABLE_RAG === 'true'`（默认 `'false'`） |

两者**无交集判断** ⇒ 只配 `EMBEDDING_MODEL` 时，文档上传成功但永不注入对话。属实。

### ⚠️ 修正：并非"内容永远不会注入任何对话"

报告称"管理员上传成功但内容永远不会注入任何对话"。这句话对**RAG 向量通道**成立，
但**漏了一条并行的知识注入通道**：

```typescript
// src/brain/knowledge-rules.service.ts:4-9
* 问题：knowledge/ 下 9 份业务规则文档此前只在 RAG 开启时经 rag-seed 进向量库
* （默认 ENABLE_RAG=false + 需配 embedding）——默认生产姿态下 AI 根本读不到
* 方案：启动后首次使用时加载 knowledge/*.md 到内存（文件名 → 业务域映射），
* 按意图分诊结果注入相关域规则到系统提示词（无 embedding 依赖、零外部服务）。
```

⇒ **知识类内容（`knowledge/*.md` 运营规则）有独立注入通道，不依赖 RAG**。
该服务被 `task-runner.service.ts` / `graph-executor.service.ts` 引用。

**修正后的表述**：RAG 上传的**向量文档**在默认配置下不注入；
但 `knowledge/` 下的运营规则文档另有注入通道。
问题**依然存在**（口径分裂是事实），只是影响面比报告描述的小。
