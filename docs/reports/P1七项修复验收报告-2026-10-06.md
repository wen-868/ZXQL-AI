## 五、验收中发现的待改进项（1 项，建议级，非阻塞）

### graph 续跑 history 把「等待用户确认」记成节点失败

**位置**：`src/brain/graph/graph-executor.service.ts:371-375`

```typescript
state.status = 'paused';
state.pendingWriteToken = write.confirmationId;
state.history.push({
  nodeId: node.id,
  label: node.label,
  success: false,      // ← 「等待用户确认」这个正常中间态被记成了失败
});
```

**问题**：`success` 是 `boolean` 二元类型（`graph.types.ts:103`），**没有中性态可选**。"等待用户确认"既不是成功也不是失败，被迫写成 `false`。

**实际影响**（已逐路径确认，比看起来轻）：
- **不影响安全闭环**：确认/取消/续跑逻辑本身完全正确，用户的确认入口、重试入口、终止逻辑都在。
- **不影响用户界面**：`history` 数组只进checkpointer 持久化，**前端消费的是 `node_end` 事件**，而挂起路径不发 `node_end`。
- **影响的是持久化数据**：同一`nodeId` 在 history 里会出现两条冲突记录——挂起时 `success:false`，确认后续跑再追加一条 `success:true`（`:241-245`）。图历史/审计回溯时同一节点既"失败"又"成功"，语义自相矛盾。

**建议改法**（二选一，都属于小改）：
- 把 `history` 元素类型扩为 `{ nodeId; label; success: boolean | 'awaiting_confirm' }` 或加独立可选字段 `pending?: boolean`，挂起时记中性标记，确认成功后再追加成功记录。
- 或挂起时**不写 history**，确认/取消续跑时再按最终结果写唯一一条。

**验收判定**：**不阻塞放行**。理由是安全语义与用户可见行为均正确，属于持久化数据的语义标注瑕疵 + 扩展性隐患（`boolean` 二元类型已经卡住了正确表达）。建议在下一轮 P2 修复中顺手带上，不要单开一次改动。
