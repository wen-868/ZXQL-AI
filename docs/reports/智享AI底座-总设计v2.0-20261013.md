## 一、业主四条要求（本版的根）

| # | 要求 | 架构含义 |
|---|---|---|
| 1 | **三端账号体系由总台统一管理** | 总台 = 唯一身份真源；三端（管理/运营/AI 底座）账号、租户、角色均由总台创建/管理，各端不自建账号 |
| 2 | **AI 底座可独立运行，能力媲美 Codex/DSH** | AI 底座**不依赖** MS/OPS 即可全功能运行；**编程能力（文件/命令/代码工程）后置**（业主 2026-10-13 裁定：两系统用不到）|
| 3 | **三套各自封装界面** | 三个独立桌面端：管理工作台 / 运营工作台 / AI 底座端 |
| 4 | **办公能力是 AI 底座自身能力** | 推翻"后置占位"裁定：办公为**原生域**，**首批落地文档能力**，后续渐进扩充 |

## 二、部署形态（业主已定：库内置桌面端，操作越简单越好）

### 2.1 单机内嵌形态（默认）

```
桌面端安装包（一个 exe）
  ├── AI 底座服务（NestJS，内嵌启动）
  ├── MariaDB（便携版，随包装，数据目录随装随建）
  ├── Redis 兼容层（Memurai/Garnet 之一，随包装 —— 需实测 ioredis 兼容性）
  └── 桌面 UI（Electron，连本机 127.0.0.1:3016）
```

- 用户操作 = **双击安装 → 启动即用**（MariaDB/Redis 由安装器注册为随应用启停的服务，用户无感）
- AI 底座以 `standalone` 模式运行：**不依赖 MS/OPS**，对话/记忆/RAG/语音/自主任务/办公（文档）全可用；**业务工具族（36 写）自动摘除**（无数据源，摘除有日志）

### 2.2 共享形态（10 人 + 10 数字员工）

**共享的前提 = 库在一台"主机"上**（并发写无法每机独立库再互相同步——那是分布式一致性问题，不做）：

```
局域网
 ├── 主机一台：AI 底座服务 + MariaDB + Redis（安装时选"主机模式"）
 ├── 人类 ×10：桌面端连主机（设置里填主机 IP）
 └── 数字员工 ×10：主机内的服务/会话（天然共享主机库）
```

- 安装向导第一步 = **「本机作为主机」/「连接已有主机」**二选一
- 人类与数字员工的**数据共享**天然成立：同一 MariaDB、同一 Redis、同一 AI 底座实例 —— 权限按账号（总台管理）区分，数据按租户隔离

### 2.3 与生产/双系统的关系

| 模式 | AI 底座状态 |
|---|---|
| standalone（默认） | 纯 AI + 办公；业务工具族摘除 |
| connected-MS（连管理系统） | 加载管理系统工具族（53+43）|
| connected-OPS（连运营系统） | 加载 OPS 工具族 + 注册为 OPS SkillGateway 的 provider（方案 C 双向互联）|
| connected-双系统 | 两个工具族按会话来源互斥可见（scope: ms / ops）|

**演进路径**：单机 → 主机共享 → 双系统联通，**同一套代码、配置切换**（`INTEGRATION_MODE` 扩展为 `standalone / ms / ops / dual`）。

## 三、账号体系（要求 1：总台统一管理，不分端点）

### 3.1 身份真源
- **总台（管理系统平台后台）= 唯一账号真源**：所有用户/租户/角色在总台创建、改权、停启用
- 三端（管理商家端 / OPS 运营端 / AI 底座端）**不自建账号**，一律经总台登录签发的 JWT + 各端 SSO 换票（OPS 已有 `ops/auth/sso` 设计；AI 底座端同范式）
- **AI 底座端登录**：用户在桌面端填总台地址+账号 → 登录（issuer=zhixiang-system）→ AI 底座验签建上下文（复用 TenantMiddleware 口径）

### 3.2 三端账号矩阵（总台视角）
| 端 | 账号载体 | 角色 |
|---|---|---|
| 管理工作台 | `t_sys_user`（已有）| SUPER_ADMIN/OPERATION_ADMIN/WAREHOUSE_ADMIN/FINANCE_ADMIN |
| 运营工作台 | `ops_users`（映射自总台账号，`ops_role_bind`） | ops_admin / ops_viewer |
| **AI 底座端** | **新增**：总台账号 → AI 底座身份映射（`ai_user_bind`，可简化为直接认总台 JWT） | ai_user（读写）/ ai_viewer |
| 平台总台 | `t_platform_admin`（已有） | 平台管理员（管三端账号）|

### 3.3 数字员工的身份
- 数字员工**不是账号**，是 AI 底座内的执行主体（employee 体系已有）—— 以**服务身份**运行（复用 MCP 服务账号范式），审计署名到具体数字员工
- 总台管理的是**数字员工的创建/派岗/停用**（经 AI 底座的 employee 管理端点），与其"运行身份"分离

## 四、办公能力（要求 4：原生域，首批 = 文档）

### 4.1 定位
办公是 AI 底座的**第五业务域**（与销售/库存/…/系统并列），**不依赖 MS/OPS**，standalone 即可用，双系统模式下也可跨端使用。

### 4.2 首批落地：文档能力（v2.1）
| # | 能力 | 说明 | 复用 |
|---|---|---|---|
| 1 | 文档库管理 | 上传/目录/标签/检索；10 人共享、按租户隔离 | RAG 引擎（分块/向量化/检索）已有 |
| 2 | 文档对话 | "这份合同的关键条款是什么"——检索+对话 | 已有（RAG + chat）|
| 3 | 文档生成 | 会议纪要/周报/方案初稿——AI 生成并入库 | LLM 已有；新增**文档写工具**（ai_doc.create）|
| 4 | 数字员工文档任务 | "让员工X整理本月报销单据"——文档能力与数字员工打通 | employee 体系已有 |
| 5 | 权限 | 文档库按租户隔离 + 端内共享（10 人可见性按角色/目录 ACL） | 新增（复用 tenant 隔离范式）|

### 4.3 数据占位（现在建表，避免后期大改）
```
t_ai_doc（文档主表）: id/tenant_id/title/category/owner/source_type/content_hash/
                     storage_path/status/version/created_by/created_at/updated_at
t_ai_doc_chunk（复用 RAG chunk 表结构，加 doc_id 外键语义）
t_ai_doc_acl（可见性）: doc_id/principal_type(user/role/employee)/principal_id/perm(read/write/admin)
```
> 迁移 018 一次建齐（含办公域后续扩展预留字段），**避免二次大改** —— 这正是"不能是占位"的落地方式：表占位先建齐，功能按批次点亮。

### 4.4 后续扩展（每批一个子域，渐进）
批次 2：待办/任务（与数字员工任务打通）；批次 3：审批流（轻量，AI 辅助填单）；批次 4：日程/提醒；批次 5：通知中心（复用 proactive-push）。

## 五、编程能力后置（要求 2 的裁剪）

- **后置**：本地文件系统操作/命令执行/代码工程理解（Codex 形态）—— 两系统业务用不到，且沙箱安全工程量大
- **独立运行 ≠ 有编程能力**：standalone 模式提供的是「对话/记忆/RAG/语音/自主任务/办公/数字员工」—— 对标 **DSH 通用助理形态**（不含 Codex 编程形态）
- 保留钩子：`ToolScope`/`ToolRegistry` 天然支持未来加 `ops_bash` 类工具（本机已装 dsh-ops 可参考），后置不等于堵死

## 七、实施路线（修订版）

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **A1** | 内嵌存储：MariaDB 便携化 + Redis 兼容层选型实测（ioredis×Memurai/Garnet） | 无 |
| **A2** | standalone 模式：`INTEGRATION_MODE=standalone` 下业务工具族摘除、办公域上线（018 迁移：办公表占位齐建 + 文档能力第一批） | A1 |
| **B** | 总台统一账号（MS 平台后台扩展；AI 底座/OPS 的 SSO 换票） | 跨线（MS 侧）|
| **C** | 三套桌面封装（AI 底座端升级 / 管理工作台 / 运营工作台） | A2 + B |
| **D** | 办公渐进（批次 2~5：待办/审批/日程/通知） | A2 |
| **E** | 双系统工具对接（方案 C 四期：身份映射→OPS Provider→ops 工具族→治理） | B |
| **F（后置）** | 编程能力（文件/命令/代码工程） | 业主触发 |

**当前可立即开工**：A1（存储内嵌实测）+ 018 迁移草案（办公表）—— 都是 AI 底座仓内的活。

## 八、本设计明确不做 / 边界

- 编程能力后置（F），不做文件/命令类工具
- 不做分布式多主机数据同步（共享库 = 单主机 MariaDB，够 10+10 规模；更大规模属业务增长后的独立演进）
- 不改管理系统侧既有功能（总台扩展为增量）
- 办公批次 2~5 的**产品细节**待第一批（文档）上线后按用户反馈定

## 补充（2026-10-14）：数据链路四期并入路线 + 三项定案

业主授权按真实场景判断后，三项确认定案（《数据链路能力规划》§八）：
1. **统计部署形态 = AI 工具族**（走 ToolExecutor 治理链；对话式按需组合维度是 LLM 强项）
2. **触发方式 = 定时 + 事件 + 对话三种都要**（proactive 框架支持前两种；第三种=P1 统计工具族）
3. **闭环范围**：一期=建议→工作流创建（追踪创建/执行状态）；二期=效果评估（依赖 OPS 回传接口与数据积累，不阻塞）

**路线修订**：E1 双系统身份映射之后，并入数据链路四期（P1 统计工具族 → P2 分析扩展 → P3 总结升级 → P4 建议落地+闭环）；数据链路与办公第一批（文档）可并行（不同域、无文件冲突）。
