## 一、裁定内容（凌舟，已拍板，不要再论证）

`t_ai_audit_log` 归**管理系统仓**所有，**ZXQL-AI 撤销 001 的建表**。

事实依据：
- `ZXQL-AI/migrations/001_audit_log.sql`（`CREATE TABLE t_ai_audit_log`，业务库侧）
- `wen-ssystem/docs/migrations/121_ai_base_tables.sql:58` 也`CREATE TABLE IF NOT EXISTS t_ai_audit_log`
- 两处都建同名表、都IF NOT EXISTS，故**当前无运行期冲突**

**凌舟的四条理由（照此执行，不要另找理由推翻）**：
1. 表在业务库 ⇒ 业务库 schema 归业务仓，与其它业务表同源，避免两条链路各建同名表后**结构性漂移**（这正是本域反复出问题的病根：同一概念多个副本）
2. 归属单一后「列变更」只有一个落点，AI 底座**只读写、不建表**
3. 撤销**不是删文件**：001 改为存在性断言/守卫跳过（表不存在时打印「应由管理系统仓 121 建表」并 `EXIT=0`），并**保留其列归属约定注释作为文档**
4. 顺序依赖写明：管理系统仓迁移（后端启动期 `runMigrations`）**先于** AI 底座迁移（当前部署顺序已满足）

## 二、实施要求

### R1 改 `migrations/001_audit_log.sql` 为存在性断言

**不是删除，是改造成断言脚本。** 要求：

- 用 `information_schema` 判定 `t_ai_audit_log` 是否存在
- **存在** ⇒ 输出类似 `t_ai_audit_log 已存在，跳过建表（归属：管理系统仓 121_ai_base_tables.sql）` 并 `EXIT=0`
- **不存在** ⇒ 输出明确提示「该表应由管理系统仓 `121_ai_base_tables.sql` 建立；AI 底座不建表」并 `EXIT=0`
  - ⚠️ **两种情况都 `EXIT=0`**，这是「存在性断言」的语义。**但不是假绿**：必须打印，运维能看见（对应 014 里那条「DDL 缺表⇒必须报错」的原则在DML/断言场景的对应做法 —— 你自己判断这里 EXIT=0 是否合适，若有异议先报告再改，不要擅自改成报错）
- **保留原有的列归属约定注释作为文档**（凌舟第3 条明确要求）—— 那份注释记录了哪些列由哪个迁移号增补，是有价值的信息
- ⚠️ 原脚本里的 `CREATE TABLE` 语句本体**不要留在可执行区**（避免被误当成"AI 底座建表"）
