# 第一部分 · 整体结论

## 一句话结论

**这个代码库的问题不是"某几个模块写错了"，而是从未建立基础设施建设层 ——
具体说：缺少「并发一致性」「错误处理分级」「数据访问隔离」三层底座。
过去八轮的修修补补都是在各自的业务模块里手工补个案，因此同类缺陷会在新模块里反复长出。**

## 决定性数据（这是根因的证据，不是推测）

| 基础设施 | 全库现状 | 含义 |
|---|---|---|
| `@VersionColumn`（乐观锁） | **0** | 不存在任何并发写保护机制 |
| 悲观锁 / `FOR UPDATE` | **0** | 同上 |
| 事务（`transaction`） | **1 处** | 且是修某个并发 bug 时才补的（`evolution-version.service.ts:161`） |
| `createQueryRunner` | **0** | 没有手写事务的习惯 |
| 幂等键 / `Idempotency-Key` | **0** | 写操作重试必然重放 |
| 多写场景数（估算） | **≥15 处** | 与上面 1 处事务形成鲜明反差 |

> 一个拥有 21 张表、40+ 个写工具、涉及资金扣减与业务单据创建的服务，
> **全库只有 1 处事务** —— 这不是"还有几个 bug 没修"，而是**缺一层 architecture**。

## 与前八轮的关系

前八轮修了大量「个案」，但没有一次触及根因。典型证据：

```
同一个 P1 缺陷在本库出现了两次，第二次仍未删除第一次的入口：
  mcp-token.service.ts:123  setEnabled(id)        ← 裸 id，无租户条件（旧）
```

# 第二部分 · 系统性根因

## 根因一：错误处理没有分级模型（导致"静默失败"散落各处）

全库约 130 个 `catch` 块（排除测试），统一采用一个反模式：

```typescript
} catch (err) {
  this.logger.warn(`xxx失败（非致命）：…`);
  // 然后返回降级值 / undefined / false / []
}
```

**问题在于这个模式不分场合使用。** 写操作和旁路增强是两种完全不同的语义：

| 类别 | 举例 | catch 后静默降级是否可接受 |
|---|---|---|
| **旁路增强失败** | 长期记忆检索、RAG 增强、规则注入 | ✅ **可接受**（降质不降功能） |
| **写路径失败** | 计费扣减、写工具执行、令牌注册 | ❌ **不可接受**（用户看到成功但实际没做） |

本库把二者混为一谈 —— 同一个 `logger.warn` 模式既用在「记忆检索失败」，
也用在「计费扣减失败」「写令牌注册失败」。**这是所有"虚假成功"类缺陷的统一根因。**

### 由根因一直接派生的缺陷（合并同类项）

这些看起来是 7 个独立 bug，实为**同一个错误模型**的 7 个实例：

| 位置 | 现象 |
|---|---|
| `task-runner.service.ts:876-881` | 写步骤令牌挂起失败 → 步骤标 `success`，**实际什么都没写** |
| `orchestrator.service.ts:958-981` | 确认令牌注册失败 → 前端拿到预览但**没有可点的确认令牌** |
| `billing.service.ts:83-87` | 计费扣减失败 → **漏计费**（且被上层 `orchestrator:1346` 的 `debug` 再吞一层） |
| `admin.controller.ts:437-445` | Redis 清记忆失败 → 仍返回 `success: true` |
| `employee-task-bridge.service.ts:121-125` | 任务结果回传失败 → 任务标「已完成」，**用户对话里什么都没有** |
| `chat.controller.ts:293-305` | 写操作已落地，计划步骤状态回写失败 → **单据已建，卡片永久停在"待确认"** |
| `proactive-push.service.ts:101-107` | WebSocket 广播失败 → MySQL 已记「推送成功」，用户永远收不到 |

## 根因二：数据一致性依赖"人工纪律"而非框架强制

### 2.1 三条并存的租户隔离通道

| 通道 | 位置 | 覆盖路由 | 问题 |
|---|---|---|---|
| ① 统一函数 | `tenant/admin-tenant-scope.ts:36/80` | `admin/*`、`review`、`rag` | ✅ 有纪律但不强制 |
| ② TenantContext | `tenant/tenant.middleware.ts:53/257` | `chat`、`agent`、`v2`、`employees` | ✅ 中间件注入 |
| ③ 控制器手写校验 | `admin.controller.ts:349/416/549`、`ai-config.controller.ts:60/76` | 同上被绕过的端点 | ❌ **与①语义相反** |

**③ 是硬性缺陷**：`admin.controller.ts:349/416/549` 先强校验 `ctx.tenantId` 存在才继续，
而平台身份的 `tenantId` 按设计就是 `undefined`
⇒ **平台身份调用这 3 个端点必得 400**，永远走不到"显式指定目标租户"分支，
与 `resolveAdminTenantId` 的平台口径直接冲突。

### 2.2 绕过 TypeORM 的 raw SQL 面

proactive 域 10 个巡检服务**全部**用 `dataSource.query` 直写 SQL 访问业务表
（`t_inventory_balance` / `t_sale_bill` / `t_member` / `t_miniapp_order` / `t_delivery_record` …），
租户条件靠**人工写进 SQL 字符串**。

好消息：9 个服务都写了内联 `tenant_id = ?`（如 `inventory-warning.service.ts:62/67`）。
坏消息：**`weekly-plan.service.ts:81-89` 一处都没写** —— 见 blocker #1。

⇒ **9 对 1 的比例说明：靠人工记得写 `"WHERE tenant_id = ?"`，迟早会漏一个。**

## 根因三：写路径缺少幂等与并发保护（财务级风险）

### 3.1 `service-client.ts` 的重试不看 HTTP 方法

```typescript
// src/bridge/service-client.ts:303-333
for (let attempt = 0; attempt <= this.maxRetries; attempt++) {
  try { return this.parseResponse(await this.httpClient.request({method, url:path, data: body, …})); }
  catch (err) {
    if (attempt < this.maxRetries && this.isRetryable(err)) { await this.sleep(500); continue; }
    throw this.toBridgeError(err, path);
  }
}
// :419-431  isRetryable 只看错误类型，完全不看 method
if (!err.response) return true;              // 网络错误/超时 → 重试
if (err.response.status >= 500) return true; // 5xx → 重试
```

`post`(:212) / `put`(:224) / `delete`(:248) **全部**委托到这个 `request()`。
⇒ **约 40 个写工具**（`create-sales-order`、`create-purchase-payment`、`inventory-transfer`、`create-refund` …）
在网络抖动时**必然**重复提交 —— 后端很可能已处理完，只是响应没回来。

### 3.2 计费扣减是典型 lost update

```typescript
// src/tenant/billing.service.ts:59-88
const billing = await this.getOrCreate(tenantId);   // 读
billing.balance = Math.max(0, Number(billing.balance) - cost);  // 改（在内存）
if (changed) await this.repo.save(billing);         // 写
} catch (err) { this.logger.warn(`计费消耗失败（非致命）…`); }   // 吞
```

N 个并发对话读到同一 `balance`，各自扣减后写回 ⇒ **前 N-1 次计费蒸发**，且无任何告警。

## 阶段 1：建立错误处理分级模型 ⭐**最高杠杆**
**目标**：从制度上消灭"虚假成功"，使后续所有新代码不再可能写出这类 bug

**这正是阻断 M-1~M-11 的统一地基。**

建立三种显式语义（建议放 `src/common/`）：

```typescript
// 语义一：旁路失败可降级（记忆/RAG/规则注入/VectorStore 装载）
degrade<T>(op, fallback, metric)      // 内部: logger.warn + metric.increment('degrade') + return fallback

// 语义二：写路径失败必须上抛（计费/写工具/令牌注册/证据台账）
mustSucceed<T>(op, ctx)               // 内部: logger.error + alert + throw

// 语义三：可最终一致的旁路（审计/用量/推送），入 Outbox 或重试队列
bestEffort(op, { retries: 3, deadLetter: true })
```

**迁移范围**（阶段 1 只迁「写路径」这一类，约 20 处，旁路类留到阶段 3）：
`task-runner:876`、`orchestrator:958/1346`、`billing:83`、`admin.controller:445`、
`employee-task-bridge:121`、`chat.controller:293`、`write-guard.controller:91`、
`write-guard:218/239`、`confirmation:426/447`、`proactive-push:101`

**验证**：
- 反测（必做）：把 `mustSucceed` 临时改回 `catch+warn`，对应用例必须立刻变红
- 新增：每个迁移点一个「依赖失败时行为正确」的用例

**先后约束**：**必须在阶段 2 之前完成** —— 阶段 2 要在这个模型之上写业务代码，否则会二次返工。
