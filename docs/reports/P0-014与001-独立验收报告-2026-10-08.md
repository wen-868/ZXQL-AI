## 二、P0-014：生产 1062 修复

### 2.1 生产故障

每次部署均失败于：

```
ERROR 1062 (23000) at line 87:
Duplicate entry 'default-2026-08-09-' for key 't_ai_usage_daily.uk_tenant_date_provider'
```

生产实况：唯一键**已存在**且为三列 `uk_tenant_date_provider (tenant_id, stat_date, provider)`，124 行 / 21 组，重复行**全部是 `provider IS NULL` 的行**。

### 2.2 根因（三原因叠加，逐条复现为真）

| | 根因 | 机理 |
|---|---|---|
| **A** | 归一化让原本不受约束的行突然受约束 | MySQL 唯一索引**允许多个 NULL** ⇒ 含可空列 `provider` 的键对 `provider IS NULL` 的行完全不生效。旧脚本把 NULL 改成 `''` 的瞬间，这些行第一次受约束且彼此重复 ⇒ 1062 |
| **B** | 去重口径比唯一键更宽 | 旧脚本按四元组去重，生产键是三列（更严格）⇒ 同三列不同 model 的两行不会被合并 ⇒ 建键撞已有三列键 |
| **C** | 守卫漏检已存在的键 | 旧脚本 `@uk_exists` 只查 `uk_usage_daily` 一个名字，不查生产已有的 `uk_tenant_date_provider` ⇒ 生产算出 0 ⇒ 守卫全部放行 |

**⚠️ 我对原因 B 的定性做了更正（详见 §2.5）**。

### 2.3 修复要点

- 合并分组键改为**归一化后三列** `(tenant_id, stat_date, COALESCE(NULLIF(provider,''),'unknown'))`，把 NULL / `''` / `unknown` 归为同一组，一步同时修好 A 与 B
- 8 个度量列全部 **SUM 合并**，保留行 `MIN(id)`，不使用 `INSERT IGNORE` / `REPLACE`，**不丢行**
- `model` 代表值取确定性规则 `COALESCE(MIN(NULLIF(NULLIF(model,''),'unknown')),'unknown')`
- 列定义收敛为 `NOT NULL DEFAULT 'unknown'`
- 哨兵值 `'unknown'`，**三处一致**：库默认值 / 迁移回填值 / 写入侧 `?? 'unknown'`
- `@uk_exists` 改为按**列集合语义**判定（任意 `NON_UNIQUE=0` 且列集合包含三列的索引），且不再用于门控归一化与合并
- 唯一键统一为三列 `uk_tenant_date_provider`

### 2.5 三条反测（本轮验收的核心价值）

| 变体 | 做法 | 结果 |
|---|---|---|
| **3（核心）** | 合并分组键从 `COALESCE(NULLIF(provider,''),'unknown')` 还原成 `provider` 原值 | **`ERROR 1062 at line 36`** ⇒ 归一化分组键有真实区分力 |
| **2c** | 让 UPDATE 真的改 provider，且组内 `unknown` 行**故意最后插入**（使 `MIN(id)` 落在 NULL 行） | **`ERROR 1062 't4-2026-08-13-unknown'`** ⇒ 因果链为真 |
| **2b（假绿）** | 同上，但 `MIN(id)` 恰好已是 `unknown` 行 ⇒ UPDATE 空操作 | **不撞 1062，反测假绿** ⇒ 我重造基线才测出真结果 |

**教训**：构造「保留行（`MIN(id)`）」类反测时，必须先确认保留行落在哪一行，否则测了等于没测。已写入执行报告 §8.1。

### 2.6 我抓到的三处证据强度问题（已更正并验收 `8955081`）

1. **「原因 B 是生产独立的第二条失败路径」不成立** —— 我在 `probe_b` 库实测：在**已有三列键**的表上插入第二行同 `(tenant_id, stat_date, provider)`、不同 `model` 的数据，直接 `ERROR 1062 Duplicate entry 't2-2026-08-11-openai'` ⇒ 生产上这种行根本不可能存在。原复现环境（无三列键）与生产不符。**结论保留（按三列合并仍必须做），定性收窄为：原因 B 仅在无三列键环境发生，生产 1062 只有原因 A 一条路径。**
2. **「换任何哨兵值都会在同一处炸」措辞含混** ⇒ 改为准确表述：原因 A 无法靠「只换哨兵值」绕过，必须**先按归一化值合并、再归一化**。
3. **脚本内两处注释自相矛盾** —— `:127-129` 称「UPDATE 改 provider 的瞬间撞 1062」vs `:267-268` 称「UPDATE 不碰 provider」。实测确认：当前实现下「DELETE 先于 UPDATE」**不是正确性必需前提**（真正必需的是归一化分组键），已改为「更保险的写法而非硬约束」，避免给后人设假陷阱。

**收尾提交核实**：`git diff | grep -vE "^[+-]\s*--"` 输出为空 ⇒ **SQL 语句本体零改动**；注释红线 `grep -nE "^\s*--[^ \t-]"` 无输出；收尾版重跑真库结果与收尾前一致。
