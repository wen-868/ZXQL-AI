### ② 跨库口径：**选 B（显式 `ai_db.<table>`）**

**理由（三条，按重要性）：**

1. **`USE` 是会话状态，B 不是。** 部署脚本「一个文件一条连接」目前没问题，但 `USE` 会把风险埋给未来：一旦有人改成分号拆分执行或复用连接，`USE ai_db;` 之后的所有语句会**静默落进 ai_db**。B 与会话当前库无关。
2. **B 可审计。** `rg -n "ai_db\." migrations/` 一次列出全部跨库引用点；A 下对象是裸名，必须人工回溯「上一条 USE 是谁」才能回答验收标准③ 的问题。
3. **B 能同时服务混合脚本。** `007` 一段业务库一段 ai_db，A 需要来回切库（`USE` 还不能吃变量，无法写成 `USE @main_db`），B 天然支持。

**为什么没有保留 007 上轮那个 `@ai_evo_db` 变量**（这点与上一张卡的处理不同，是有意改的）：

- 本仓 `@ai_db` 这个变量名的既有语义是 **`DATABASE()` = 业务库**（004/005/008/009/010/011 都这么用），再引入一个指向私有库的变量只会制造第二种歧义；
- 库名实际上由 `003:14` 的 `CREATE DATABASE IF NOT EXISTS ai_db` **钉死**（这条语句本身无法参数化），私有化改名必须改 003 —— 那么「只有 007 用变量、其余用字面量」就构成了新的不一致，而"不一致"正是本卡要根治的病；
- 全字面量让 `rg -n "ai_db\." migrations/` 成为唯一的权威审计入口，直接对应验收标准③。

上轮那个变量的**真正价值**（判定与执行同源、不出现「查 A 库改 B 库」）由约定继承了：**同一文件的 `information_schema` 判定与 DDL/DML 必须引用同一个限定名**。

改动点：
- `007:38 / 48` 判定 `WHERE TABLE_SCHEMA = 'ai_db'`
- `007:41 / 51` 执行 `'ALTER TABLE ai_db.ai_evolution_version ADD COLUMN ...'`
- `README.md:21-30` 新增 §二.6「跨库引用口径（2026-10-08 统一，强制）」

## 四、为什么「缺表」对 DDL 和 DML 要区别对待（不是无脑跳过）

- **DML 回填（013）缺表 ⇒ 跳过 + EXIT=0**：回填是**一次性数据修正**，不是结构必需项；表不存在只说明还没有数据可回填。
- **DDL（003/007）缺表 ⇒ 必须报错**：缺表意味着 003 没跑成功 = 结构不完整，静默跳过就是"假绿"。
