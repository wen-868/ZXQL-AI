# R101-AI-42 回传（P0 热修：`t_ai_notice` 索引超长导致生产迁移失败）

> 类型：**P0 生产阻塞热修**｜关联：R101-AI-40（通知中心）｜负责人：阿坚｜收口：凌舟｜日期：2026-10-16
> 现象：AI 底座 **Auto Deploy 连续 9 次红**（`ERROR 1071 Specified key was too long`）⇒ 新版本无法上线
> 归属：**AI 仓**

---

## 一、根因（1071）

`migrations/022_ai_notice.sql` 的

```sql
KEY idx_ai_notice_receiver (tenant_id, receiver)
```

`receiver` 为 `VARCHAR(1000)` ⇒ InnoDB 索引键长 `(36 + 1000) × 4 = 4144` 字节 **> 3072 上限** ⇒
`ERROR 1071 Specified key was too long; max key length is 3072 bytes`（InnoDB + utf8mb4）。

> 为什么此前没发现：整批验证都在 **sqlite**（无该上限）与**静态核查**（看不出字节数）上做；
> `.cjs` 静态脚本当时也只看列类型、未做**键长累计** ⇒ **只有真 MySQL 才暴露**。

---

## 二、修法：**删除该索引**（不是缩短，也不是加前缀）—— 硬判据

我核实了通知 List 的真实查询：
```sql
tenant_id = ? AND ( id IN (...) OR receiver LIKE '%,me,%' OR receiver LIKE '%,role:x,%' ... )
```
`receiver LIKE '%,me,%'` 是**前导通配**（`%...`）⇒ **B+Tree 索引用不上**。

| 方案 | 能否建起来 | 对前导通配 LIKE 有效 | 结论 |
|---|---|---|---|
| 缩短到 191 / 加前缀 `receiver(191)` | ✅ | ❌ 依然无效 | 只是把**无效索引合法化**，白搭写入开销 |
| **删除** | —（无需建） | —（本就无效） | ✅ **零查询损失 + 彻底消除 1071** |

`tenant_id` 等值过滤仍由 `luk_ai_notice_dedupe (tenant_id, dedupe_key)` 的 **tenant_id 最左前缀**服务。
注释已写清该理由（避免后人误以为漏建索引）。

## 三、三处同步改（+ 幂等清尾）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `migrations/022_ai_notice.sql` | CREATE TABLE 内**删除** `KEY idx_ai_notice_receiver` 行（并留注释说明理由）；**追加"四之三 幂等清尾"**：`information_schema.STATISTICS` 判定存在则 `DROP INDEX` |
| 2 | `migrations-sqlite/005_ai_notice.sql` | 删除该 `CREATE INDEX`；改为 `DROP INDEX IF EXISTS "t_ai_notice__idx_ai_notice_receiver"`（天然幂等清尾） |

但**不赌**其他环境（scratch / 某测试库）已建过带该索引的表 ⇒ 清尾保证"重跑即干净"。

## 五、过程如实（我的验证脚本自身的问题）

首跑 MySQL 验证**失败**：`ERROR 1146 Table 'ai022.t_ai_acl' doesn't exist`
⇒ 原因是我**只应用了 018**，而 `t_ai_acl` 是 **019 改名**的产物 ⇒ 022 的 `ALTER TABLE t_ai_acl MODIFY ENUM(...)` 找不到表。
**关键澄清**：该次失败发生在**第 50 行的 ENUM MODIFY**，而 `CREATE TABLE t_ai_notice` **在此之前已成功**
⇒ **1071 确已消除**；失败是**我的测试前置步骤缺失**，不是迁移问题。补上 019 后 6 步全绿。

> 教训：**验证脚本的前置依赖也要跟迁移序列对齐**（本例 `t_ai_acl` 的"建表"在 018、改名在 019）。
