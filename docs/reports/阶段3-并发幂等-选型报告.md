## Q1 · 真正的高并发风险写路径

### 筛选口径

不罗列 40 个写工具。36 个写工具的并发暴露面是**同一个**（B-2 已止血），不逐个列。判据：

- **A 级（可重放无自然键）**：同一逻辑请求可被重放且无业务唯一键 → 重复落库/重复外部写
- **B 级（read-改-write）**：先读后写，中间无锁/无条件更新 → 丢失更新、双活
- **C 级（check-then-act）**：getOrCreate 类 → 并发双插
- **D 级（定时器 × 用户请求撞同一行）**：两条独立入口写同一行

### Q1 结论

- **最高风险 Top 3**：**#1 `savePlan`丢失更新** > **#2 `updateBilling` × `deduct` 覆盖** > **#5/#6 `evolution-version` 的 `rollback`/评测回写**。
- 三者共性：**`repo.save(整行)` 或 `repo.update(无条件)` 写整份快照，且 WHERE 不含状态/版本条件**。这不是"缺少锁"的问题，是"用 ORM 的 save 写整行"的问题。
- **A 类（外部写重放）已被阶段 0 B-2 削掉大头，剩余缺口是令牌重放（#9#10），优先级低于 B/C/D。**
- 任务卡给的候选核实结果：
  - `billing.getOrCreate` → 属实，但因 `unique: true` 实际后果是**异常被吞**而非双写（#3）。
  - `orchestrator` 写工具分发链 → 未见 orchestrator 内直接落库；分发链的重复风险实际落在 WriteGuard 令牌重放（#9/#10），**不在 orchestrator**。
  - `task-runner.service.ts` 步骤落账 → 属实且**是最高风险项**（#1）。
  - 「定时任务与用户请求撞同一行」→ 属实（#2 #4 #5 #11）。

## Q2 · 三方案适用边界与选型建议

### 2.1 机制边界（结合本仓实际，不是教科书复述）

| 方案 | 本仓可行性 | 真实代价 |
|---|---|---|
| **乐观锁 `@VersionColumn`** | TypeORM 1.1.0 支持，但**必须加 DDL**且 `synchronize: false` ⇒ 只能靠迁移。冲突时抛 `OptimisticLockVersionMismatchError`（1.x 的错误类名/行为需实测确认，见待裁决 D-3）⇒ **每个冲突点的业务代码都要写重试循环**，而本仓冲突点有 6+ 处（#1#2#5#6#7#8） | DDL + 6 处重试循环。且 `savePlan` 的 `steps` 是 JSON 整列，乐观锁只能**整份 JSON 二进制比对**，代价可接受；但对 `t_tenant_ai_billing` 有 §0.2 的双写问题，乐观锁会让管理员频繁撞冲突 |
| **悲观锁 `FOR UPDATE`** | `createQueryRunner=0` ⇒ 事务基础设施为零。但 **`activate:161` 已证明 `repo.manager.transaction` 可用**，且它用的是 `EntityManager` 上直接 `createQueryBuilder`，**不需要 QueryRunner** ⇒ 落地成本比任务卡估的低。**致命限制：跨库不可事务**（§0.2）⇒凡涉及 `ai_db`（experience/correction/sample/evolution_version）的路径一律不能用 | 长事务：`savePlan` 的 `steps` 整份读改写若加 `FOR UPDATE`，会把 LLM 调用（`runAgentStep:687` 调模型，秒级）夹在事务里⇒ **绝对不能锁着等 LLM**。这排除了「整个 run() 加事务」的做法 |
| **纯幂等键（去重键 + 唯一索引）** | 需新建幂等表。**项目现成能力可复用**：`write-guard.service.ts:210SET NX` + `:233` Lua CAS 释放 + `:576multi()`，模式已验证 | **只解决"重复提交"，不解决"并发覆盖"**。⇒ 对 #1 #2 #5 #6 #7 这6 个「丢失更新」类**完全无效** —— 它们不是"提交了两次"，而是"提交了但覆盖了" |

**真正需要处理的，按场景分三档**：

| 场景 | 表 | 建议方案 | 理由（明确） |

| **check-then-act 双插**：#3 `getOrCreate`、#8 `upsertProfile` | `t_tenant_ai_billing`、`t_ai_ltm_profile` | **`INSERT ... ON DUPLICATE KEY UPDATE` / 唯一键冲突捕获（可吞）**，`getOrCreate` 已有 `unique: true` ⇒ 只要把 `ER_DUP_ENTRY` 捕获后重查即可，**不需要新基础设施**。#8 先解 D-1 | `getOrCreate` 的修法是 5 行 try-catch，不需要锁 |
| **重复提交（重放）**：#9 写工具令牌重放、#11 定时巡检重复推送 | 新表 `t_ai_idempotency_key` | **纯幂等键（唯一索引 + Redis 加速）** —— 这是幂等键唯一真正适用的场景 | 只有"同一逻辑操作被执行两次"才需要幂等键 |
| **跨实例防重入**：#11 `runForAllTenants` | Redis | **复用 `write-guard` 的 `SET NX` 锁**，把 `running` 从进程内 `Set` 换成 Redis 锁（key: `ai:proactive:lock:{taskName}`，PX 取巡检周期的量级） | 锁 TTL 需 ≥ 巡检耗时，否则退化为同#10 的问题 |

### 2.3 一句话选型建议

> **不要建统一的锁/事务基础设施**——本仓 6 个高风险点里 5 个的正解是「条件 UPDATE 取代 `save` 整行」（零 DDL，复制 `activate` 已验证的范式），只有「重复提交」类才需要幂等键，且幂等键应落 **MySQL 表**（唯一索引是唯一能同时保证"同键只落一次"和"跨实例/重启有效"的机制，Redis 只做前置加速）。

## Q3 · 幂等键设计（采纳，用于重复提交类）

### 3.1 键的构成

**两层，不合并**：

**第一层 —— 业务自然幂等键（无客户端参与，优先）**

构成：`sha256(tenantId ‖ toolName ‖ canonical(args))`

- 适用：`create-customer`、`create-sales-order` 等**参数完全决定结果**的写工具。用户连发两条相同指令 ⇒ 键相同 ⇒ 第二次直接返回第一次结果。
- 取 `canonical(args)`（键排序后序列化）而非原始 JSON，否则参数顺序差异会算出不同键。
- ⚠️ **边界**：含 `remark`/`operatorNote` 等自由文本参数的写工具（`confirmation.service.ts:411` 会注入 `remark`）必须**先把自由文本剔除**，否则用户换个语气重述就成了新键。
- **真实收益有限、必须说清**：它只能挡住"完全相同"的重放，挡不住"改了备注的同一单"。所以它是第一层，不是唯一层。

**第二层 —— 客户端 `Idempotency-Key`**

- 请求头（`Idempotency-Key`，标准头名），缺失时**降级到第一层**，不强制。
- 价值场景明确：**弱网下用户点两次"确认"**。`chat.controller.ts:285confirmAndExecute` 已有 WriteGuard 令牌挡双击（`write-guard.service.ts:403`），但令牌锁 TTL 仅 5s 且锁在写外（#10）⇒ 第二层在网关侧独立兜底，不依赖业务进程存活。
- 取值：前端生成 UUID v4，随确认请求下发；**必须与 `tenantId` 合成复合键**（防止跨租户碰撞）。

### 3.2 存储位置 —— 选 MySQL 表，Redis 只做前置

| 维度 | MySQL 表（采纳） | Redis（仅前置加速） |
|---|---|---|
| 同键只落一次的保证 | **唯一索引，数据库级裁决**，天然做到 | `SET NX` 能挡并发，但**主从异步复制下挡不住**：`SET` 成功后主库崩溃、复制未完成 ⇒ 键丢失，重放穿透 |
| 重启/故障切换 | 持久 | 若 Redis 无 AOF/RDB 或切换未持久 ⇒ 键全丢，重放穿透 |
| TTL 清理 | 需自建清理任务 | 原生 TTL |
| 多实例一致 | 天然 | 需确认部署是单 Redis 还是哨兵/集群 |

**为什么主选 MySQL**：本项目 Redis **默认无持久化保证**（§0.2 三处 `new Redis` 都只配了 `retryStrategy`，**无 `RDB`/`AOF` 相关配置，无哨兵/集群代码**）⇒ 把幂等正确性挂在它上面，Redis 一重启所有幂等保护归零。而幂等键存在的意义恰恰是"防重复"，正确性必须落在**持久且有唯一约束**的地方。

**Redis 的唯一用途**：在 `t_ai_idempotency_key` 前加一层 `SET NX` 闸门，让绝大多数重复请求**不打到 DB**。降级必须**直接跳到 MySQL**，不能"Redis 挂了就不校验"（那等于无保护）。**必须复用现有 `write-guard.service.ts:210` 的 `set(key, owner, 'PX', ttl, 'NX')` + `:233` 的 Lua CAS 释放范式**，不要引入新客户端。

### 3.3 并发下如何保证"同键只落一次"

采用 **MySQL 唯一索引 + 冲突捕获**，不用 Redis 分布式锁做正确性保证：

```
请求 → Redis SET NX（闸门，失败则短暂退避重试 Redis）
     → INSERT INTO t_ai_idempotency_key (idempotency_key, ...) VALUES (?, 'in_progress')
     → 唯一键冲突 ⇒ SELECT 查该键状态：
         completed  → 返回已存 result（重放直接命中，不执行业务）
         in_progress → 409 「处理中，请稍后」（另一个请求正在执行）
     → 未冲突 ⇒ 执行业务写 → UPDATE 该键 SET status='completed', result=?
```

关键点：

1. **唯一索引是唯一的正确性来源**（`UNIQUE KEY uk_idem_key (tenant_id, idempotency_key)`）。Redis 只做性能。
2. **`in_progress` 状态必须落库**，不能只放 Redis —— 否则进程崩溃后 Redis 键过期，键回到"不存在"状态，仍可重放。落库 + `expires_at` 才能做"处理中超过 N 分钟视为僵死，允许接管"。
3. **`result` 必须存**，否则第二次重放只能返回"已处理过"，用户拿不到结果，还得再点一次。
4. **业务写与"标记完成"不在一个事务里**（业务写是外部 HTTP，事务撤不回，见 Q4）⇒ 存在"业务写成功但键未标记 completed"的窗口。**该窗口内的重放会重复执行业务写**。这是本方案**无法消除的残留风险**，必须明说。缓解：键在业务写**之前**就已落库（`in_progress`），所以重放会被 409 挡住而非穿透；只有"业务写成功 + 标记完成失败"才重复，窗口大小 = 一次外部 HTTP 调用时间。

### 3.4 落地形态

新表 `t_ai_idempotency_key` + `IdempotencyService`（放`src/common/`，因为 `rate-limiter`/`metrics` 都在 common，Redis 客户端抽共享 provider 也在这层）。

## Q4 · 事务基础设施的落点

### 4.1 现有唯一事务

`src/evolution/evolution-version.service.ts:161` `this.repo.manager.transaction(...)`。注意：**它用的是 `Repository.manager` 上的 `transaction`，不是 `DataSource.transaction`，也不需要 `createQueryRunner`**（事务内的 `em.getRepository()` 由TypeORM 内部管理 QueryRunner）。**这推翻了任务卡"事务基础设施本身要先建"的判断** —— 基础设施已存在且已在生产跑了 4 天（`activate` 是活跃路径）。

### 4.2 统一封装在哪一层

**建议：`src/common/transaction.ts` 导出一个函数，而不是建 BaseService/Repository 基类。**

理由（本仓实证）：本仓没有 BaseService、没有 Repository 基类（实体直接 `@InjectRepository` 注入）。为 6 个用例建继承体系是过度设计。而统一封装只需解决两件事：

```ts
// 伪代码，仅示意落点
export async function inTransaction<T>(
  em: EntityManager,          // 或 DataSource
  fn: (em: EntityManager) => Promise<T>,
): Promise<T>
```

必须带的能力（针对本仓已踩的坑）：

1. **默认禁止在事务内做外部 HTTP 调用** —— 见 §4.4，这是硬约束。
2. **统一的重试/冲突映射** —— 把 `OptimisticLockVersionMismatchError`（以及 1.x 的等价错误类）映射为 `ConflictException(409)`，口径与 `evolution-version.service.ts:187` 既有做法一致。
3. **两个 DataSource 的边界断言** —— 传入的 `em` 属于哪个连接必须显式，**禁止跨库事务**（§0.2）。

### 4.3 现有 `manager.transaction` 用法是否该统一改写

**不改写。** 唯一一处用法（`activate:161`）本身是正确的：单库、单连接、事务内**无外部调用**（只有两条 UPDATE）。重写它带来的收益是零，风险是把已上线的并发修复改坏。

**要新增的是约束，不是重构**：在封装里加一条静态检查或 lint 规则 —— "事务回调内不得出现 `serviceClient.*` / `executor.executeToolCall` / `chatSync`"。因为 `activate` 是**对的**，它证明了 `repo.manager.transaction` 在本仓可用，不需要动。

### 4.4 事务内是否允许 `bestEffort` —— **不允许，必须拆到事务外**

**结论：事务内禁止 `bestEffort`（以及任何外部请求）。**

理由是任务卡提示的那条，但要说清具体机制：

1. **回滚无法撤销已发出的外部请求。** `bestEffort` 包裹的是异步任务（`error-semantics.ts`），若在事务内调用，它发起的工作（HTTP 写后端、推 WebSocket）**已经离开进程**，事务 `ROLLBACK` 只能撤销 DB 操作，撤销不了后端已建的单。⇒ **业务层回滚了，用户手里的单据却真实存在** —— 这是最坏的一致性状态（比不一致更糟：账实不符且无人知晓）。
2. **`bestEffort` 语义上也不该在事务内**。查 `bestEffort` 的实际用法：本仓全部 54 处 `bestEffort` 都是**"DB 写入失败的旁路兜底"**（`audit-logger.ts:441`、`billing.service.ts:90`、`capture.service.ts:103`），其文档语义是"失败必落 logger.error + 指标 + 死信，运维可据死信补"。在事务内调用会产生**语义二义**：这个失败是该rollback，还是交给死信补？两者不能同时成立。
3. **具体到 `activate`**：`activate:161` 事务内只有两条 `createQueryBuilder().update().execute()`，**没有 `bestEffort`** ⇒ 现有做法正确。

**正确模式（顺序不能反）**：

```
① 事务内：纯 DB 写（UPDATE/INSERT），条件更新裁决，失败即 rollback 抛出
② 事务提交后
③ 再 bestEffort：审计日志、指标、推送、WebSocket、HTTP 调用
```

`evolution-version.service.ts:193` 的 `this.logger.log` 在事务内（日志无害，但**外部 HTTP/审计写入要挪到提交后**）。审计写入要特别注意：`activate` 当前**根本没写审计**（只 `logger.log`），若将来补 `auditLogger.logAiCall`，**必须在事务外** —— `AuditLogger.logAiCall` 内部会写 `t_ai_audit_log` + `t_ai_usage_daily`（`audit-logger.ts:426` UPSERT），**后者是另一个库的表也无所谓（它自己有原子 UPSERT），但若放进事务会白拉长事务**。

**唯一例外**：事务内若确实要记录审计，**只能写同库的 `t_ai_audit_log`，且必须用同一 `em`**，且要接受"日志行也随业务一起 rollback"（对审计而言这其实是**优点**：业务没成则不该有"已激活"的成功审计）。
