## 二、P0 验收（2 项，全部属实、全部已修）

### P0-1 `POST /api/admin/tools/execute` 可用任意租户身份执行全部业务工具
- 原问题：`admin.controller.ts` 的 `context.tenantId` 直接取请求体，违反「tenantId 只认 JWT」铁律。租户 A 的合法管理员在 body 传租户 B 的 tenantId，即可读写 B 的订单/客户/库存。
- 修复：租户口径统一收敛到 `src/tenant/admin-tenant-scope.ts` 的 `resolveAdminTenantId`。
  - 商户身份：锁本租户，自报他人 → **403 明确拒绝**（原为静默改写，越权尝试不留痕、不可观测，且与其他两处口径不一致）。
  - 平台身份：跨租户运维**必须显式指定**目标租户，缺失 → 400，**绝不回退 `'default'`**。
  - 无身份（绕过守卫直调）→ 403。
- 端到端：商户 A 伪造 `t_bravo` → 403，且响应详情点名被拒租户便于溯源；商户 A 传自己租户 → 不误伤。
- 提交：`06a2507`（修复）、`dbd1e66`（口径统一为显式 403）。

### P0-2 商户管理员可改平台级及任意租户的 AI 配置与计费
- 原问题：`ai-config.controller.ts` 的 `/platform`、`/tenants/:tenantId`、`/billing/:tenantId` 仅挂 `AdminGuard`，无平台身份校验。把别家租户的 provider/apiKey 改成攻击者端点即等于劫持对方全部 AI 对话流。
- 修复：同上，收口到 `resolveAdminTenantId`。
- 端到端：商户访问平台配置 → 403；商户读别家租户配置 → 403；平台身份访问平台配置 → 200（不误伤）。
- 提交：`06a2507`。

> **附带修复**：`dbd1e66` 补齐了 `src/tenant/admin-tenant-scope.ts` 模块本体。此前提交 `6e532ae` 已让5 个控制器 import 该模块，但**模块文件从未提交**，导致远端 main 分支编译不过（TS2307）。上一轮门禁"全绿"是因为工作区存在该未跟踪文件造成**假绿**。教训已落地：本报告的所有门禁均在**纯净 HEAD 的独立 worktree** 上重跑。

## 三、P1 验收（6 项，5 项属实已修，1 项报告已过时）

### P1-3 admin 路由无 TenantMiddleware 致E4 对真实租户全部失效 — ✅ 已修
- 属实。`tenant.module.ts` 只覆盖 chat/agent/v2/employees 四条路由；`ai-db.controller.ts` 的 e4/train、readiness、dataset、e5 auto-close 原先全部 `getData()?.tenantId ?? 'default'`，生产上永远取到 `default`。
- 补充：上下文缺失问题在历史提交 `6e532ae` 已由 `AdminContextMiddleware` 根治（`/admin/*` 接入 `TenantContext`，与业务路由唯一差异是平台身份允许无目标租户进入）。本轮在其上再加**显式校验层**，杜绝任何 `'default'` 兜底。
- 涉及端点全部改走 `resolveAdminTenantId` / `resolveOptionalAdminTenantId`：E4 三端点、E5 auto-close、三个列表端点、createCorrection。
- 端到端：商户调 e4/readiness → 200（真实租户可用）；平台未指定租户 → 400。

### P1-4 E3 few-shot 回流无租户过滤+ 缓存全局共享 — ❌ 报告已过时
- 提交 `2b345b3`（本轮审查之前）已修：样本查询强制带 `tenantId`、缓存 key 按租户分片（同实例切租户不串缓存），无上下文调用归 `default` 分片。含 3 条经反测验证的回归用例。
- **A 租户话术不会再注入 B 租户提示词。此项无需再动。**

### P1-5 数字员工任务表无 `tenant_id` 列 — ✅ 已修（实为比报告更严重）
- 属实，且报告低估了后果：`getTaskById` 只按自增 id 查，`completeTask`/`markTaskRated` 按 id 裸改，**可枚举并篡改别家租户任务**（泄漏 + 投毒双重）。
- 修复：
  - 迁移 `migrations/011_employee_task_tenant.sql`：加 `tenant_id VARCHAR(32) NULL` + `idx_emp_task_tenant` 索引，并按 `employee_id` 关联 `t_ai_employee` 回填历史行（幂等，`information_schema` 判定 + `PREPARE` 动态 SQL）。
  - 实体 `AiEmployeeTaskEntity` 加 `tenantId` 字段与索引装饰器。
  - `employee.service.ts` 四处强制带租户：`getTaskById(taskId, tenantId)`、`completeTask(..., tenantId)`、`markTaskRated(..., tenantId)`、`recordTask` 写入 tenantId。
- **迁移真实库验证**：本地执行成功，8 行历史任务全部回填租户、0 遗留 NULL，连续重跑 2 次无错（幂等）。

### P1-6 E5 评测：空 completion 用例自动判"通过" — ✅ 已修
- 属实。`JSON.stringify(data).includes('')` —— 空串是任何字符串的子串，**恒真**，准确率虚高；配合自治策略可自动激活一个实际未验证的版本。
- 修复：显式分支 `trimmed === ''` → `ok = false`，note 为「标准答案为空，用例无效（不计通过）」。

### P1-7 E5 基线为 0 时门槛恒真 — ✅ 已修
- 属实。`Number(0) != null` 成立，`newAccuracy >= 0.95 * 0` 即 `>= 0`，**0% 准确率也算达标**。
- 修复：引入 `hasUsableBaseline = baselineAccuracy != null && Number.isFinite(baselineAccuracy) && baselineAccuracy > 0`，基线为 0 时门控不成立。

### P1-8 自动分派与任务回传丢 `customerId` 分区 — ✅ 已修
- 属实。`buildMemoryKey` 管理端为 `ai:memory:{tenantId}:{sessionId}`，运营客户端为 `ai:memory:{tenantId}:{customerId}:{sessionId}`。回传漏传 `customerId` 会写到另一个 key，用户在自己会话里永远看不到回传结果，**任务事实上失联**。
- 修复：`employee-task-bridge.service.ts` 回传改传 `input.customerId`；`EmployeeTaskRunInput` 与 `dispatchTask` 输入加 `customerId?: string`；`orchestrator.service.ts` 自动分派（含分派通知 `saveHistory`）与 `dispatch-employee-task.tool.ts` 同步透传。
- 新增 `employee-task-bridge.service.spec.ts`（6 例）专测"回传落在哪个记忆分区"——该文件此前**不存在**，跨层拼接处无测试正是踩坑[44]记录的 P0 藏身处。
