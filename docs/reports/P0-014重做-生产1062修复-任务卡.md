## 二、🔴 根因（我已从代码核实，比「没做存量去重」更精确 —— 请照下面这个改，别照那句理解）

追单卡 §三写「014 没先做存量去重」。**这个描述不准确**：014 **有**去重逻辑（`014_usage_daily_unique_key.sql:100` 与 `:109`，`GROUP BY tenant_id, stat_date, provider, model`）。真正的原因是**两个叠加**：

### 原因 A：归一化让「原本不受约束的行」突然受约束 ⇒ 撞键（对应报错行 87）

MySQL 唯一索引**允许多个 NULL** ⇒ `uk_tenant_date_provider` 因为含可空列 `provider`，**对 provider IS NULL 的行完全不生效**。生产那 124 行的重复**全部是 NULL 行**（`default/2026-08-10/NULL` = 47 行就是典型）。

`014:87`：
```sql
UPDATE t_ai_usage_daily SET provider = '' WHERE provider IS NULL AND @uk_exists = 0;
```
把 NULL 改成 `''` 的**瞬间**，这些行第一次真正受 `uk_tenant_date_provider` 约束 ⇒ 而它们彼此重复 ⇒ **1062，报错行号正好是 87**。

### 原因 B：去重口径是四元组，而生产键是三列（更严格）

- 014 去重：`GROUP BY tenant_id, stat_date, provider, model`（**四**列）
- 生产已有键：`UNIQUE (tenant_id, stat_date, provider)`（**三**列，**不含 model**）

三列比四元组**更严格** ⇒ 即使不归一化，凡同一 `(tenant, date, provider)` 下存在**不同 model** 的两行，014 的四元组去重**不会合并它们**，而建 `uk_usage_daily` 时会撞上已有的三列键。

### 原因 C：守卫漏检已存在的键

`014:42-64` 的 `@uk_exists` 只检查 `uk_usage_daily`（014 自己要建的那个键），**不检查生产已有的 `uk_tenant_date_provider`** ⇒ 在生产上它算出的 `@uk_exists = 0` ⇒ 守卫全部放行 ⇒ 直接撞键。

⇒ **只修 A 不够**（换个哨兵值还会撞 B），**只修 B 也不够**（三列键下 NULL 行仍需合并）。
