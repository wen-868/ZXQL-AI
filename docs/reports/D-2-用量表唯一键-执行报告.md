## 3. R2 迁移 `migrations/014_usage_daily_unique_key.sql`

### 3.1 结构（7 步）

1. 检测唯一键：`uk_usage_daily` 存在 **或** 任意非主键唯一索引恰好覆盖四列 → 打印「已存在，跳过」
2. 查重（只读）：`dup_groups` / `rows_before` / `groups_before`
3. 重复组聚合进临时表 `tmp_usage_daily_dups`（只收 `COUNT(*)>1` 的组）
4. **SUM 合并**回保留行（`keep_id = 组内 MIN(id)`，`created_at` 改为组内 `MIN(created_at)`）
5. 删除多余行（用 NULL 安全比较 `<=>`）
6. `ALTER TABLE ... ADD UNIQUE KEY uk_usage_daily (tenant_id, stat_date, provider, model)`（条件执行）
7. 核验输出：`dup_groups_after` / `rows_after` / `groups_after` / 最终索引列表

### 3.2 相对任务卡的一处**有意偏离**（已评估，非扩权）

任务卡第 3 步只列了 5 个度量列（chat_count / tool_call_count / prompt_tokens / completion_tokens / total_tokens）。
实际表有 **8 个**度量列，另有 `prompt_cost` / `completion_cost` / `total_cost`（见 1.7 DDL）。
若只合并 5 列就删行，**被删行携带的 cost 会永久丢失**，直接违反卡上「去重步骤必须保留全部用量数值」的硬约束。
⇒ **014 按 8 列全量 SUM 合并**。理由已写进脚本顶部注释。

### 3.3 幂等与红线自检

```
$ grep -nE "^\s*--[^ \t-]" migrations/014_usage_daily_unique_key.sql
grep-exit:1        # 无输出 —— 注释红线通过

$ grep -niE "if exists" migrations/014_usage_daily_unique_key.sql
88:DROP TEMPORARY TABLE IF EXISTS tmp_usage_daily_dups;
138:DROP TEMPORARY TABLE IF EXISTS tmp_usage_daily_dups;
```

- 全文**不含** `ADD INDEX IF NOT EXISTS` / `ADD UNIQUE KEY IF NOT EXISTS`（MariaDB 专有，MySQL 8.0 报 1064），
  仅在注释里提及。加索引用 `information_schema` 判定 + `PREPARE`（沿用 012 风格）。
- 出现的 `DROP TEMPORARY TABLE IF EXISTS` 属于 `CREATE TABLE IF NOT EXISTS` 语族，MySQL 8.0 支持，不是红线那条。
- 去重步骤天然幂等：临时表只收重复组，无重复时 UPDATE/DELETE 命中 0 行。
- ⚠️ 依赖会话变量（`PREPARE`）⇒ **必须整文件执行**，不可按分号拆分。
- 脚本顶部已写明执行前备份 `t_ai_usage_daily`。

## 5. 未在目标版本上验证的部分（必须显式标注）

⚠️ **全部四步验证跑在 MariaDB 11.4.5 上，没有跑在 MySQL 8.0 上。**

本机情况：无 MySQL 8.0 安装（`%TEMP%/mysql80` 不存在、PATH 无 mysql、`Program Files` 无 MySQL 目录、
无 docker / chocolatey，只有 `winget`），3307 端口无服务。

MariaDB 支持 `ADD INDEX IF NOT EXISTS` 而 MySQL 8.0 不支持 ⇒ **在 MariaDB 上跑通不证明 MySQL 8.0 可跑**。

为把风险压到最低，014 只用 MySQL 8.0 与 MariaDB 的**交集语法**：

| 用法 | MySQL 8.0 | MariaDB | 014 是否用到 |
|---|---|---|---|
| `information_schema.STATISTICS` 判定 | ✅ | ✅ | ✅ |
| `PREPARE / EXECUTE / DEALLOCATE`（含 ALTER TABLE） | ✅ | ✅ | ✅ |
| `ADD UNIQUE KEY`（无 `IF NOT EXISTS`） | ✅ | ✅ | ✅ |
| `ADD INDEX IF NOT EXISTS` | ❌ 1064 | ✅ | **未用** |
| `CREATE/DROP TEMPORARY TABLE IF NOT EXISTS` | ✅ | ✅ | ✅ |
| `UPDATE ... JOIN` / `DELETE t FROM t JOIN ...` | ✅ | ✅ | ✅ |
| `<=>` NULL 安全比较 | ✅ | ✅ | ✅ |

## 8. 残留风险

### 8.1 （第一轮）`provider` / `model` 为 NULL 时唯一键不去重 —— **第二轮已闭环，见第 10 节**

> 本条是第一轮的记录，保留以说明问题来源。**该问题已在第 10 节闭环**，此处不再残留。

⇒ 每一次工具执行都会产生一条 NULL 行的用量记录，这是本机 99 行 NULL 的主要来源。

## 10. 第二轮：NULL 不去重闭环

### 10.1 为什么要闭环

第一轮我把「provider/model 为 NULL 时唯一键不去重」登记为残留风险。团队负责人判定这是
**半截修复**，必须闭环 —— 我同意，理由是：

- 本机库 196 行里 **99 行 provider 与 model 均为 NULL**（约一半）⇒ 唯一键建完后
  **对约一半的行无效**；
- 更关键的是它会**持续恶化**：`logToolExecution`（`audit-logger.ts:294-295`）硬编码传
  `provider: null, model: null`，每次工具执行都新增一条 NULL 用量行。

⇒ 库侧约束单独修不好这个问题，必须**库侧 + 写入侧**配合。团队负责人据此**正式放宽**
了「不改 audit-logger」的边界（原边界基于「缺的只是库侧约束」的判断，该判断不完整）。

### 10.2 改动 1：014 增加 NULL 归一化（去重之前）

新增第 2 步，插在「检测唯一键」之后、「查重/去重合并」之前：

```sql
UPDATE t_ai_usage_daily SET provider = '' WHERE provider IS NULL AND @uk_exists = 0;
UPDATE t_ai_usage_daily SET model    = '' WHERE model    IS NULL AND @uk_exists = 0;

SELECT SUM(provider IS NULL) AS provider_null_left,
       SUM(model IS NULL) AS model_null_left,
       COUNT(*) AS rows_after_normalize
  FROM t_ai_usage_daily;
```

**顺序不可颠倒**：先归一化 → 再去重合并 → 最后建唯一键。若反过来先按 NULL 合并再改空串，
可能撞上已存在的空串行而冒出新的重复组。

两处相对指示的**加固**，均已写进脚本注释：

1. **`AND @uk_exists = 0` 守卫**：若目标库**已存在**该唯一键，且 NULL 行与空串行同时存在，
   这条 UPDATE 会在语句内触发 1062 重复键错误。加上守卫后，这种情况下跳过归一化
   （重复组仍按第 6 步的 `<=>` 合并，不丢数据），需要人工确认后再处理。
2. **保留 `<=>` 未简化成 `=`**：指示里说可以简化。我保留了，因为迁移执行期间若有并发写入
   插入 NULL 行，`=` 会漏掉它们（残留下重复行）而 `<=>` 能一并收进组里；
   两者在无 NULL 时行为完全一致。这是**可选加固**，若你认为应简化可以直接改。

### 10.3 改动 2/3/4：写入侧与注释

- `audit-logger.ts:476-477`：入参改为 `params.provider ?? ''` / `params.model ?? ''`
  （两处调用点 `logAiCall:226`、`logToolExecution:292` 都被这一处覆盖）。
- `audit-logger.ts:417-436`：原注释「按唯一键：存在则累加，不存在则插入」在键缺失期间不成立，
  会误导维护者。改为如实描述：键由 014 建立，**建立之前每次调用都 INSERT 新行**；
  并写明为什么传空串而不是 NULL。
- `ai-usage-daily.entity.ts`：注释同步为空串约定。**`nullable: true` 保持不变** ——
  改列定义会触发大表 ALTER，不在本轮范围；空串约定由写入侧保证。

### 10.4 额外：加了一条回归守卫用例（本轮主动加，可驳回）

`src/bridge/audit-logger.spec.ts` 新增 1 条：
`upsertDailyUsage：provider/model 为 null 时落空串而非 NULL（唯一键可去重）`，
断言 `usageParams[0][7] === ''` 且 `[8] === ''`。
理由：空串约定是**约定而非类型约束**（列仍 nullable），没有任何类型系统会拦住有人改回传 `null`，
而一旦改回就是静默故障。这是本轮唯一一处超出指示清单的改动，若你认为不该加可以驳回，我撤掉。
