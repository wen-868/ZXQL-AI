## 迁移与改造量（交付物 4）

### 现状（凌舟已核实，我复核一致）
- 迁移是**手写 SQL 单套**：`migrations/NNN_*.sql`（17 个，无子目录），用 `mysql <db> < file` 投放；含 MySQL 专有写法（`ENGINE=InnoDB`、`COMMENT`、`AUTO_INCREMENT`、`information_schema + PREPARE` 幂等范式）。
- 双连接：业务库 `database.module.ts` `type:'mysql'` + `ai_db`（4 表）。

### 组织方案（推荐 **乙案**）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 甲：平行目录手工移植 | 新增 `migrations-sqlite/`，逐条移植 17 个文件（`IF NOT EXISTS` + `PRAGMA table_info` 替代 `information_schema`/`PREPARE`） | 与 MySQL 侧同构，审计轨迹一致 | **8~20 h**（每个 0.5~1.5 h）+ 双套同步维护成本 |
| **乙：桌面端单基线 + `synchronize` 受控** | 桌面端首次启动用 **一条基线建表脚本**（由实体 `synchronize` 生成一次并固化为 `migrations-sqlite/000_baseline.sql`）；版本升级时人工生成增量 | 半天内可落地；不需维护 17 份方言副本 | 失去"逐迁移可追溯"；增量需人工生成（可用脚本从实体 diff 生成） |
| 丙：只支持全新库 + 不迁移 | 桌面端永远 `synchronize: true` | 最省 | 升级无审计、无法回滚，**不建议** |

### 改造量估算（better-sqlite3 路线，**MySQL/生产零改动**的并行模式）

| 项 | 内容 | 估算 |
|---|---|---|
| 实体类型适配 | F1 `char`→`varchar`、F2 `mediumtext`→`text`、F3 `bigint` 主键→`integer`：约 30 个实体文件（可脚本化扫改 + 人工复核） | 0.5 ~ 1 人日 |
| SQL 方言分支 | F5 的 4 处 `ON DUPLICATE KEY` → `ON CONFLICT`（建议同时改用 `DO NOTHING`+`changes` 判重，见 E3） | 0.5 人日 |
| 判重与数值 | F4 `isDuplicateKeyError()` 扩方言；F6 金额读回类型核查 | 0.5 人日 |
| 迁移双套 | 乙案基线 + 升级脚本 | 0.5 人日（甲案另加 1~2.5 人日） |
| 运行时双模式 | `DB_DRIVER=mysql|sqlite` 配置分流（两条 DataSource 工厂）+ 桌面端与云端各自的 e2e | 1 人日 |
| 打包/CI | Electron 原生模块 rebuild + asar unpack；CI 增 SQLite 矩阵 | 0.5 ~ 1 人日 |
| **合计** | | **≈ 3.5 ~ 5 人日**（不含 LibSQL 自研 driver 的额外成本） |

### 若坚持 LibSQL（不推荐）
额外成本：自研 `options.driver` 适配层（better-sqlite3 API 子集）+ 持续跟随 TypeORM/驱动 API 变化 + Windows 绑定与 Electron rebuild **双份**风险
⇒ 结论：**用 better-sqlite3 达到同样的"单文件、零进程、双击即用"目标，成本最低、风险最小**；而 LibSQL 的增值（嵌入式副本/远程同步）在本项目桌面场景**并非当前需求**。
