```
=== 修复前（构造：sessionId 吸收分隔符）===
```

**兼容性核实**（存量 key 是否要迁移）：
```

含特殊字符的 key 旧 != 新          ⇒ 读不到，但TTL 仅 1 小时，窗口可忽略
```

### ② confirm/cancel 令牌级 Redis NX 互斥锁 ⚠️ **实现有缺陷**

**改法正确**：抽出 `doConfirm` / `doCancel` 私有方法，`confirm` / `cancel` 外层加锁 + `finally` 释放。降级口径合理（锁不可用不阻断主流程，与记忆降级同口径）。

**缺陷：`releaseTokenLock` 无 owner 校验，超时后会误解他人锁**

当前实现：
```typescript
private async releaseTokenLock(token: string): Promise<void> {
  await this.redis.del(`ai:wg:lock:${token}`);   // ← 无条件 del
}
```

时间线推演（单次 confirm 耗时 > 5s 时）：
```
0ms     A: set NX PX 5000 → OK（获锁）
100ms   A: doConfirm 执行中…
5000ms  锁自动过期，key 消失        ← PX 5000 到期
5100ms  B: set NX PX 5000 → OK（获锁）← A 还在跑，B 也进来了
5300ms  A: finally → del(lock)       ← ★ 把 B 持有的锁删了
5400ms  C: set NX PX 5000 → OK      ← B 还在跑，C 也进来了
```
⇒ **A 不知道自己的锁已过期并被B 替换，误删了 B 的锁**，互斥在慢请求下退化为无锁，回到修复前的双击穿透状态。

**严重度：中**。不是新引入的越权（正常速度下锁有效），只在 >5s 的慢请求窗口退化；租户绑定没问题（锁 key 含 token，token 本身已租户绑定，无跨租户互斥隐患）。

**建议改法**（任选）：
```typescript
// 方案A：随机 owner + Lua CAS 删除（推荐）
const owner = randomUUID();
await this.redis.set(key, owner, 'PX', 5000, 'NX');
// 释放时
await this.redis.eval(
  `if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`,
  1, key, owner,
);
```
方案 B：延长 PX 至覆盖最坏执行时长（但无法保证上限）。方案 C：接受退化但**显式注释说明**，别让人误以为锁是强互斥。

1. **⑫ graph 超时 env 防护未落地**，自述与代码不符。危害为全站故障级（`TOOL_TIMEOUT_MS="60s"` 或空串 ⇒ 所有工具瞬间超时），且修复模式就在同仓 `employee.service.ts:249-254`，照抄即可。**这是硬性阻塞项。**
2. **⑦ NX 锁 release 无 owner 校验**，慢请求下互斥退化（中等危害）。建议同期修正，一行 Lua 脚本可解。
3. **新增测试覆盖严重不足**（14 项仅 1 项有适配），掩码默认值经反测证明零信号。合规类修复无测试保护是系统性风险。
