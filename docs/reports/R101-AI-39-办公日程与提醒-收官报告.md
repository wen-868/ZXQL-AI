## 二、本批三条设计要点

### ① 幂等键：从源头避开 NULL 坑（优于前两批）
唯一键取**全 NOT NULL 四列**；可空的 `end_at`/`remind_at` **不进键** ⇒ DB 层真实有效（对比：AI-37 `due_at`、AI-38 `related_biz` 均因 NULL 不判重而只能靠业务层承重）。

### ② participants 的双形态一致性（凌舟点名坑）
```
存储归一化：  "u1,u12"  ⇒  ",u1,u12,"     （首尾逗号边界）
库层匹配：    LIKE '%,user:u1,%'           （双方言一致）
⇒ 杜绝 %u1% 误命中 u12（子串误配）
```
spec 有**正反双向**断言；大小写差异（MySQL ci / sqlite cs）因 principal 全小写而在取值域内无歧义（注释留痕）。

### ③ 状态机"能否回放"的语义分层（规范 §2.1 应用）
| 场景 | 终态关系 | 处理 |
|---|---|---|
| `aiTodoComplete` / `aiScheduleComplete` | 单一无歧义终态 | **可回放** |
| `aiApprovalApprove/Reject` | **互斥终态**（且可能由不同人并发产生） | **不回放**（明确失败 + 告知当前状态）|
| `aiScheduleCancel` 遇 `done` | 跨终态 | **明确失败** |

## 七、可复用结论（供批次 5 通知中心）

1. **通知/提醒类**：复用 proactive 域（`@Cron` + `push`），**不新建通道**；但要注意"推送 ≠ 持久化"——**错过即丢**（通知中心要补的正是这一层）
2. **模块归属**：先查目标模块 spec 是否有精确结构断言 + 是否存在环；必要时**独立模块**是最干净的解法
3. **幂等键**：优先选**全 NOT NULL** 列进键；可空列进键 = DB 层失效
4. **参与者/接收人匹配**：**首尾逗号归一化 + `LIKE '%,x,%'`**（双方言一致，杜绝子串误配）
5. **状态机**：同终态可回放、互斥/跨终态明确失败（规范 §2.1）
6. **mutation 纪律**：正则变异、不改语法、确认 total 非 0、形状断言断言到关键内容
