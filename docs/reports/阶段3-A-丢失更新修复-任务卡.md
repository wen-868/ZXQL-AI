## 一、为什么做这三处

第九轮审查的系统性根因之一：**写路径无幂等无并发保护**。实测全仓 `@VersionColumn`=0、`FOR UPDATE`=0、`createQueryRunner`=0、事务仅 1 处。

本次修复的三处是 Top3 风险中**零 DDL、可立即落地**的三处，且范式中已有同文件内已上线的成功案例可复制。

## 二、⚠️ 关键：三处修法分两类，不要套同一个范式

这是我在派发前复核代码时确认的，**套错范式会白做**：

### A 类：`ai-config-admin.service.ts:355 updateBilling` —— 修法是 **partial UPDATE（只写传入的列）**

- 现状（`:371` findOne → 内存改 → `:398` `this.billingRepo.save(billing)` **整行回写**）
- 冲突方：`src/tenant/billing.service.ts` 的 `deduct` 用 **raw SQL 原子 UPDATE** 改 `free_chat_count`（`:137`）与 `balance`（`:157`），`WHERE` 只按 `tenant_id`
- 丢失更新的机理：`updateBilling` 读到的内存快照带着旧的 `balance`，`save()` 把**整行**写回 ⇒ 覆盖掉并发 `deduct` 已扣减的值 ⇒ **漏计费（用户白嫖）**
- ⚠️ 这里的性质**不是状态机**，是「写了不该写的列」⇒ **不能**套 `WHERE status=...` 的条件范式
- 正确修法：**只 UPDATE 本次 `input` 里真正传入的列**（`planType` / `freeChatCount` / `freeTokenLimit` / `overagePrice` / `monthlyChatLimit` / `monthlyTokenLimit` / `monthlyPrice` / `enabled`），一个都没传就不写；`balance` 等未被本次修改的列**一个都不要出现在 SET 里**
- 记录不存在时仍需 create（保留现有 `:372-374` 的 create 分支语义）

### B 类：`task-runner.service.ts:149 savePlan` 与 `evolution-version.service.ts:205 rollback` —— 修法是 **条件 UPDATE（WHERE 带原状态 + `affected===0` 抛 409）**

- **`savePlan`**（`:157-164`）：`this.planRepo.update({ id, tenantId }, {...})`，`WHERE` **只有 id + tenantId，无 `state`/`version`** ⇒ 与 `approveStep` / `rejectStep` / `cancelPlan` 等改 `state` 的路径互斥时发生丢失更新，表现为步骤永久卡在 `suspended`
  - ⚠️ `savePlan` 在 `task-runner.service.ts` 内有 **10+ 个调用点**（`:190/224/252/288/339/347/388/403/455` 等）⇒ **尽量不改对外签名**；若确需新增「期望的前置状态」参数，必须在报告里说明改动范围与理由
- **`rollback`**（`:205-217`）：`getOrThrow` + `assertStatus(['active'])` 之后 `this.repo.save(entity)` **裸整行回写**
  - ⚠️ **同文件 `activate`（`:161-194`）已经用了正确范式**：`manager.transaction` + `createQueryBuilder().update().set().where('id = :id AND status = :status')` + `affected === 0` 抛 `ConflictException`（409）
  - ⇒ `rollback` 是**同文件内的不对称漏项**，直接复制 `activate:176-190` 的范式即可（前置状态 `active`，目标状态 `rolled_back`）

**范式参考**：`src/evolution/evolution-version.service.ts:176-190`（含 `:182-190` 的注释说明为什么抛 409 而不是 500）
