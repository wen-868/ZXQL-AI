## 二、对任务卡的两处事实更正（开工前逐行核实）

任务卡 A1 节的论证基础有两处不准确，均已在本卡纠正。**这不是措辞问题，是会导出错误实现的问题。**

### 更正 1：「三处结构完全同构」—— 不同构

第 3 处比另两处多一个兜底分支：

| 位置（b52a39c） | scopedTenantId |
|---|---|
| `:369` sessionArchive | `isPlatform() ? tenantId : ctx.tenantId` |
| `:432` clearMemory | `isPlatform() ? tenantId : ctx.tenantId` |
| `:572` queryAuditLogs | `isPlatform() ? tenantId \|\| ctx.tenantId : ctx.tenantId` |

取证：`sed -n '369,371p;432,434p;572,574p'`

**影响**：若按"三处同构"统一，第 3 处会被错误地改成 optional 或保留兜底，直接决定审计查询是收紧还是维持宽松。

### 更正 2：「平台未指定 tenantId ⇒ 查全部」在真实平台 JWT 下不成立，当前是 400

三处开头都有前置门 `if (!ctx?.tenantId) throw BadRequestException(400)`。
而 `AdminContextMiddleware.resolvePlatformContext`（`tenant.middleware.ts:257-269`）里
`tenantId: payload.tenantId`，而 `PlatformJwtPayload.tenantId` 是**可选**的
（`jwt-verify.ts:45-46`，注释明写「平台 token 通常无 tenantId」）。

⇒ **典型平台 JWT 根本走不到 `scopedTenantId` 那一行，现在就是 400。**
任务卡表格里「平台+不传 ⇒ scopedTenantId=undefined ⇒ 查全租户」只在
「平台 JWT 恰好带了 tenantId」的预留兼容形态下才成立。

**推论（重要）**：统一函数读 `req.adminIdentity`，其平台分支**不要求 tenantId**
⇒ 统一函数永远不会给平台 400。
所以**任何**收敛都必然改变「平台 JWT 无 tenantId」这条路径的响应码。
这是任务本身的固有结果，不是实现选择。

## 三、三处语义归属判断与依据

判断依据是**下游代码结构**，不是语义推测。

### 3.1 `:349` 会话归档查询 → `resolveOptionalAdminTenantId`

**归属**：平台可跨租户运维、未指定 = 查全部。

依据：
- 下游 QueryBuilder 是 `if (scopedTenantId) { qb.andWhere('a.tenant_id = ...') }`（`:361`），
  **结构上支持**「无租户条件 = 查全部」。
- 端点自身注释 `:360` 即写明「平台身份未指定租户时保持跨租户查询（运维场景）」。
- 读操作，无破坏性。

⇒ 用 optional，保留跨租户运维视图。

### 3.2 `:416` 清除记忆 → `resolveAdminTenantId`

**归属**：必锁某租户。

依据：
- 破坏性写操作，且对象是用户资产（记忆），比读审计更严重。
- `tenantId` 是**必填路径参数** `@Param('tenantId')`（`:410`）：NestJS 在进入方法体**之前**
  即拒绝缺失的路径参数 ⇒ 平台永远显式指定目标租户，**不存在"平台未指定"的场景**。
- `MemoryManager.clearHistory(tenantId: string, ...)` 要求 `string`；若用 optional 传下
  `undefined`，会拿 `undefined` 拼 Redis key（`buildKey`），删不存在的 key 且静默无效。
  破坏性操作不允许静默降级。

### 3.3 `:549` 审计日志查询 → `resolveAdminTenantId`（**不是** optional）

**归属**：必锁某租户。这是本卡最容易被选错的一处。

依据：
- `AuditLogger.queryAuditLogs(tenantId: string, ...)` 内部
  `.where('log.tenant_id = :tenantId')`（`audit-logger.ts:391`）**恒定过滤，无条件**。
  ⇒ **结构上无法查全部租户**。
- 若误用 optional：平台未指定 → 传 `undefined` ⇒ `tenant_id = NULL` ⇒ **静默返回空**。
  这正是 `docs/规范/踩坑日志.md:463` 记录的反模式：
  「`if (!tenantId) return {total: 0}` 这种"参数缺失就静默返回空"……静默空值会把参数用错伪装成数据为空」。
- 且 `:573` 的 `|| ctx.tenantId` 兜底会被移除（见 §五）。

## 四、对外行为变化（已获team-lead 裁决确认）

| 端点 | 场景 | 收敛前 | 收敛后 | 性质 |
|---|---|---|---|---|
| 归档查询 | 平台 JWT 无 tenantId + 不传参 | 400 | 200 查全租户 | 恢复运维能力（该端点本就该查全部） |
| 清除记忆 | 平台 JWT 无 tenantId | 400 | 400 | **无变化** |
| 清除记忆 | 商户自报他人 | 403 | 403 | 无变化 |
| 审计查询 | 平台 + 不传 tenantId | 200（走`:573` 就近兜底） | **400** | **收紧** |
| 审计查询 | 平台 JWT 无 tenantId | 400 | 400 | 无变化 |
| 审计查询 | 商户自报他人 | 403 | 403 | 无变化 |
| 全部三处 | 绕过守卫直调（req 无身份） | 400 / AI_001 | **403 / AI_010** | 语义归正 |

### 关于「清除记忆」风险等级的更正（采纳 team-lead 的核对）

我初版报告把这一处评为「风险最高」，理由是「平台 JWT 无 tenantId 就能删任意租户记忆」。
**team-lead 核对后指出该判断不成立，我确认这个更正是对的**：

`tenantId` 是 `@Param('tenantId')` 必填路径参数，NestJS 参数管道在进入方法体前即拒绝缺失路径参数
⇒ 平台**必须**显式指定 tenantId 才能调通此端点。收敛为 `resolveAdminTenantId` 对这一处
**不产生任何行为变化**（上表已列实测：平台无 tenantId 场景前后同为 400）。

⇒ 我原报告的「放宽」措辞是错的，实际既非放宽也非收紧。此处按更正后的事实记录。

### 关于「缺身份 400 → 403」

判定为**语义归正**：缺身份本质是鉴权问题而非参数问题。`AdminGuard` 已在管道最前端拦掉
无 token / 无效 JWT，能走到控制器读取身份失败的只可能是**绕过守卫直调**
（如 spec 直接调方法）。此时报 400「请携带有效 JWT」是误导性的（带着合法 JWT 也会 400）。
统一函数报 403 / AI_010「缺少管理端身份」语义准确。

## 十、A1 与 A2 的重叠说明

避免两份报告读起来像在修同一个问题 —— **A1 与 A2 不是同一个问题**：

| | A1（本卡） | A2（listTasksFor 补 tenantId） |
|---|---|---|

⇒ **A2 是"补机制"（补上纵深防御、防止将来 `employeeId` 语义变化或新增调用方时失守），
不是"修漏洞"。** A1 修的是当下已存在的写法分叉。两者无重叠。

## 十一、发现但本卡未处理的问题

### 1. 🔴 `mcp-token.service.ts` 新老 API 并存（建议另立卡，优先级高于 A1）

```
:123  async setEnabled(id, enabled)  → this.repo.update(id, {...})          裸 id，无 tenant_id 条件
:162  async remove(id)                → this.repo.delete(id)                  裸 id，无 tenant_id 条件
```

控制器 `mcp-admin.controller.ts:122/:139` 已正确调用新版 `setEnabledFor(id, enabled, tenantId)` ✓，
但**两个旧版仍在仓库中** ⇒ 未来任何新调用方直接调旧版即天然越权。

这正是第九轮点名的「新老 API 并存」样本，也印证了根因「修 bug 必须删旧入口，不能只留个新版本」。

⚠️ 本卡未动：`mcp-token.service.ts` 不在 A1 文件域内，且删除旧版需同步改spec。

### 2. 🟡 `mcp-admin.controller.ts` 的 optional 用法值得复核

`setEnabled`(`:122`) / `remove`(`:139`) 用 `resolveOptionalAdminTenantId(req)`，
即**平台不传 tenantId = 全量改任意 id**。对「按 id 停用/删除」这类操作，
`optional` 意味着平台可在不指定租户时操作全平台范围的记录。是否应改为必锁，需单独评估。

### 3. 🟡 `TenantContext.requireTenantId()` 的注释已过时

`tenant-context.ts:175-183` 的 `requireTenantId()` 注释仍称平台跨租户场景"调用此方法会抛错"，
但 A1 收敛后管理端点不再走该方法。注释需同步（未改，超出本卡文件域）。

### 4. 🟡 平台 JWT 无 tenantId 时，审计查询返回 400 的提示语可更友好

现返回 `AI_010`「平台身份跨租户操作必须显式指定 tenantId（不接受缺省值）」。
语义准确，但管理台用户看到 400 时可能困惑（前端若未传 tenantId）。属产品体验层面，
不改。
