# AI 底座 · 数据链路能力规划（抓取 → 统计 → 分析 → 总结 → 建议 → 工作流）v1.0

> 设计人：凌舟｜2026-10-14｜状态：方案稿（业主确认后实施）
> 业主口径：「重点是数据抓取，统计，分析，总结，建议。要完善工作流」
> 原则：**复用优先** —— OPS 已有采集（intel）与编排（workflow），AI 底座补 AI 段（统计/分析/总结/建议），不重造

---

## 一、数据链路全景（六段）

```
① 抓取 → ② 统计 → ③ 分析 → ④ 总结 → ⑤ 建议 → ⑥ 工作流执行
（OPS intel）  （AI）     （AI）     （AI）    （AI）      （AI+OPS workflow）
```

| 段 | 职责 | 载体 | 现状 |
|---|---|---|---|
| **① 抓取** | 多源数据采集（网页/评论/热点/关键词/竞品） | **OPS intel 模块**（collect-source + collect-task，web/local 双模式，清洗+限频） | ✅ 已实现 |
| **② 统计** | 聚合/去重/分组/趋势计算/环比同比 | **AI 底座（新增）** | ❌ 缺 |
| **③ 分析** | 异常检测/对比/归因/预测 | AI 底座 **proactive 域部分已有**（business-anomaly / gross-margin / customer-churn） | ⚠️ 部分 |
| **④ 总结** | 自然语言总结（日报/周报/专题） | AI 底座 **daily-briefing / weekly-plan 已有** | ⚠️ 部分 |
| **⑤ 建议** | 可执行建议（补货/催收/营销/定价） | AI 底座 **replenishment-advice 等已有** | ⚠️ 部分 |
| **⑥ 工作流** | 建议落地为可执行工作流（人工确认/自动执行） | **OPS workflow + AI 底座 Agent 引擎** | ⚠️ 两套未打通 |

## 二、缺口分析与补齐方案

### 缺口 1：② 统计段 —— 抓取数据没有统计加工链
- OPS intel 采回的原始数据（评论/热点/竞品）**没有统计聚合**（按源/平台/时间/情感分桶、趋势、环比）
- **补齐**：AI 底座新增 `ops-statistics` 工具族（对 intel 采集结果做统计加工），或 OPS 侧补统计服务 —— **建议 AI 底座做**（LLM+SQL 混合统计是 AI 强项）

### 缺口 2：③④⑤ 的覆盖面 —— 现有分析/总结/建议只覆盖**进销存域**，不覆盖**运营域**
- proactive 9+3 项全是进销存/财务域（库存预警/应收催收/经营异常…）
- **运营域**（短视频/直播的选题/脚本/投放/粉丝）的分析总结建议**空白**
- **补齐**：proactive 框架按 OPS 数据源扩展（运营域简报/竞品分析/投放建议）—— 依赖 OPS 数据经 Skill Gateway/适配层进 AI 底座（双系统对接 E 期）

### 缺口 3：⑥ 工作流 —— 两套编排未打通
- OPS workflow（RabbitMQ + SSE，nodes 编排）与 AI 底座 Agent 引擎（planner/task-runner/self-heal）**各自独立**
- **补齐**（分两步）：
  - 短期：AI 建议 → **人工确认** → 经 ops_ 工具创建 OPS workflow（建议落地为工作流模板）
  - 长期：AI 建议 → 自动生成 workflow 节点图（需 workflow.service 支持 AI 生成 nodes 的接口）

### 缺口 4：链路无“闭环追踪”
- 建议 → 工作流 → 执行结果 → 回流为新的分析输入 —— **没有闭环**（建议提了就完了，不知道效果）
- **补齐**：建议实体加 `workflow_id` / `effect_feedback` 字段，形成“建议→执行→效果→再分析”闭环

## 三、实施路线（四期，每期可独立验收）

| 期 | 内容 | 依赖 | 量级 |
|---|---|---|---|
| **P1 统计工具族** | AI 底座新增 `ops-statistics` 工具族（对 intel 采集结果统计加工：分组/趋势/环比/TopK）—— 对接 OPS intel API（走双系统对接 E 期的通道） | 双系统对接 P1（身份映射）| 1 天 |
| **P2 分析扩展** | proactive 框架扩运营域（竞品动态分析/投放效果分析/内容表现分析）—— 依赖 OPS 数据进 AI | 同上 | 2 天 |
| **P3 总结升级** | daily-briefing / weekly-plan 扩运营域（或新增 ops-briefing）；支持“按任意主题即时总结”（对话式，非仅定时） | P2 | 1 天 |
| **P4 建议落地+闭环** | 建议 → ops workflow 模板创建（ops_ 工具）+ 建议实体闭环字段（019 迁移）+ 效果回流分析 | P3 + OPS workflow 接口 | 2 天 |

## 四、与既有架构的关系

| 层 | 关系 |
|---|---|
| **治理链** | 新增工具族（ops-statistics 读 / 建议-落地写）**同过治理链**：读全自动；写（创建 workflow/落地建议）走写全审核 |
| **OPS Skill Gateway** | 双向：AI 底座读 OPS 采集数据（经适配层）；AI 底座生成能力注册为 OPS 的 Provider（方案 C 双向互联）|
| **权限** | OPS 会话来源（zhixiang-ops JWT）→ 映射租户 → ops 工具族可见（总设计 v2.0 D2 已定）|
| **办公能力** | 数据链路的产出（报表/建议/简报）可**沉淀为办公文档**（与文档中心打通）—— 两规划互不冲突 |

## 五、待业主确认（3 项）

1. **统计工具族的部署形态**：AI 底座新增工具（走 ToolExecutor 治理链）✓ 推荐；还是 OPS 侧做统计服务（AI 只调用）？
2. **数据链路的触发方式**：定时（proactive @Cron）+ 事件（采集完成触发）+ 对话（用户即时问）三种都要，还是先只做对话式？
3. **闭环追踪的范围**：只追踪“建议→工作流创建”，还是要“执行结果→效果评估”全闭环（后者需 OPS workflow 执行结果回传接口）？

---

## 六、本规划不做什么

- 不重造 OPS 的采集能力（intel 已有，AI 只消费其产物）
- 不做通用爬虫框架（intel 的 web/local 双模式已覆盖当前需求）
- 不做 BI 级可视化（OPS dashboard/BI 域已有，AI 只供数）
- 不做实时流计算（当前数据量无需；统计批处理即可）

## 七、业主补充（2026-10-14）：**这条链路对管理系统同样重要**

> 「数据抓取→统计→分析→总结→建议，这条工作流对管理系统也同样重要。例如：抓取商品销售和库存数据，分析价格走势和销售预测等等，都是需要这条工作流的。」

### 7.1 修正：链路是**双数据源、双落地域**（非运营专属）

| 段 | 管理系统侧（进销存） | 运营系统侧（短视频直播） |
|---|---|---|
| **① 抓取** | **MS 后端业务数据**（销售单/库存/商品价格/应收应付）—— 经 ServiceClient（59 处现成调用）+ API 目录动态技能 | OPS intel 采集（评论/热点/竞品/关键词）|
| **② 统计** | 销量聚合/库存周转/价格带分布/客户复购 | 播放量/互动率/粉丝增长/竞品对比 |
| **③ 分析** | **价格走势分析**、**销售预测**、毛利异常、库存预警、客户流失 | 竞品动态、内容表现、投放效果 |
| **④ 总结** | 每日/每周经营简报（已有）+ 专题总结（价格带/品类/客户） | 运营周报/内容复盘 |
| **⑤ 建议** | **定价建议**（低毛利警告→调价建议）、**补货建议**、催收计划、营销选品 | 投放建议、选题建议、发布策略 |
| **⑥ 工作流** | 落地为 AI 底座工具执行（过写全审核）或 MS 审批流 | 落地为 OPS workflow（AI 生成 nodes）|

### 7.2 管理域的具体能力项（新增，进实施路线）

| # | 能力 | 数据源 | 说明 |
|---|---|---|---|
| M1 | **价格走势分析** | `query-sale-bills`（历史成交）+ `update-product-price`（调价史）| 按商品/SKU 出价格曲线与趋势，识别"售价低于进价"类风险（AI-18 已有风险标注的数据基础）|
| M2 | **销售预测** | 销售单历史（按商品/品类/客户）| 时间序列预测（简单移动平均/同环比外推起步），输出预测区间与置信度 |
| M3 | **库存周转分析** | `query-inventory` + 销售速度 | 周转天数/滞销识别/安全库存建议 |
| M4 | **客户复购与流失** | 销售单 × 客户维度 | 复购率/RFM 分层（AI 底座已有 customer-churn proactive 可扩展）|
| M5 | **定价建议闭环** | M1 + 毛利数据 | 建议 → 用户确认 → `update-product-price` 执行（**过写全审核门**）|

### 7.3 实施路线更新（P1 扩为双域统计）

| 期 | 内容（更新） |
|---|---|
| **P1 统计工具族** | 对**两个数据源**统计加工：MS 业务数据（经 ServiceClient/API 目录）+ OPS intel 采集数据 |
| **P2 分析扩展** | 进销存域补 **M1 价格走势 / M2 销售预测 / M3 库存周转**（proactive 框架扩展，复用 business-anomaly/gross-margin 范式）；运营域同批 |
| **P3 总结升级** | 简报双域合并（经营简报 + 运营简报）；支持对话式"按主题即时总结" |
| **P4 建议落地+闭环** | 双域建议落地：管理域走 AI 工具（过写全审核）/运营域走 OPS workflow；闭环字段 019 迁移 |

### 7.4 关键优势（管理域这条链路）

- **数据源现成**：59 处 ServiceClient 调用 + 43 个 API 目录动态技能 = 销售单/库存/价格数据**已在 AI 底座可达范围**
- **proactive 框架现成**：business-anomaly / gross-margin-anomaly / replenishment-advice 就是这条链上的 ③⑤ 段雏形
- **写落地有治理**：建议落地（调价/下单）经写全审核门 ✓ —— **"建议"不会变成"AI 擅自改价"**

### 7.5 治理补充（管理域特有）

- M5 定价建议闭环：**建议 → 用户确认 → update-product-price（high risk，过写全审核）** —— 金额与价格类写操作的 risk 已标 high（AI-18 补标），审核口径已就绪
- 预测类能力输出**必须标注"预测"与置信度**，不得冒充历史真值（对应队列 S3-98「p95 无列禁用近似值冒充真值」同族纪律）

## 八、三项确认定案（业主授权按真实场景判断，2026-10-14）

| # | 事项 | 定案 | 真实场景依据 |
|---|---|---|---|
| ① | **统计部署形态** | **AI 工具族**（走 ToolExecutor 治理链） | 用户在对话里问"这个月五粮液卖得怎么样" ⇒ AI **即时按任意维度组合统计**（LLM 强项）；若统计做在 OPS 侧，AI 只能调固定报表，失去按需灵活性。且走治理链 = 审计/幂等/租户隔离自动覆盖 |
| ② | **触发方式** | **三种都要**（定时 + 事件 + 对话） | 每日简报（定时）；库存预警触发补货建议（事件，proactive 框架已支持）；"马上分析红星商行欠款"（对话，即统计工具族调用）。proactive 框架天然支持前两种，第三种=P1 统计工具族 |
| ③ | **闭环范围** | **一期：建议→工作流创建**（追踪创建与执行状态）；**二期：效果评估** | 效果回流需 OPS workflow 执行结果回传接口（对方开发）+ 效果评估口径（需数据积累）⇒ 不阻塞一期；一期先闭环"建议不落空" |

### 附加定案（随 ① 派生）
- **统计工具族双域**：管理域（销售/库存/价格，经 ServiceClient+API 目录）+ 运营域（intel 采集数据，经双系统通道）—— 同一工具族、按会话来源取数
- **治理**：统计=读全自动（不耗幂等键、不受写严桶限流——R101-AI-31 分桶后读走宽桶）；建议落地=写全审核（M5 定价建议 risk=high 已就绪）

## 九、并入总设计路线（v2.0 修订）

总设计 v2.0 路线并入数据链路四期（排在 E 双系统对接的 P1 身份映射之后）：

```
A1 内嵌存储 → A2 standalone 装配 → B 总台账号 → C 三端封装
```
