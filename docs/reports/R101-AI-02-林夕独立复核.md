### 2.2 ⚠️ 险情：pnpm 差点删除主仓 node_modules（必须报备）

在 junction worktree 里执行 `pnpm exec jest` 会失败，原始输出：

```
[ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY] Aborted removal of modules directory due to no TTY
If you are running pnpm in CI, set the CI environment variable to "true", or set "confirmModulesPurge" to "false".
[ERROR] Command failed with exit code 1: ... pnpm install
```

**机理**：pnpm 把 junction 识别为"需要清除的 modules 目录"，试图执行 `pnpm install` 并 `remove modules dir`。因**无 TTY** 才 abort——**若设了 `CI=true` 它就会真的执行**，而 junction 指向主工作区的 `D:\Users\ZXQL\ZXQL-AI\node_modules`，后果是全仓依赖被清。

**处置**：立即弃用 pnpm，改用 node 直跑二进制绕开 pnpm 的 deps check：

```bash
node node_modules/jest/bin/jest.js --silent
node node_modules/typescript/bin/tsc -p tsconfig.json --noEmit
node node_modules/eslint/bin/eslint.js "src/**/*.ts" --max-warnings=0
```

**已确认主仓依赖完好**：`ls node_modules | wc -l` = **504**（与主工作区一致）。

**建议进长期纪律**：junction worktree 里禁止用 `pnpm exec` / 禁止设 `CI=true`。

## 6. 两处「我预判错了，实证推翻」——如实记录

### 6.1 `||` → `??` 的劣化：挡住它的是 B-2，不是 B-1

我开工前的预判是「B-1（优先级方向）会挡住 `||`→`??`」。**实测推翻**：

- B-1（优先级方向）**仍绿** —— 因为用例里 `resolved.apiKey` 是非空字符串，`??` 与 `||` 结果相同 ⇒ **B-1 单独对这一劣化无分辨力**
- B-2（兜底方向）**红**：`Expected: "sk-external-lib" / Received: ""`

**挖出的真实脆弱点**：`resolved` 未配置时解析出的是**空字符串 `''` 而非 `null`**。因此：
- `'' || external.apiKey` → `external.apiKey`（正确兜底）
- `'' ?? external.apiKey` → `''`（**兜底失效，密钥为空**）

⇒ **结论**：这一劣化被 **B-2** 挡住，**组合覆盖无盲区**；但**逐条**看，B-1 对 `||`→`??` 无分辨力。这是分辨力边界，不是缺陷，如实列报。

### 6.2 C 组的双向夹住成立

把三元改成**无条件带 config**（与反测 C 的反向劣化），结果 `1 failed, 1 passed`：
- C-1（正向）**绿**（它本就要求带 config）
- C-2（负向补集）**红** —— `not.toHaveBeenCalledWith('custom_kimi', expect.anything())` 被违反

⇒ C-1/C-2 一正一反**双向夹住**：无论三元退化成"总不带"还是"总带"，都有断言能抓住。设计成立。

## 7. 判红与观察项

### 判红：**0 条**

按验收标准 2，「回退后仍绿」的断言才判红。实测中**负责各语义的断言在回退后均由绿转红**，无一条符合判红条件。

### 观察项 1 —— A-5（匿名 401）不属于本单新增的分辨力

A-5 守护的是 `AdminGuard` 的既有行为（无 Bearer ⇒ 401），与 R101-AI-01 的「平台身份收口」**无关**：反测 A 移除 `requirePlatformIdentity` 后它**仍绿**，证明它对该修复零分辨力。

**不是缺陷**（作为"守卫未整体失效"的回归有价值），但**不应计入"本单新增的自动化守护"**。建议凌舟在收口时把它从 R101-AI-01 的"缺口 1 已消除"口径里摘出来——否则会把既有覆盖当成新增覆盖。

### 观察项 2 —— B-4 把 `strictEgress === false` 固化为"正确断言"

B-4 断言 `expect(result.config.strictEgress).toBe(false)`，其语义是「平台来源解析出的 strictEgress 为 false，原样透传」。

这与我此前记录的观察项同源（`ai-config.service.ts:309` 平台端点 `strictEgress=false`，即**平台来源端点不做严格出站校验**）。影响：

- **分辨力**：对"透传语义"有分辨力（若被改成 true 会红）
- **副作用**：它同时**阻挡了一项可能正确的安全加固** —— 未来若凌舟裁定"平台端点也应收紧"，这条断言会先变红。

建议：这条断言锁死的是**当前行为**而非**应有行为**。若平台端点收紧一事尚无裁定，维持现状即可，但**裁定收紧时必须同步改这条断言**，否则会被误判为回归。
