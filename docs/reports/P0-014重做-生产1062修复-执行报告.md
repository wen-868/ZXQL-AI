## 二、根因独立核实（三条全部复现，与追单卡描述不同）

⚠️ **追单卡 §三写「014 没先做存量去重」不准确** —— 旧脚本**有**去重（按四元组 `GROUP BY tenant_id, stat_date, provider, model`）。涉及三条原因，其中 A 与 C 在生产直接成立、B 仅在「无三列键环境」成立（⚠️ 定性更正见下节）；A 与 C 已在 MySQL 8.0.28 上逐条复现：

### 原因 A（归一化让原本不受约束的行突然受约束）

复刻：已有 `uk_tenant_date_provider (tenant_id, stat_date, provider)` + 大量 `provider IS NULL` 行 → 跑**旧版** 014：

```
+--------------------------------------------------------+
| next_step                                              |
+--------------------------------------------------------+
| uk_usage_daily 不存在，继续执行去重与建键              |
+--------------------------------------------------------+
EXIT=1
Stderr: ERROR 1062 (23000) at line 87: Duplicate entry 'default-2026-08-10-'
        for key 't_ai_usage_daily.uk_tenant_date_provider'
```

`line 87` 与生产报错行号**完全一致**。机理：MySQL 唯一索引允许多个 NULL ⇒ 含可空列 `provider` 的键对 `provider IS NULL` 的行**完全不生效** ⇒ 旧脚本 `SET provider = ''` 的瞬间这些行第一次真正受约束，而它们彼此重复。

### 原因 B（去重口径比唯一键更宽）—— ⚠️ 定性更正：不是生产独立的第二条失败路径

本报告初版把原因 B 定性为「独立第二条失败路径，已在 MySQL 8.0.28 上单独复现（provider 全非 NULL、模型各不相同）⇒ ERROR 1062 at line 27（建键语句）」。**林夕独立验收证明这一定性夸大了**：

在**已有三列键** `uk_tenant_date_provider (tenant_id, stat_date, provider)` 的表上（`probe_b` 库），插入第二行同 `(tenant_id, stat_date, provider)`、不同 `model` 的数据，**数据库直接拒绝**：

```
ERROR 1062 (23000): Duplicate entry 't2-2026-08-11-openai'
for key 't.uk_tenant_date_provider'
```

也就是说**生产上这种行根本不可能存在**——三列键早就在拦。原先那次「复现」必然是在**没有三列键**的表上做的（新库从零建、或键尚未建立），该环境与生产结构不符，不能作为生产第二条失败路径的证据。

**更正后的定性**：

- 生产 1062 只有**原因 A 一条路径**（归一化瞬间让原本不受约束的 NULL 行突然受约束）。
- 原因 B 只在「无三列键环境」（新库初始化、或键尚未建立）才会发生。
- **结论保留**：合并仍必须按**归一化后的三列**做——四元组 / 原值分组都不对（反测见 §八 变体 3）。

原先「只修 A 不够（换哨兵仍撞 B），只修 B 也不够」的表述一并更正：原因 A **无法靠「只换哨兵值」绕过**，必须**先按归一化值合并、再归一化**，才能让归一化不产生新重复。

### 原因 C（守卫漏检）

旧脚本 `@uk_exists` 只查 `uk_usage_daily` 一个名字，生产上算出 `0` ⇒ 守卫全部放行（上面输出 `next_step` 已证）。

### 附带发现（我方修正，非卡上内容）—— ⚠️ 已随 §二定性更正一并修订

初版此处写「三列键在已有三列键的表里意味着同 `(tenant, date, provider)` 下两行不同 model 根本插不进去，这从侧面印证原因 B 的现实性」——**这是误读，已撤回**：这一事实恰恰证明**相反的结论**——原因 B 描述的行在生产上**不可能存在**（`probe_b` 实测见上节），原因 B 不是生产 1062 的第二条失败路径。

### 1. 选了 (a) 还是 (b)，理由

**选 (a)**：列改 `NOT NULL DEFAULT 'unknown'`。

| 理由 | 说明 |

| 可执行性 | 生成列/函数索引在 MySQL 需 8.0.13+、MariaDB 需 10.2+ 才支持持久化索引；本仓迁移要求两引擎通用。(a) 只是 `MODIFY COLUMN`，两引擎早已支持且行为一致 |

### 2. 哨兵值定成什么，三处是否一致

**哨兵值 = `'unknown'`**（provider 与 model 同）。不用 `''`：空串与「有效但为空」不可区分，报表里表现为空值，且极易被下轮迁移再次误判成"未设置"。

| 处 | 位置 | 值 |
|:--|:--|:--|
| 库默认值 | `migrations/014_usage_daily_unique_key.sql:321, :345`（MODIFY COLUMN）；实体 `ai-usage-daily.entity.ts` | `NOT NULL DEFAULT 'unknown'` |
| 迁移回填值 | 同脚本第 5 步（`WHERE provider IS NULL OR provider = ''`） | `'unknown'` |
| 写入侧兜底 | `src/bridge/audit-logger.ts:491-492` | `params.provider ?? 'unknown'` / `params.model ?? 'unknown'` |

**三处已完全一致**，且实体类型从 `string | null` 收紧为 `string`（tsc 两项均通过，无残留 null 消费方）。

### 3. 合并后 `model` 取值的确定性规则

```sql
COALESCE(MIN(NULLIF(NULLIF(model, ''), 'unknown')), 'unknown')
```

读作：**先剔除 NULL / `''` / `'unknown'`，再取字典序升序最小的 model；组内无任何有效 model 则取 `'unknown'`**。

- 为什么先剔除 `'unknown'` 再 MIN：否则一旦组内存在 `'unknown'`，字典序最小的极可能就是它，会把同组内**真实的 model 掩盖掉**。
- 为什么不用「占比最大的 model」：MIN 是纯函数，任何时刻对同一组数据重跑结果完全一致；「取第一行」依赖物理行序，不可复现（卡上明令禁止）。占比口径需窗口函数/自子查询，分区边界更易错，且在 DELETE 已改变行集后重算会得到不同结果。两者都只是「代表值」，既然必然有损，宁取规则最简、最易审计的。
- **独立复核**：用一条独立查询从迁移前快照反算该规则并逐行比对，8 行全部 `RULE_OK`（实测输出见 §五）。

### 7.1 不可逆代价（必须让审查方知晓）

**合并后 `model` 退化为「组内代表值」，本表不能再按 model 拆分用量。**

### 8.1 三条反测原文与报错（含一次假绿）

1. **变体 3（核心）**：合并分组键从 `COALESCE(NULLIF(provider,''),'unknown')` 还原成 `provider` 原值 ⇒
   `ERROR 1062 (23000) at line 36: Duplicate entry 't3-2026-08-12-unknown' for key 't_ai_usage_daily.uk_tenant_date_provider'`
   ⇒ 归一化分组键有真实区分力。
2. **变体 2c**：让 UPDATE 真的改 provider，且该组 `unknown` 行故意最后插入（使 `MIN(id)` 落在 `provider IS NULL` 的行上）⇒
   `ERROR 1062 (23000) at line 20: Duplicate entry 't4-2026-08-13-unknown' for key 't_ai_usage_daily.uk_tenant_date_provider'`
   ⇒ 脚本旧注释描述的「先 UPDATE 再 DELETE 会瞬时撞键」因果链在该前提下为真。
3. **变体 2b 假绿（本轮最有价值的教训）**：同上的 UPDATE 改 provider，但该组 `MIN(id)` 恰好已是 `unknown` 行 ⇒ UPDATE 是空操作 ⇒ **不撞 1062，反测假绿**。为此重造了基线数据才测出真结果（即变体 2c）。
   **教训：构造「保留行（MIN(id)）」类反测时，必须先确认 MIN(id) 落在哪一行，否则测了等于没测。**
4. **问题 1 的实测（`probe_b` 库）**：已有三列键的表插第二行同三列不同 model ⇒
   `ERROR 1062 Duplicate entry 't2-2026-08-11-openai'` ⇒ 原因 B 定性更正的依据（见 §二）。
