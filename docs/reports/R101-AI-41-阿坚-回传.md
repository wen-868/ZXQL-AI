## 三、关键设计

### S1 Cancel（状态机语义分层，引规范 §2.1）
| 当前状态 | 处理 |
|---|---|
| `pending` / `in_progress` | **原子迁移** `UPDATE ... WHERE status IN ('pending','in_progress')` ⇒ cancelled |
| 已 `cancelled` | **回放**（无歧义终态）|
| 已 `done` | 🔴 **明确失败**（跨终态：完成不能被"撤销为取消"；撤销完成是另一产品动作，本单不做）|
- 权限：`canWriteResource`（与 `aiTodoUpdate` 同口径）；preview→confirm；`idempotencyKeyFields=['todoId']`

### S2 Discard（**采纳"软删"并给出更优解说明**）
- **软删**：置 `deleted_at`（保留记录 ⇒ 可回溯"谁写过又丢了什么草稿"）；❌ 不做物理 DELETE
- 🔴 **为什么用 `deleted_at` 列而不是扩展 `status` 枚举**（我采纳的"更优解"）：
  1. `draft/pending/approved/…` 是**工作流状态**；"被丢弃"是**生命周期标记**，语义层级不同
  2. 扩展 MySQL ENUM 需**四处同步**（TS 联合 + 实体 enum + MySQL ENUM + sqlite）—— **AI-40 刚踩过**（`notice`）
  3. 与既有家族一致（通知 `archived_at`、日程 `reminded_at`）同为"时间戳标记"范式
- 约束：**仅 draft 可弃**（pending 及以后 ⇒ 明确拒绝 + 指引用 `aiApprovalCancel`）；权限 = 申请人/平台/ACL write；**原子条件 `status='draft' AND deleted_at IS NULL`**；已弃 ⇒ 回放
