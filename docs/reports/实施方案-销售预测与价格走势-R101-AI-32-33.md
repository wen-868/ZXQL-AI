## 二、能力一：销售预测（R101-AI-32）—— 可直接实施

### 2.1 输入数据与算法（务实选型）

| 层 | 方案 |
|---|---|
| 数据输入 | `api_get_sales_trend`（趋势序列）+ `querySaleBills`（明细，可选下钻）|
| 算法（起步） | **同环比外推 + 移动平均**（非机器学习）：<br>① 取历史 N 期（默认 12 期）实际值<br>② 计算同比/环比增速，取稳健值（去掉异常期）<br>③ 外推未来 K 期（默认 1~3 期）<br>④ 输出**预测区间**（下限/中枢/上限）+ 置信度 |
| 为什么不用 ML | 数据量小（单租户）、可解释性优先、工程成本低；后续数据积累后可升级 |

### 2.2 工具契约（草案）

```
名称：forecastSales
入参：
  - dimension: 'product' | 'category' | 'customer' | 'overall'（默认 overall）
  - targetId: number（dimension 非 overall 时必填）
  - granularity: 'day' | 'week' | 'month'（默认 month）
  - periods: number（预测期数，默认 1，上限 3）
  - historyPeriods: number（历史期数，默认 12）
出参：
  - forecast: [{ period, lower, central, upper, confidence }]
  - basis: { historyUsed, growthRate, excludedOutliers: [...] }   ← 可解释性
  - disclaimer: "本结果为基于历史数据的预测，非实际发生值（置信度 xx%）"
```

### 2.3 红线（对应队列纪律）

- **必须标注"预测"**并给出置信度，**不得冒充历史真值**（同 S3-98「p95 无列禁用近似值冒充真值」同族纪律）
- 历史数据不足（< 3 期）⇒ **明确拒绝并说明**（不硬给数字）

## 三、能力二：价格走势分析（R101-AI-33）—— 需先建价格历史

### 3.1 阻塞事实（实测）

- 现有价格能力**只有写**：`updateProductPrice`（改价）
- **无价格历史表 / 无调价记录查询** ⇒ 走势分析无数据可依

### 3.2 分两步实施

**第 1 步（前置）：建价格历史**
| 项 | 方案 |
|---|---|
| 数据落点 | **管理系统侧**（按业主「哪一端的工作归哪一端」原则修正：价格主数据归属 MS，AI 侧不应自建价格表）|
| 理由 | 价格是 MS 业务真源；若 AI 侧自建 `t_ai_price_history`，只会记录"经 AI 改价"的记录，与 MS 后台直接改价的历史割裂 ⇒ 数据不完整、且越界 |
| MS 侧需求 | ①调价时落历史记录（含 SKU/价格等级/旧值/新值/时间/操作人）②提供按 SKU 的价格时间序列查询接口（供 AI 消费）|
| AI 侧 | 仅消费该接口，**不建价格表** |

> ⚠️ 方案修订说明（2026-10-15）：初稿曾建议"AI 底座侧自建价格历史表以避免跨线阻塞"。
> 经业主指出「要分清是哪一端应该去做的工作」，已修正为 **MS 侧提供**（价格数据归属管理系统）。
> 代价：需跨线协作（MS 线排期），但数据归属正确、无割裂风险。

**第 2 步：走势工具**
```
名称：analyzePriceTrend
入参：skuId / productId、priceLevel（零售/批发/进价…）、start、end
出参：
  - series: [{ date, price }]
  - trend: 'up' | 'down' | 'flat'（含涨跌幅、波动区间）
  - insight: 自然语言结论（如"近 90 天零售价 3 次上调，累计 +12%"）
  - 关联风险提示：若当前售价低于进价 ⇒ 引用 AI-18 的亏损警告语义
```

### 3.3 与既有能力的协同

- 与 `updateProductPrice`（写，risk=high）形成**闭环**：改价有历史、走势可追溯
- 与 M5「定价建议闭环」衔接：走势 + 毛利 ⇒ 定价建议 ⇒ 用户确认 ⇒ 改价执行（过写全审核）

## 四、实施步骤（分四步，每步可独立验收）

| 步 | 内容 | 依赖 | 估算 |
|---|---|---|---|
| **S1** | 销售预测工具 `forecastSales`（算法 + 工具 + 契约 + 反测） | 无 | 1 天 |
| **S2** | 价格历史落点（`t_ai_price_history` 019 迁移 + 改价成功后落历史） | 无 | 0.5 天 |
| **S3** | 价格走势工具 `analyzePriceTrend`（读历史 + 走势 + 结论） | S2 | 1 天 |
| **S4** | 集成验证（真实租户数据跑通 + 对话式触发 + 门禁） | S1+S3 | 0.5 天 |

**合计 ≈ 3 人日**（不含跨线等待）

---

## 五、验收标准（硬）

1. 三门禁全绿：**≥ 157 套件 / 1725 用例**（新增 spec 累加）
2. **反测不可省**：
   - 预测：去掉历史数据校验（<3 期应拒绝）⇒ 用例红；去掉"预测"标注 ⇒ 用例红
   - 价格历史：改价执行后**无历史记录** ⇒ 用例红
3. **真实数据验证**：用真实租户（非 demo）跑一次预测 + 一次走势，输出可解释（含 basis/disclaimer）
4. 对话式触发：自然语言（"预测下个月五粮液的销量"、"五粮液最近价格走势"）能命中工具
5. 既有 spec 零断言修改

## 六、分工（按系统归属 —— 业主原则「哪一端的工作归哪一端」）

### 6.1 分界线

| 工作 | 归属 | 执行线 | 理由 |
|---|---|---|---|
| **① 按商品/SKU 的销售时间序列接口** | 管理系统 | **MS 线（codex）** | 销售数据在 MS；现有 `api_get_sales_trend` 只有 period/start/end，**无商品维度** ⇒ 只能整体趋势，不能按商品预测 |
| **② 价格历史记录 + 查询接口** | 管理系统 | **MS 线（codex）** | 价格主数据在 MS；现有**无任何价格读接口**（只有 `updateProductPrice` 写）⇒ 价格走势无数据可依 |
| **③ 销售预测工具（forecastSales）** | AI 底座 | **AI 线（阿坚/凌舟）** | 消费 MS 接口做算法加工 + 自然语言结论（ADR-002：统计=AI 工具族）|
| **④ 价格走势工具（analyzePriceTrend）** | AI 底座 | **AI 线（阿坚/凌舟）** | 消费 MS 价格历史接口做走势分析 |

### 6.2 依赖顺序

```
MS 线：① 销售序列接口 ┐
       ② 价格历史接口 ┴──→ AI 线：③ 预测工具 / ④ 走势工具 → 集成验证
```
⇒ **MS 侧接口先行**（阻塞项）；AI 侧可在接口契约确定后并行开发（按契约 mock）。

### 6.3 我方（AI 线）内部角色

| 角色 | 职责 |
|---|---|
| **凌舟（我）** | 方案 + 派单 + 跨线协调（向 MS 线提接口需求）+ 过程审计 + 独立验收 + 收口推送（**不写业务代码**）|
| **阿坚** | ③/④ 工具实现（算法 + 契约 + 反测）；按 ADR-002 指定 hy4-preview |
| **苏然** | 反测用例与执行（含 mutation）|
| **林夕** | 独立复核（契约一致性、红线、真值冒充检查）|

### 6.4 需要向 MS 线提的需求（跨线协作单，同 S3-181-C 模式）

1. **按商品/SKU 的销售时间序列接口**（入参：skuId/productId、granularity、start/end；出参：按期的销量/销售额序列）
2. **价格历史查询接口**（入参：skuId、priceLevel、start/end；出参：价格时间序列）+ **调价时落历史记录**

### 6.5 备选（AI 线执行通道不稳时）
近期 teammate/workflow 通道**连续失败**（A2 后期由我代笔）。本轮：
- 先试派阿坚；若再失败 ⇒ 凌舟代笔实现，**验收仍独立**（苏然/林夕），质量不降

## 七、风险与不做

| 项 | 说明 |
|---|---|
| 预测准确性 | 起步用统计外推，**不承诺精度**；输出区间与置信度而非单点值 |
| 价格历史完整性 | AI 底座侧自建 ⇒ **只记录经 AI 改价的记录**；管理系统后台直接改价的历史**不会进入**（需 MS 配合才能全覆盖）—— 需向用户明示此边界 |
| 不做 | 机器学习模型训练、实时预测、跨租户预测（数据隔离红线） |
