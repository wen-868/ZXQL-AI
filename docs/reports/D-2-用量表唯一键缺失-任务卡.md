## 一、缺陷陈述（审查方实测）

### 失效链

`src/bridge/audit-logger.ts:441-454` 的用量汇总用原生 SQL UPSERT：

```sql
INSERT INTO t_ai_usage_daily
  (tenant_id, stat_date, chat_count, ...) VALUES (?, ?, ?, ...)
ON DUPLICATE KEY UPDATE
  chat_count = chat_count + VALUES(chat_count), ...
```

`ON DUPLICATE KEY UPDATE` **只在撞上唯一约束（含主键）时才走 UPDATE 分支**。而 INSERT **不带 `id`** ⇒ 主键自增永不冲突。

⇒ 该 UPSERT 能否去重，**完全取决于表里是否存在 `(tenant_id, stat_date, provider, model)` 的唯一键**。

### 取证一：用量表实体没有任何唯一键

```
$ grep -n "@Index" src/database/entities/ai-usage-daily.entity.ts
13:@Index('idx_tenant_id', ['tenantId'])
14:@Index('idx_created_at', ['createdAt'])
15:@Index('idx_tenant_created', ['tenantId', 'createdAt'])
16:@Index('idx_tenant_date', ['tenantId', 'statDate'])
17:@Index('idx_date', ['statDate'])
```
5 个索引**全部非唯一**（`@Index(name, [cols])` 默认 `unique: false`）。
关键：`idx_tenant_date` 是 `(tenant_id, stat_date)` **非唯一**，且**不含 `provider`/`model`** ⇒ 即使去重也对不上 UPSERT 的四元组口径。

### 取证二：全仓 5 张表有唯一键，用量表不在其中

```
$ grep -rn "unique: true" src/database/entities/

```
**用量表是全仓唯一缺少唯一键的高频写入表。**

### 取证三：DDL 缺失，无法自证

该表 DDL 不在本仓任何迁移里（`migrations/` 中 `CREATE TABLE` 只有 9 张表，`t_ai_usage_daily` 不在其中）。历史缺口对应的 `001` 迁移本就缺失。
⇒ **代码层面已可判定存在风险，但「生产现状」必须连库取证。**

## 二、如果成立，后果是什么

无唯一键 ⇒ 每次用量上报都 INSERT 新行 ⇒ 表按**请求数**而非**租户×日期×模型**膨胀：

| 受影响对象 | 失真方式 |
|---|---|
| `usage-stats` 报表 | 每次读多次求和，若按行取值则**只取到单条碎片**而非当日汇总 |
| `usage-alert` 超阈值告警 | 单条记录远低于阈值 ⇒ **告警永不触发**，超额用量完全不可见 |
| 计费/额度判定 | 若依赖该表，同样失真 |

⚠️ 这类故障的特点是**没有任何报错**。系统正常返回 200，只是数字一点点错，可能已经持续很久。

### R2 修复迁移 `migrations/014_usage_daily_unique_key.sql`

**必须幂等且可重入**，结构建议：

1. **检测**：`information_schema.STATISTICS` 查唯一键是否已存在 → 已存在则 `SELECT '已存在，跳过'`，直接退出
2. **查重**（关键前置）：不存在时先查 $(tenant_id, stat_date, provider, model)$ 的重复组数
   ```sql
   SELECT COUNT(*) FROM (
     SELECT tenant_id, stat_date, provider, model
       FROM t_ai_usage_daily GROUP BY tenant_id, stat_date, provider, model
      HAVING COUNT(*) > 1
   ) AS dups;
   ```
3. **去重合并**（仅在有重复时执行）：把重复组的 `chat_count / tool_call_count / prompt_tokens / completion_tokens / total_tokens` **SUM 合并到一行**，删除多余行。
   - ⚠️ **绝不能直接 `DELETE` 掉多余行** —— 那会**丢用量数据**，账目永久不平
   - 保留哪一行的 `created_at`：建议保留 `MIN(created_at)`（最早创建）
4. **建唯一索引**：`ALTER TABLE t_ai_usage_daily ADD UNIQUE KEY uk_usage_daily (tenant_id, stat_date, provider, model)`

⚠️ **MySQL 8.0 红线**：不支持 `ADD INDEX IF NOT EXISTS`（MariaDB 语法）⇒ 必须用 `information_schema` 判定 + `PREPARE` 动态 SQL，沿用既有迁移（008/009/010/012）的风格。
⚠️ **注释红线**：`--` 后必须至少留一个空白，否则 1064；中英文混排、全角括号紧跟 `--` 极易踩。自检 `grep -nE "^\s*--[^ \t-]" migrations/014_*.sql` 必须无输出。

**数据安全性约束（硬性）**：
- 去重步骤**必须保留全部用量数值**（SUM 合并），不得简单删除
- 迁移文件顶部用注释写明：执行前建议备份 `t_ai_usage_daily`
- **脚本只写不执行** —— 不在任何真实库（含本机）上执行 R2 的破坏性部分
