## 零、核心原则

**以下三条原则高于一切具体规则：**

1. **一个标准，一个项目。** 所有人读同一份标准，所有代码按同一份标准写。不存在"后端标准"和"前端标准"两份东西。

2. **先达标，再提交。** TS 报错不过不提交，构建失败不提交，与标准不符不提交。这是铁律，没有例外。

3. **公共逻辑只写一次。** 编号生成、价格判断、权限校验、追溯码解析、错误处理——这些只能存在于一个地方。任何地方出现第二份实现，就是 Bug。

4. **错误面前没有"不是我引入的"。** 遇到 TS 报错、构建失败、测试不过，不允许以"这是预存的""这是第三方库的问题""这不是我改的"为由推卸。每条错误只有三种归宿：修复、记录到踩坑日志并标注原因、报告凌舟决策。任务执行人对自己触及的全部代码质量负责。

5. **任务前必读 + 禁止私自修改（2026-08-16 用户指令，硬性规定）。** 任何成员（包括 AI 代理、运营人员、管理系统所有成员）做任务前必须读取 `docs/项目规则.md` 与本文档（`docs/项目统一标准.md`），未读取不得开工；没有问题的地方禁止私自修改，只允许修改有问题的地方，禁止顺手重构、扩大改动范围。违反者提交一律打回。

## 第一章：后端架构分层

### 1.1 固定目录结构

```

├── config/                    ← 全局配置（集中管理）
│   ├── env.ts                 ← 环境变量
│   ├── database.ts            ← 数据库连接池
│   ├── redis.ts               ← Redis 连接
│   ├── wechat-pay.ts          ← 微信支付配置
│   ├── tenant.ts              ← 租户配额（10G 等）
│   ├── api-billing.ts         ← API 计费配置
│   ├── permission.ts          ← 权限开关
│   └── constants.ts           ← 业务常量（箱规、导出上限、告警阈值等）
├── middleware/                 ← 全局中间件
│   ├── auth.ts                ← Token 鉴权（requireAuth/requirePlatformAuth/requireRoles）
│   ├── tenant.ts              ← 租户隔离校验

│   ├── store/                 ← 门店端
│   ├── miniapp/               ← 小程序端
│   ├── platform/              ← 平台端
│   └── instant-retail/        ← 即时零售
├── service/                   ← 业务逻辑层（所有数据库操作在此）
│   ├── admin/                 ← 同 controller 分端
│   ├── store/
│   ├── miniapp/
│   ├── platform/

│   ├── response.ts            ← 统一返回格式（ok/fail）

├── types/                     ← 类型定义
├── jobs/                      ← 定时任务
└── server.ts                  ← 入口文件
```

### 1.2 分层规则（不可违反）

| 层 | 允许做什么 | 禁止做什么 |
|:---|------|------|
| **controller** | 接收参数 → 调用 service → 返回结果 | 直接操作数据库（import db/query/pool） |
| **service** | 业务逻辑、数据库操作、调用外部 API | 直接操作 req/res 对象 |
| **route** | 注册路由、挂载中间件 | 写业务逻辑、直接操作数据库 |
| **shared** | 纯工具函数、不依赖 Express | 依赖 req/res、使用 Express 类型 |
| **middleware** | 请求拦截、鉴权、校验 | 写业务逻辑 |
| **config** | 导出配置常量 | 写业务逻辑、依赖 runtime 状态 |

### 1.3 当前差距（对照整改清单）

| 标准要求 | 当前状态 | 整改方向 |
|------|------|------|
| 有 `config/` 目录 | 无，配置散落在 `shared/` 中（db.ts、env.ts、wechat-pay.ts、redis-cache.ts） | 迁移到 `config/`，在 shared/ 中留 re-export 兼容 |
| 有 `middleware/` 目录 | 无，中间件混在 `shared/` 中（auth.ts、tenant.ts、price-guard-middleware.ts、error-handler.ts、async-handler.ts） | 迁移到 `middleware/` |
| controller 不操作数据库 | 2 个违规（wechat.controller.ts 直接 SQL、notification.controller.ts 传递 pool） | 下沉到 service |
| 返回体使用 `msg` | 当前使用 `message` | 改为 `msg`，补充 traceId/apiCost |

## 第二章：命名统一标准

### 2.1 数据库

| 对象 | 格式 | 示例 |
|------|------|------|
| 表名 | `t_模块_功能` | `t_product_spu`、`t_sale_bill`、`t_inventory_batch` |
| 字段名 | `snake_case` 小写+下划线 | `tenant_id`、`created_at`、`settlement_type` |
| 租户字段 | 所有表必带 `tenant_id` VARCHAR(36) | 无例外 |
| 主键 | `id` BIGINT UNSIGNED AUTO_INCREMENT | 统一 |
| 时间字段 | `created_at`、`updated_at` DATETIME | 统一 |
| 注释 | 中文 COMMENT | `COMMENT '客户类型：RETAIL-零售/WHOLESALE-批发'` |

**SQL 表名铁律（不可违反）：**
- DDL 通过 `shared/migration.ts` 的 `addTablePrefix()` 自动补 `t_` 前缀，DDL 层面已 100% 合规
- **Service / Controller / Middleware 中手写的原生 SQL 也必须使用 `t_` 前缀**，不依赖自动前缀补全（自动前缀仅在迁移执行时生效，运行时手写 SQL 直接打到数据库）
- 禁止出现 `FROM sale_bill`、`JOIN product_sku`、`INTO sys_user` 等不带 `t_` 前缀的表名
- 违规示例（禁止）：`SELECT * FROM sale_bill WHERE tenant_id = ?`
- 正确示例：`SELECT * FROM t_sale_bill WHERE tenant_id = ?`

### 2.2 后端 TypeScript

| 对象 | 格式 | 示例 |
|------|------|------|
| 文件 | `kebab-case` | `sale-bill.service.ts`、`purchase-order.controller.ts` |
| 类/接口 | PascalCase | `RouteConfig`、`AuthUser` |
| 函数/变量 | camelCase | `createOrder`、`listProducts` |
| 常量 | UPPER_SNAKE_CASE | `MAX_EXPORT_LIMIT`、`DEFAULT_SHELF_LIFE_DAYS` |
| 路由文件 | `模块.route.ts` | `admin-order.route.ts`、`store.route.ts` |

### 2.3 前端 Vue3

| 对象 | 格式 | 示例 |
|------|------|------|
| 视图组件 | PascalCase | `CustomersView.vue`、`SaleBillCreate.vue` |
| 公共组件 | PascalCase | `PriceInput.vue`、`TenantSelector.vue` |
| 变量/函数 | camelCase | `customerList`、`handleSubmit` |
| API 调用 | 统一使用 `api.ts` 中的方法 | 不直接在组件中用 axios |

### 2.4 API 路由

| 端 | 前缀 | 示例 |
|------|------|------|
| 工作台 | `/api/admin/` | `/api/admin/products` |
| 门店端 | `/api/store/` | `/api/store/orders` |
| 小程序端 | `/api/miniapp/` | `/api/miniapp/cart` |
| 平台端 | `/api/platform/` | `/api/platform/tenants` |
| 即时零售 | `/api/instant-retail/` | `/api/instant-retail/webhook` |

| HTTP 方法 | 用途 | 示例 |
|------|------|------|
| GET | 查询 | `GET /api/admin/products` |
| POST | 新增 | `POST /api/admin/products` |
| PUT | 修改 | `PUT /api/admin/products/:id` |
| DELETE | 删除 | `DELETE /api/admin/products/:id` |

**禁止**将动作动词嵌入 URL 路径（如 `/orders/:id/submit`、`/orders/:id/approve`）。状态变更应使用 PUT 请求并在 body 中传递操作类型。

## 第三章：全局返回体统一标准

### 3.1 强制格式

所有 API 接口**必须**使用以下格式返回，不允许任何特例：

```typescript
{
  code: string;    // "0"=成功，非 0=错误
  msg: string;     // 提示文字
  data?: T;        // 业务数据
  traceId: string; // 全局追踪 ID（UUID）
  apiCost: number; // 本次调用消耗计量数
}
```

### 3.2 统一返回函数（唯一出口）

**文件：** `backend/src/shared/response.ts`

```typescript
// 成功
export function ok<T>(data?: T) {
  return { code: "0", msg: "成功", data, traceId: uuid(), apiCost: 1 };
}

// 失败
export function fail(msg: string, code = "400") {
  return { code, msg, traceId: uuid(), apiCost: 1 };
}
```

**所有 controller 必须使用 `ok()` 和 `fail()` 返回，禁止直接 `res.json({...})`。**

### 3.3 错误码规范

| code | 含义 |
|------|------|
| "0" | 成功 |
| "400" | 参数错误 |
| "401" | 未认证 |
| "403" | 权限不足 |
| "404" | 资源不存在 |
| "500" | 服务器内部错误 |
| "1001" | 租户配额超限 |
| "1002" | 存储容量超限 |
| "1003" | 价格权限不足 |

## 第四章：公共工具层标准（shared/）

### 4.1 必须存在的公共工具

| 工具 | 文件 | 说明 |
|------|------|------|
| 编号生成器 | `shared/biz-no.ts` | **唯一实现**。所有单据编号必须调用此函数 |
| 追溯码生成/解析 | `shared/trace-code.ts` | **唯一实现**。生成箱码/瓶码，扫码解析 |
| 价格过滤 | `shared/price-filter.ts` | 纯函数。根据角色过滤价格字段 |
| 密码哈希 | `shared/password.ts` | bcrypt 封装 |
| 日期工具 | `shared/date-utils.ts` | 日期格式化、范围计算 |
| 订单履约分流 | `shared/fulfillment.ts` | WHOLESALE/RETAIL 状态机分流 |
| 返回格式 | `shared/response.ts` | ok/fail 统一返回 |
| 日志 | `shared/logger.ts` | pino 日志 |

### 4.2 公共工具规则（不可违反）

1. **禁止重复实现。** 同一个功能在 shared/ 中只能有一份代码。发现第二份，立即删除并统一。
2. **禁止在业务代码中内联公共逻辑。** 价格判断、编号生成、追溯码解析——业务代码中直接调用 shared/ 函数，不得手写内联逻辑。
3. **shared/ 不依赖 Express。** 公共工具是纯函数，不依赖 req/res/next。

## 第五章：业务硬性约束

### 5.1 价格隔离（不可违反）

| 角色 | 可见价格 | 规则 |
|------|------|------|
| 零售商 | 零售价 | 不可见批发价、成本价 |
| 批发商 | 批发价 | 不可见上游底价/成本价 |
| 供应商 | 供货价 | 不可见下游成交零售价 |
| 管理员 | 全部价格 | 审计日志记录每次查询 |

**中间件：** `price-guard.ts` 必须应用到**所有价格敏感路由**，包括：
- `product.route.ts` — 商品列表/详情
- `admin-order.route.ts` — 订单管理
- `store.route.ts` — 门店销售
- `miniapp.route.ts` — 小程序
- `export.route.ts` — 导出

**禁止**在服务层手写 `customerType === "WHOLESALE"` 判断价格可见性，必须调用 price-guard。

### 5.2 追溯码（不可违反）

1. 出入库**必须**自动绑定追溯码，写入 `trace_event_log`
2. 追溯码生成/解析**必须**调用 `shared/trace-code.ts`
3. 追溯码支持按商品/分类启停（总开关在 `config/permission.ts`）

### 5.3 销售中心

1. 批发和零售共用同一套单据体系（`sale_bill` 表），通过 `customer_type` 字段区分
2. 批发订单：跳过支付、ACCOUNT 结算、不锁定库存
3. 零售订单：正常支付流程、CASH/CREDIT 结算

### 5.4 数据存储

1. 每个租户配额固定 10G，超容量弹窗提醒，**禁止自动删除历史单据**
2. 结构化数据全部存入 MySQL
3. 图片/附件本地归档，不上云

### 5.5 历史单据

1. 支持归档标记（`archived` 状态），归档后不可编辑
2. 支持 CSV 导出
3. 禁止物理删除已完成单据
4. 归档逻辑统一在 `service/admin/archive.service.ts` 中

## 第六章：前端统一标准

### 6.1 项目划分

| 项目 | 技术栈 | 用户 | 负责人 | 状态 |

> 注：`app-mobile` 基于 uni-app 框架，以商家功能为主，核心差异化是销售单分享收款（客户打开链接直接付款）。移动端不做独立"门店终端"应用，不做"门店收银模式"。收款流程：商家创建销售单 → 分享给客户 → 客户打开链接点付款按钮 → 跳转微信/支付宝 → 付款后按钮状态自动更新 → 商家端同步收款状态。PC端收银台通过角色权限切换实现。

### 6.2 前端代码规范

1. **API 调用统一：** 所有接口调用通过 `api.ts` 中的方法，不在组件中直接使用 axios

3. **表单校验：** 所有提交表单必须有 `el-form` 的 `:rules` 验证规则
4. **硬编码禁止：** 密钥、Token、配置不得硬编码在前端代码中
5. **目录结构：** `src/views/` → 页面组件，`src/components/` → 公共组件，`src/api.ts` → 接口封装

### 6.3 前端依赖安全

| 禁止行为 | 说明 |
|------|------|

## 第十二章：数据库迁移规范

### 12.1 迁移文件命名

```
docs/migrations/
├── 001_初始数据库.sql
├── 002_增加追溯码表.sql
├── 003_增加品牌表.sql
├── ...
└── NNN_描述.sql
```

**规则：**
1. 格式：`NNN_中文描述.sql`（NNN 为三位数字序号，如 `001`）
2. 序号递增，不可重复
3. 描述使用中文，简洁明了

### 12.2 迁移规则（不可违反）

1. **禁止修改已执行的迁移文件。** 已执行的迁移文件是历史记录，修改会导致环境不一致。如需变更，新建一个迁移文件。
2. **禁止删除迁移文件。** 即使迁移内容有误，也不删除，而是新建一个修正迁移。
3. **迁移文件必须可重复执行。** 使用 `IF NOT EXISTS`、`IF EXISTS` 等幂等语句。
4. **迁移前必须备份。** 生产环境执行迁移前，必须备份数据库。
5. **safeExec 不支持参数化查询。** `shared/migration.ts` 中的 `safeExec(conn, sql, label)` 函数签名只接受 SQL 字符串，不接受参数数组（内部实现是 `await conn.query(sql)`，没有传第二参数）。因此：
   - 迁移 SQL 中若需要拼接值，必须自行做转义或使用字面量（迁移场景下值可控，风险较低）
   - 禁止通过字符串拼接用户输入到迁移 SQL（迁移文件本就不应该包含用户输入）
   - 业务运行时的 SQL 必须走 service 层的参数化查询（`conn.query(sql, [params])`），不要用 safeExec 做业务查询
   - safeExec 设计用途仅为迁移 DDL/DML 幂等执行，内置了 `ER_DUP_FIELDNAME`/`ER_TABLE_EXISTS_ERROR` 等可忽略错误的静默跳过逻辑

### 12.3 迁移文件格式

```sql
-- ============================================
-- 迁移编号：NNN
-- 描述：简短描述
-- 创建人：姓名
-- 日期：YYYY-MM-DD
-- ============================================

-- 正向迁移
ALTER TABLE xxx ADD COLUMN yyy VARCHAR(64) COMMENT '字段说明';

-- 如果需要回滚，注释中写明回滚语句
-- 回滚：ALTER TABLE xxx DROP COLUMN yyy;
```

## 第十三章：错误处理规范

### 13.1 错误分类

| 分类 | 错误码范围 | 说明 | 示例 |
|------|:---:|------|------|
| 成功 | 0 | 操作成功 | — |
| 参数错误 | 400 | 请求参数不合法 | 必填字段为空、格式不正确 |
| 认证错误 | 401 | 未登录或 token 失效 | token 过期、未携带 token |
| 权限错误 | 403 | 无权限访问 | 角色权限不足、价格权限不足 |
| 资源不存在 | 404 | 请求的资源不存在 | 商品不存在、订单不存在 |
| 业务错误 | 1000-1999 | 业务逻辑错误 | 库存不足(1001)、配额超限(1002)、状态不允许(1003) |
| 系统错误 | 2000-2999 | 系统级错误 | 数据库错误(2001)、外部服务错误(2002) |
| 服务器错误 | 500 | 未预期的内部错误 | 代码异常 |

### 13.2 错误处理流程

```
controller 调用 service
    ↓
service 抛出业务异常
    ↓
async-handler 捕获异常
    ↓
error-handler 统一处理
    ↓
返回统一格式 { code, msg, traceId, apiCost }
    ↓
飞书告警（P0 错误）
    ↓
错误日志持久化
```

### 13.3 错误处理规则

1. **controller 层禁止 try-catch。** 所有错误由 async-handler 自动传递到 error-handler，不要在 controller 中手动捕获。
2. **service 层抛出业务异常。** 使用 `throw new AppError(code, message)` 抛出可识别的业务错误。
3. **禁止直接 `res.status().json()`。** 错误响应统一走 `ok()`/`fail()` 或 error-handler。
4. **P0 错误必须飞书告警。** 错误码 500 和 2000-2999 范围的错误，必须触发飞书通知。

### 13.4 当前问题

当前 47 个 controller 中有 168 个 try-catch 直接 `res.status().json()` 返回错误，导致全局 errorHandler、飞书告警、错误日志持久化全部失效。需按标准整改。

## 第十八章：五道防线（开发到验收闭环保障）

> **v1.5 新增（2026-07-29）**
> **背景**：R42至R66共25轮任务，问题反复出现。根因分析确认：不是同事不努力，是项目管理体系存在5个结构性缺陷。
> **详见**：`docs/问题循环根因分析与改进方案.md`
> **效力**：以下五道防线规则凌驾于所有其他规则之上，凌舟和全体成员必须严格执行。
> **目标**：从文档开发到测试验收各环节形成闭环，确保修过的问题不会再出现。

### 18.1 防线1：任务完成验证标准（凌舟复核制）

**规则**：任何任务标记"已完成"前，必须满足以下全部条件：

1. **git验证**：`git log --oneline -1` 确认有对应 commit
2. **代码验证**：`grep` 确认目标代码已修改（具体 grep 命令写入任务验收标准）
3. **构建验证**：`npm run build` 或 `npx tsc --noEmit` 0 错误
4. **测试验证**：`npx vitest run` 全部通过（后端）/ 前端构建成功
5. **凌舟复核**：凌舟亲自执行上述 1-4 步，确认全部通过后才标记"已完成"

**禁止**：任何成员的文本报告不能作为"已完成"的依据。凌舟必须用 `git log` + `grep` 双重验证。

**任务格式中的验收标准字段**：
每个任务必须包含可执行的验证命令，如 `grep -c "xxx" file` → 预期值，凌舟据此验证任务是否真正完成。

### 18.2 防线2：API契约文档（前后端对齐制）

**规则**：所有前后端交互的 API 必须先写契约文档，再开发。

**文档位置**：`docs/API接口文档.md`

**契约格式**：
```
### POST /api/store/auth/login
- 端类型：移动端 / 工作台 / 超级后台
- 请求体：{ username: string, password: string }
- 响应：{ code: 0, data: { token: string, user: {...} } }
- 后端文件：backend/src/routes/store-auth.routes.ts
- 前端文件：app-mobile/src/api/modules/auth.ts
```

**开发流程**：
1. 阿坚先在 API接口文档.md 中定义接口（路径、请求体、响应体）
2. 前端（墨/阿澈）根据 API接口文档.md 开发，不得自行编造路径
3. 后端阿坚按 API接口文档.md 实现，不得自行改字段名
4. 任何 API 变更必须先改 API接口文档.md，再改代码

**端点隔离规则**：
- 移动端只能调用 `/api/store/*` 端点
- 工作台只能调用 `/api/admin/*` 端点
- 超级后台只能调用 `/api/platform/*` 端点

### 18.3 防线3：数据库变更管理（统一跟踪制）

**规则**：所有数据库变更必须统一管理、统一执行、统一验证。

**数据库变更清单**：
- 文件位置：`docs/数据库变更清单.md`
- 记录每个迁移脚本的：文件名、执行状态、执行日期、验证结果
- 凌舟维护此文件，每次执行迁移后更新

**迁移脚本规范**：
1. 文件名格式：`NNN_简短描述.sql`（NNN 为三位数字序号）
2. 每个脚本必须包含 `IF NOT EXISTS` / `IF EXISTS` 保护，确保可重复执行
3. 脚本末尾必须包含验证 SQL（如 `SELECT COUNT(*) FROM information_schema.tables WHERE table_name = 't_xxx'`）
4. 表名必须带 `t_` 前缀
5. 字段必须有中文 COMMENT

**服务器执行流程**：
1. 阿坚在本地编写并测试迁移脚本
2. 凌舟将命令发给用户在服务器执行
3. 用户执行后，凌舟通过 API 或命令验证表/字段是否创建成功
4. 更新 `docs/数据库变更清单.md`

### 18.4 防线4：派单前核实制度（凌舟派单制）

**规则**：凌舟在派发任何任务前，必须先核实当前代码状态。

**核实清单**：
1. `grep` 确认问题代码确实存在（而不是已修复）
2. `git log --oneline -5` 查看最近提交，确认没有其他人已修复
3. 如果任务涉及删除文件，必须先 `Read` 文件确认内容
4. 任务描述中的"问题"和"修复方向"必须基于实际代码，不能基于记忆

**执行方式**：
- 派单前在任务文件中记录核实命令的输出结果
- 例如：`核实：grep -c "order_no" dashboard.service.ts → 3（确认问题存在）`

**任务格式中的核实字段**：
每个任务必须包含凌舟派单前执行的核实命令及输出，确认问题确实存在。

### 18.5 防线5：端到端集成验收（轮次闭环制）

**规则**：每个轮次完成后，必须在真实部署环境做端到端验收。

**验收清单**：
1. **官网**（www.onepan.cn）：首页加载、导航链接、下载链接全部点击验证
2. **工作台**（admin.onepan.cn）：登录 → 仪表盘数据加载 → 侧边栏菜单跳转 → 商品列表 → 各功能页
3. **超级后台**（saas.onepan.cn）：页面加载 → 登录 → 租户管理
4. **移动端**（m.onepan.cn）：登录 → 首页数据 → 各 tab 页面
5. **API后端**（api.onepan.cn）：登录 API → 核心业务 API（dashboard/products/orders）

**验收标准**：
- 每个页面的核心功能必须实际操作一遍
- 每个 API 必须返回 200（无数据时返回空数组/零值，不返回 500）
- 浏览器控制台无 JS 错误
- 网络请求无 401/500 错误

**执行方式**：
- 凌舟在每个轮次结束后执行端到端验收
- 验收结果记录在任务文件中
- 发现的问题立即写入下一轮任务，但不标记当前轮次为"已完成"

### 18.6 任务格式（含验收标准和核实字段）

每个任务必须包含以下字段：

```
#### [编号] 简短标题
- 优先级：P0 / P1 / P2
- 负责人：阿坚 / 墨 / 阿澈
- 预计：0.5天 / 1天 / 2天
- 状态：待开始 / 进行中 / 已完成 / 阻塞
- 文件：`精确的文件路径`
- 问题：[一句话描述问题]
- 修复：[具体修复方向]
- 验收标准：[具体的 grep 命令 + 预期输出，或构建/测试通过条件]
- 核实：[凌舟派单前执行的核实命令及输出，确认问题确实存在]
```

**字段说明**：
- **验收标准**（对应防线1）：必须包含可执行的验证命令，凌舟据此验证任务是否真正完成
- **核实**（对应防线4）：凌舟派单前必须执行核实命令并记录输出，确认问题代码确实存在、未被其他人修复

| 每次踩坑后 | 在「核心技术沉淀」中记录坑和教训 |
| 每次必读文件清单变化时 | 同步更新记忆文件中的「必读文件清单」 |
| 发现新的未解决问题时 | 在「当前关注的问题」中记录 |
| 问题彻底解决后 | 从「当前关注的问题」中删除 |

### 20.4 「当前关注的问题」章节规则

此章节是记忆文件中最重要的动态内容：

- **记录什么**：当前未解决的系统性问题、正在进行的改进方案、需要持续关注的风险点
- **不记录什么**：已解决的 Bug、已完成的任务（这些放在「历史任务总览」中）
- **格式**：
  ```
  ### [问题编号] 问题标题
  - 状态：关注中 / 处理中 / 等待验证
  - 关联文档：`docs/xxx.md`
  - 关联任务：R67-xx
  - 摘要：[一句话描述问题和当前进展]
  ```
- **当前需要记录的问题**：
  - 问题循环根因——五道防线改进方案（关联 `docs/问题循环根因分析与改进方案.md`，R67 全部完成且端到端验收通过后删除）

### 20.5 执行纪律

- **每位成员**：任务完成后如果不更新记忆文件，等同于任务未完成
- **凌舟**：审查成员提交时，检查记忆文件是否同步更新；未更新的要求补更
- **新任务开始前**：必须先读自己的记忆文件，再读必读文件清单中的所有文件

### 20.6 迁移后恢复上下文流程

每次新任务开始前，按以下顺序恢复完整上下文：

1. **拉取最新代码** — `git pull origin main`
2. **读自己的记忆文件** — 快速回忆职责、历史、技术沉淀、当前关注的问题
3. **读必读文件清单中的全部文件** — 按 `docs/tasks/current-tasks.md` 顶部「必读文件清单」逐一阅读
4. **读任务文件** — `docs/tasks/current-tasks.md`，找到自己的任务
5. **读最新代码** — 确认当前状态，避免基于记忆写代码
6. **执行任务** — 按标准和规范执行，随时对照自查清单
7. **完成后更新记忆文件** — 补充新任务、新踩坑、新技术沉淀、更新当前关注的问题
