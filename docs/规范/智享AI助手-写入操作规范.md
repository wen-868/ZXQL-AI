## 一、核心原则

> **租户说意图 → AI补全规则 → 生成预览 → 用户确认 → 执行完成**

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 租户提供  │───▶│ AI 智能   │───▶│ 生成预览  │───▶│ 用户确认  │───▶│ 执行完成  │
│ 核心信息  │    │ 补全规则  │    │ 完整单据  │    │ 最终授权  │    │ 写入系统  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
   用户只需        AI自动填充       用户看到         用户确认        数据写入
   说清意图        业务规则         完整结果         才真正执行      数据库
```

| 原则 | 说明 |
|------|------|
| **单据格式遵循系统规范** | AI创建的单据与用户在Web端手动创建的单据**完全一致**——同一张表、同样字段、同样校验规则。AI只是输入方式不同，不走特殊通道 |
| **用户最小输入** | 用户只需说清意图和核心要素（谁、什么、多少），其余AI根据系统规则自动补全 |
| **AI智能补全** | AI根据客户类型、商品属性、业务规则自动填充价格、折扣等，补全逻辑与系统Web端表单的默认值逻辑一致 |
| **先预览后执行** | 所有写操作先展示完整单据预览，用户确认后才真正写入 |
| **确认即授权** | 用户说"确认"、"可以"、"没问题"才执行，其他回复视为拒绝 |
| **可撤销** | 执行后3分钟内可撤销（仅限未发货状态） |

## 二、写入操作通用流程

### 2.1 标准流程（6步）

```
用户输入（模糊/口语化）
  │
  ▼
Step 1: 意图识别
  │ AI 判断用户想做什么操作（创建/修改/删除？哪个业务域？）
  │
  ▼
Step 2: 信息提取
  │ 提取用户已提供的信息：客户名、商品名、数量、价格（如有）
  │ 标记缺失的关键信息
  │
  ▼
Step 3: 智能补全（关键！）
  │ 查询系统补全：
  │   ├─ 客户信息：客户ID、客户类型、专属价格等级、地址、联系方式
  │   ├─ 商品信息：商品ID、规格、库存、多条价格（零售价/批发价/会员价）
  │   ├─ 价格匹配：根据客户类型自动选择价格
  │   ├─ 库存校验：是否满足需求
  │   └─ 业务规则：最低限价、信用额度、账期
  │
  ▼
Step 4: 信息确认（有缺失则追问）
  │ 如果信息不完整或模糊 → 追问用户
  │ 如果信息完整 → 进入预览
  │
  ▼
Step 5: 预览展示
  │ 以结构化卡片展示完整单据内容
  │ 显示所有AI自动填充的字段（让用户清楚AI做了什么）
  │ 明确提示"请确认后执行"
  │
  ▼
Step 6: 用户确认 → 执行
  │ 用户确认 → 调用后端API写入 → 返回结果
  │ 用户拒绝 → 取消操作
  │ 用户修改 → 回到Step 4重新补全
```

### 2.2 AI 自动补全字段清单

| 字段 | 来源 | 补全规则 |
|------|------|----------|
| 客户ID | 后端客户服务 | 根据客户名称模糊匹配 |
| 客户类型 | 后端客户服务 | 零售/批发/VIP，决定价格等级 |
| 客户地址 | 后端客户服务 | 自动填充配送地址 |
| 商品ID | 后端商品服务 | 根据商品名称模糊匹配 |
| 商品规格 | 后端商品服务 | 自动填充（52度500ml） |
| **销售单价** | 后端商品服务 + 后端客户服务 | **根据客户类型自动匹配**（见第三章） |
| 库存可用量 | 后端库存服务 | 校验是否满足订单数量 |

## 三、智能价格填充规则

### 3.1 价格优先级

```
客户类型 → 决定价格等级 → 匹配商品价格

┌──────────────┬──────────────────┬───────────────────────────┐
│ 客户类型      │ 价格字段          │ 使用规则                   │
├──────────────┼──────────────────┼───────────────────────────┤
│ 批发客户      │ wholesale_price  │ 优先使用批发价              │
│ 零售客户      │ retail_price     │ 使用零售价                  │
│ VIP客户       │ vip_price        │ 使用VIP价（通常低于零售）    │
│ 未分类/新客户  │ retail_price     │ 默认零售价                  │
│ 有合同价的客户 │ contract_price   │ 使用合同约定价（最高优先级）  │
└──────────────┴──────────────────┴───────────────────────────┘
```

### 3.2 价格填充流程

```
用户说: "给红星商行送10箱五粮液"  ← 没提价格
  │
  ├─ 1. 查客户: 红星商行 → 客户类型=批发客户
  ├─ 2. 查商品: 五粮液 → 零售价¥1,200, 批发价¥980, VIP价¥1,050
  ├─ 3. 匹配: 批发客户 → 自动选用批发价¥980
  ├─ 4. 备注: "已自动应用批发客户价格（批发价¥980/件）"
  └─ 5. 预览中明确标注价格来源

用户说: "给光明超市五粮液20件，按1100算"  ← 明确指定价格
  │
  ├─ 1. 查客户: 光明超市 → 零售客户
  ├─ 2. 查商品: 五粮液 → 零售价¥1,200
  ├─ 3. 用户指定¥1,100 → 使用用户指定价（但需校验不低于最低限价）
  └─ 4. 预览标注: "用户指定价¥1,100（零售参考价¥1,200）"
```

### 3.3 价格安全校验

| 校验项 | 规则 | 处理 |
|--------|------|------|
| 低于进货价 | 售价 < 采购价(purchase_price) | ⚠️ **提示警告，不阻止执行**。实际业务中存在亏钱出货的情况，AI只提醒不拦截 |
| 低于最低限价 | 售价 < min_price | ⚠️ **提示警告，不阻止执行**。由用户决定是否继续 |
| 价格偏差 | 售价低于默认价20%以上 | 提醒用户确认 |
| 零价格 | 售价=0 | 阻止执行（金额不能为0） |
| 价格缺失 | 商品没有对应客户类型的价格 | 追问用户输入价格 |

**低于进货价的提示示例**：

```
⚠️ 价格提醒

五粮液52度500ml 的采购价为 ¥141.67/瓶，本次售价 ¥130.00/瓶，
低于进货价 ¥11.67/瓶，本单预计亏损 ¥700.20。

确认是否以亏损价格出货？
[确认出货] [修改价格] [取消]

ℹ️ 实际业务中可能存在清库存、客户维护等亏钱出货场景，此提醒仅供参考。
```

**关键原则**：AI只做提示，不做拦截。是否亏钱出货由用户决定。

## 四、单位换算与金额计算

> **核心规则：单价永远以最小单位（瓶）为基准。用户说"箱"只换算数量，单价始终是瓶单价。**

### 4.1 单位体系

每个商品在系统中有以下单位定义：

| 字段 | 说明 | 示例（五粮液） |
|------|------|---------------|
| `min_unit` | 最小单位（计价单位） | 瓶 |
| `box_unit` | 包装单位 | 箱 |
| `box_ratio` | 换算比（1箱 = N瓶） | 6 |
| `retail_price` | 零售价（每瓶） | ¥200.00/瓶 |
| `wholesale_price` | 批发价（每瓶） | ¥163.33/瓶 |
| `purchase_price` | 采购价（每瓶） | ¥141.67/瓶 |

> **所有价格字段在数据库中均按最小单位（瓶）存储，不存在"每箱价格"这个字段。**

### 4.2 换算规则

```
规则: 单价 = 瓶单价（不换算）
      数量 = 用户说的数量 × 换算比（换算为瓶）
      金额 = 瓶数量 × 瓶单价

用户说"100箱"  →  数量换算: 100 × 6 = 600瓶  →  600 × 瓶单价
用户说"50瓶"   →  数量不换算: 50瓶            →  50 × 瓶单价
用户说"20件"   →  查box_ratio换算: 20 × 6 = 120瓶  →  120 × 瓶单价
```

### 4.3 完整示例

#### 采购场景

```
用户: "从XX酒业进货100箱五粮液，进价850"

Step 1: 查商品
  → 五粮液: min_unit=瓶, box_unit=箱, box_ratio=6
  → purchase_price = ¥141.67/瓶（系统默认采购价）

Step 2: 用户说"进价850"
  → 850就是瓶单价，不换算
  → 单价 = ¥850.00/瓶

Step 3: 数量换算
  → 100箱 × 6瓶/箱 = 600瓶

Step 4: 金额计算
  → 600瓶 × ¥850.00/瓶 = ¥510,000.00

Step 5: 预览
  📋 采购单预览
  ┌─────────────────────────────────────────────┐
  │ 供应商    XX酒业                              │
  │ 商品      五粮液52度500ml                     │
  │ 数量      100箱（= 600瓶）                    │
  │ 换算比    1箱 = 6瓶                           │
  │ 单价      ¥850.00/瓶                          │
  │ 合计      600瓶 × ¥850.00 = ¥510,000.00      │
  │                                             │
  │ ℹ️ 单价以最小单位(瓶)核算                     │
  └─────────────────────────────────────────────┘
```


### 4.4 用户指定价格的解析

**单价始终是瓶单价，无论用户说的数量单位是什么：**

| 用户说法 | AI解析 | 计算 |
|----------|--------|------|
| "进价850" | ¥850/瓶 | 不换算，直接用 |
| "进价850，100箱" | ¥850/瓶 | 100×6=600瓶，600×850=¥510,000 |
| "每瓶850" | ¥850/瓶 | 同上 |
| "批发价163" | ¥163/瓶 | 不换算，直接用 |

**判断逻辑**：

```
用户说了价格数字（如"850"）:
  │
  └─ 这个数字就是瓶单价，直接使用，不做任何换算
     850 → ¥850.00/瓶

用户没说价格:
  │
  └─ 根据客户类型自动匹配系统中的瓶单价
     批发客户 → wholesale_price（瓶）
     零售客户 → retail_price（瓶）
```

### 4.5 数据库中的单位存储

```sql
-- 商品表中与单位相关的字段（现有表，不新增）
-- t_product_spu 表:
--   min_unit        VARCHAR(16)  -- 最小单位: 瓶
--   box_unit        VARCHAR(16)  -- 包装单位: 箱
--   box_ratio       INT          -- 换算比: 6（1箱=6瓶）
--   retail_price    DECIMAL      -- 零售价（每瓶）
--   wholesale_price DECIMAL      -- 批发价（每瓶）
--   purchase_price  DECIMAL      -- 采购价（每瓶）
--   min_price       DECIMAL      -- 最低限价（每瓶）

-- 单据明细表中的存储（现有表，不新增）:
-- t_sale_bill_item 表:
--   product_id      -- 商品ID
--   quantity        -- 数量（用户输入的原始值，如100）
--   unit            -- 单位（用户说的单位，如"箱"）
--   min_quantity    -- 最小单位数量（换算后，如600）
--   unit_price      -- 单价（瓶单价，如850.00）
--   total_amount    -- 合计金额（min_quantity × unit_price = 600 × 850 = 510000）
```

> **注意**：以上字段名以实际数据库表结构为准，AI开发时需对照 `docs/数据库变更清单.md` 和 `init_database.sql` 确认字段名。

### 4.6 换算校验规则

| 校验项 | 规则 | 不通过时 |
|--------|------|----------|
| 换算比存在 | 商品必须有 box_ratio | "该商品未配置箱瓶换算比，请先在商品管理中设置" |
| 换算整除 | 数量×换算比必须为整数 | "100箱×6=600瓶 ✅" / "10箱×7=70瓶 ✅" |
| 单价不为零 | 换算后单价 > 0 | "单价计算异常，请检查" |
| 低于进货价 | 售价 < purchase_price | ⚠️ 提示警告，不阻止执行 |
| 低于限价 | 售价 < min_price | ⚠️ 提示警告，不阻止执行 |

## 六、确认机制设计

### 6.1 确认级别

| 级别 | 适用场景 | 确认方式 | 示例 |
|------|----------|----------|------|
| 🟢 轻量确认 | 低风险查询操作 | 无需确认，直接返回 | "查一下库存" |
| 🟡 标准确认 | 常规写操作 | 预览卡片 + 确认按钮 | 创建销售单、采购单 |
| 🔴 重要确认 | 不可逆操作 | 预览卡片 + 明确确认词 + 撤销期 | 取消订单、删除数据 |

### 6.2 用户确认词

```
用户可以说以下任意词汇表示确认：
  "确认"  "可以"  "好的"  "没问题"  "行"  "对"  "是的"  "执行"  "开单"

用户说以下内容视为拒绝/需要修改：
  "等等"  "不对"  "改一下"  "不是这个"  "取消"  "算了"
  
用户直接提出新意图视为放弃当前操作：
  "算了，帮我查一下库存" → 放弃创建销售单，改为查库存
```

### 6.3 撤销期

```
操作完成后3分钟内，用户可以说:
  "撤销刚才的单子"
  "撤回SO20260730001"
```

## 七、安全规则

### 7.1 写操作前置校验

| 校验项 | 规则 | 不通过时的处理 |
|--------|------|---------------|
| 客户存在 | 客户必须在系统中存在 | "未找到该客户，是否创建新客户？" |
| 商品存在 | 商品必须在系统中存在 | "未找到该商品，请确认商品名称" |

| 操作权限 | 用户角色有对应写权限 | "您没有创建销售单的权限" |

### 7.2 批量操作限制

### 9.2 数据库设计

```sql
-- ============================================
-- AI用量统计表（按租户按日汇总）
-- ============================================
CREATE TABLE ai_usage_daily (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id     VARCHAR(32) NOT NULL,
  stat_date     DATE NOT NULL,
  
  -- 调用统计
  chat_count        INT DEFAULT 0,    -- 对话次数
  tool_call_count   INT DEFAULT 0,    -- 工具调用次数
  rag_query_count   INT DEFAULT 0,    -- 知识检索次数
  
  -- Token统计
  prompt_tokens     BIGINT DEFAULT 0, -- 输入Token
  completion_tokens BIGINT DEFAULT 0, -- 输出Token
  total_tokens      BIGINT DEFAULT 0, -- 总Token
  
  -- 费用统计（元，保留4位小数）
  prompt_cost       DECIMAL(12,4) DEFAULT 0.0000,
  completion_cost   DECIMAL(12,4) DEFAULT 0.0000,
  total_cost        DECIMAL(12,4) DEFAULT 0.0000,

  model             VARCHAR(64),
```

### 9.3 数据采集流程

```
每次AI调用 → 实时写入 ai_audit_log（明细）
                    │
                    ▼
         定时任务（每小时） → 按 tenant_id + stat_date + provider 汇总
                    │
                    ▼
         写入 ai_usage_daily（汇总）
                    │
                    ▼
         总台读取 → 展示统计报表 → 生成账单
```

**采集时机**：

```
AI调用发生:
  │
  ├─ 即时: 写入 ai_audit_log（包含每条对话的完整记录）
  │
  └─ 每小时汇总: 
       SELECT tenant_id, DATE(created_at), provider,
              COUNT(*),
              SUM(prompt_tokens), SUM(completion_tokens)
       FROM ai_audit_log
       WHERE created_at >= last_run
       GROUP BY tenant_id, DATE(created_at), provider
       → UPSERT INTO ai_usage_daily
```

**费用计算**：

```typescript
// 费用计算逻辑

function calculateCost(usage: {
  promptTokens: number;
  completionTokens: number;
  provider: string;
}): { promptCost: number; completionCost: number; totalCost: number } {
  
  // 各服务商价格（元/千Token）
  const PRICING: Record<string, { prompt: number; completion: number }> = {
    deepseek:  { prompt: 0.001,  completion: 0.002  },
    qwen:      { prompt: 0.002,  completion: 0.006  },
    zhipu:     { prompt: 0.000,  completion: 0.000  },  // 免费额度
    ollama:    { prompt: 0,      completion: 0      },  // 本地免费
  };

  const price = PRICING[usage.provider] || PRICING.deepseek;
  
  const promptCost = (usage.promptTokens / 1000) * price.prompt;
  const completionCost = (usage.completionTokens / 1000) * price.completion;
  
  return {
    promptCost: Math.round(promptCost * 10000) / 10000,
    completionCost: Math.round(completionCost * 10000) / 10000,
    totalCost: Math.round((promptCost + completionCost) * 10000) / 10000,
  };
}
```

### 9.6 计费策略

| 计费模式 | 说明 | 适用场景 |
|----------|------|----------|
| **免费额度** | 每月免费100次对话 **或** 10万Token（OR逻辑，任一超出即计费） | 试用期租户 |
| **按量计费** | 超出免费额度后按 ¥0.001/千Token | 中小租户 |
| **预付费余额** | 租户预先充值，实时扣减，余额不足暂停AI服务 | 主推模式 |
| **月套餐** | 固定月费，含套餐内额度，超出部分按量计费 | 大租户 |
| **自定义** | 可单独配置单价、免费额度和套餐额度 | 特殊客户 |

**免费额度判定规则（OR逻辑）**：

```
每月1日00:00重置免费额度计数器

判定流程：
  当月累计对话数 > 100 ？
       OR
  当月累计Token > 100,000 ？
       │
       ├─ 否 → 本次调用免费，不扣费
       │
       └─ 是 → 本次调用按超额单价计费
              计费范围 = 超出阈值后的全部调用（非仅超出部分）

举例：
  租户A本月第95次对话，累计Token 98,000 → 免费额度内
  租户A本月第101次对话，累计Token 102,000 → 触发计费
    · 第101次起每次调用按 ¥0.001/千Token 计费
    · Token和次数两项指标中先触发的为准
```

**预付费余额模型**：

```
预付费扣费流程：

  租户充值 ¥100 → balance = 100.00
       │
       ▼
  每次AI调用 → 实时计算费用 → 从 balance 扣减
       │
       ├─ balance > 预警阈值（¥10）→ 正常服务
       │
       ├─ balance ≤ 预警阈值 → 服务正常 + 推送充值提醒
       │
       └─ balance ≤ 0 → 暂停AI服务（保留只读查询能力）
                     充值后自动恢复

扣费公式：
  本次费用 = (prompt_tokens / 1000 × 输入单价)
           + (completion_tokens / 1000 × 输出单价)
  balance -= 本次费用（事务扣减，保证原子性）
```

**费用归属**：

```
总台视角:

租户AI费用 = 租户实际消耗Token费用 + 平台服务费

┌─────────────────────────────────────────────────┐
│                                                 │
│  DeepSeek收费: ¥0.001/千Token（AI服务商）       │
│  ↓                                              │
│  总台向租户收费: ¥0.002/千Token（含平台服务费）  │
│  ↓                                              │
│  平台毛利: ¥0.001/千Token                        │
│                                                 │
└─────────────────────────────────────────────────┘

即: 租户看到的价格 = 服务商成本价 × 2（可配置倍数）
```

### 9.7 账单周期与月度账单

**账单周期定义**：

| 项目 | 规则 |
|------|------|
| 周期单位 | 自然月（每月1日00:00 至 月末23:59:59） |
| 免费额度重置 | 每月1日00:00重置，未使用额度不结转 |
| 出账时间 | 次月1日 02:00 自动生成上月账单 |
| 结算时间 | 次月1日 02:30 预付费用户自动从余额扣款 |
| 逾期处理 | 后付费用户次月5日内未付 → 状态置为 overdue，暂停AI服务 |
| 跨月调用 | 以 `created_at` 所在自然月归属，不拆分 |

```
账单生成定时任务（每月1日 02:00 执行）：

  对每个租户：
    1. 汇总上月 ai_usage_daily → 写入 ai_monthly_bill
    2. 计算免费额度抵扣
    3. 计算应付金额
    4. 预付费用户 → 从 tenant_ai_balance 扣款 → status=settled
    5. 后付费用户 → status=pending，等待付款
```
