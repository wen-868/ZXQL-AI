## 〇、硬性规定（2026-08-16 用户指令，最高优先级，强制执行）

> 适用范围：任何成员，包括所有 AI 代理、子代理、运营人员、管理系统所有成员，无一例外。

1. **任务前必读**：任何成员做任务前必须读取本文件（`docs/项目规则.md`）与 `docs/项目统一标准.md`，并按 `docs/tasks/current-tasks.md` 顶部必读文件清单逐一阅读。未读取不得开工。
2. **禁止私自修改**：没有问题的地方禁止私自修改，只允许修改有问题的地方。禁止顺手重构、禁止扩大改动范围、禁止改动与任务无关的代码和文档。
3. **修改需有依据**：任何修改必须能说明"哪里有问题、改了什么、为什么"；对任务理解不确定时，先向凌舟确认，不允许凭猜测动手。
4. **违规处理**：违反本规定的提交一律打回返工；验收时发现与任务无关的改动，一律视为违规。

### 2.1 任务分配与责任到人规则（2026-08-06 新增，最高优先级）

> **背景**：项目要高质量推进，必须先立规矩。任何人（含凌舟）不得盲目做事、不得越权代做、不得让任务无人认领。

1. **任务必须分配**：所有任务由凌舟统一规划分派，每个任务必须有明确的「负责人」字段。禁止无主任务；禁止成员自行认领不属于自己职责的任务。
2. **各司其职**：成员只执行上表职责范围内的任务。跨职责需求由凌舟协调后再分派，成员不得越界代做他人职责（例如前端不得擅改后端、测试不得代写业务代码）。
3. **责任可追溯**：每个模块、页面、接口、文档都有归属负责人。哪里出问题，凌舟直接派对应负责人定位修复；修复结果按五道防线验收，责任到人、闭环到底。
4. **禁止盲目做事**：执行前必须先读完必读文件清单与自己的任务卡，明确验收标准；对任务理解不确定时，先向凌舟确认，不允许凭猜测动手。
5. **凌舟职责边界**：凌舟负责规划、分派、审计、验收与工作文件维护，不越权代写业务代码；仅在用户明确授权时（如 UI 打磨轮次）直接执行。

### 2.2 工作纪律（2026-08-06 用户要求，全员遵守）

1. **最小改动**：修改文件只能修改有 bug 的地方，没有问题的地方不允许动；不顺手重构、不扩大改动范围。
2. **先讨论再执行**：执行任务前必须先与凌舟/需求方讨论清楚，直到真正理解问题、范围与验收标准后才能开始。
3. **节约资源**：阅读大文档只精读相关章节，不全文展开；执行前先出计划，按计划推进，不盲目消耗资源。
4. **任务文件必读**：`docs/tasks/current-tasks.md` 顶部必读文件清单每次任务前必须逐一阅读，未读不得开工。
5. **总负责人制**：凌舟是项目总负责人，负责整体规划与最终把关；团队执行结果由凌舟独立验证后认定。

## 四、任务文件规则（最重要）

### 1. 只有一个任务文件

- 路径：`docs/tasks/current-tasks.md`
- 这是唯一合法位置，唯一的任务文件
- 所有团队成员读取这一个文件获取任务

### 2. 禁止多人多文件

- 不再创建 ajian-tasks-*.md、mo-tasks-*.md、ache-tasks-*.md 等独立文件
- 不再创建 task-plan-*.md、task-breakdown-*.md 等分解文件
- 所有任务集中在 current-tasks.md 一个文件中

### 3. 轮次编号

- 每次凌舟分派任务为一个轮次，格式：R1、R2、R3...
- 轮次信息包含：日期、来源、状态
- 示例：`### R1 — 2026-07-02 合并后问题修复 [已完成]`

### 4. 任务格式（固定，不可变）

每个任务必须包含以下字段：

```
#### [编号] 简短标题
- 优先级：P0 / P1 / P2
- 负责人：阿坚 / 墨 / 阿澈
- 预计：0.5天 / 1天 / 2天
- 状态：待开始 / 进行中 / 已完成 / 阻塞
- 文件：`精确的文件路径`
- 问题：[一句话描述问题]
- 修复：[具体修复方向]
- 验收标准：[具体的 grep 命令 + 预期输出，或构建/测试通过条件]
- 核实：[凌舟派单前执行的核实命令及输出，确认问题确实存在]
```

**字段说明**：
- **验收标准**（对应防线1）：必须包含可执行的验证命令（如 `grep -c "xxx" file` → 预期值），凌舟据此验证任务是否真正完成
- **核实**（对应防线4）：凌舟派单前必须执行核实命令并记录输出，确认问题代码确实存在、未被其他人修复

### 5. 测试报告规则

- 测试报告统一放在 `docs/reports/` 目录
- 格式：`docs/reports/test-report-YYYY-MM-DD.md`
- 凌舟收到报告后，提取问题写入 current-tasks.md 对应轮次

## 十一、凌舟工作流程

收到新任务/反馈时：

1. 先读 `docs/踩坑日志.md`
2. 先读 `docs/tasks/current-tasks.md` 顶部的「必读文件清单」，逐一阅读所有必读文件
3. 排查问题 → 定位根因 → 确认负责人
4. 在 `current-tasks.md` 中新增轮次，按固定格式写入任务
5. 如果本轮创建了新的分析文档或重要文档，将其加入 `current-tasks.md` 顶部的「必读文件清单」（详见第十三章）
6. 提交推送，通知相关成员
7. 成员提交后，合并审查，更新任务状态
8. 将新发现的坑写入 `docs/踩坑日志.md`
9. 每轮结束后，删除所有远程/本地分支，保持只有 main
10. 问题彻底解决后，将对应的必读文件从「必读文件清单」中移出

## 十二、五道防线（2026-07-29 新增 — 最高优先级）

> **背景**：R42至R66共25轮任务，问题反复出现。根因分析确认：不是同事不努力，是项目管理体系存在5个结构性缺陷。
> **详见**：`docs/问题循环根因分析与改进方案.md`
> **效力**：以下五道防线规则凌驾于所有其他规则之上，凌舟和全体成员必须严格执行。

### 防线1：任务完成验证标准（凌舟复核制）

**规则**：任何任务标记"已完成"前，必须满足以下全部条件：

1. **git验证**：`git log --oneline -1` 确认有对应 commit
2. **代码验证**：`grep` 确认目标代码已修改（具体 grep 命令写入任务验收标准）
3. **构建验证**：`npm run build` 或 `npx tsc --noEmit` 0 错误
4. **测试验证**：`npx vitest run` 全部通过（后端）/ 前端构建成功
5. **凌舟复核**：凌舟亲自执行上述 1-4 步，确认全部通过后才标记"已完成"

**禁止**：任何成员的文本报告不能作为"已完成"的依据。凌舟必须用 `git log` + `grep` 双重验证。

### 防线2：API契约文档（前后端对齐制）

**规则**：所有前后端交互的 API 必须先写契约文档，再开发。

**文档位置**：`docs/API接口文档.md`

**契约格式**：
```
### POST /api/store/auth/login
- 端类型：移动端 / 工作台 / 超级后台
- 请求体：{ username: string, password: string }
- 响应：{ code: 0, data: { token: string, user: {...} } }
- 后端文件：backend/src/routes/store-auth.routes.ts
- 前端文件：app-mobile/src/api/modules/auth.ts
```

**开发流程**：
1. 阿坚先在 API.md 中定义接口（路径、请求体、响应体）
2. 前端（墨/阿澈）根据 API.md 开发，不得自行编造路径
3. 后端阿坚按 API.md 实现，不得自行改字段名
4. 任何 API 变更必须先改 API.md，再改代码

**端点隔离规则**：
- 移动端只能调用 `/api/store/*` 端点
- 工作台只能调用 `/api/admin/*` 端点
- 超级后台只能调用 `/api/platform/*` 端点

### 防线3：数据库变更管理（统一跟踪制）

**规则**：所有数据库变更必须统一管理、统一执行、统一验证。

**数据库变更清单**：
- 文件位置：`docs/数据库变更清单.md`
- 记录每个迁移脚本的：文件名、执行状态、执行日期、验证结果
- 凌舟维护此文件，每次执行迁移后更新

**迁移脚本规范**：
1. 文件名格式：`NNN_简短描述.sql`（NNN 为三位数字序号）
2. 每个脚本必须包含 `IF NOT EXISTS` / `IF EXISTS` 保护，确保可重复执行
3. 脚本末尾必须包含验证 SQL（如 `SELECT COUNT(*) FROM information_schema.tables WHERE table_name = 't_xxx'`）
4. 表名必须带 `t_` 前缀
5. 字段必须有中文 COMMENT

**服务器执行流程**：
1. 阿坚在本地编写并测试迁移脚本
2. 凌舟将命令发给用户在服务器执行
3. 用户执行后，凌舟通过 API 或命令验证表/字段是否创建成功
4. 更新 `docs/数据库变更清单.md`

### 防线4：派单前核实制度（凌舟派单制）

**规则**：凌舟在派发任何任务前，必须先核实当前代码状态。

**核实清单**：
1. `grep` 确认问题代码确实存在（而不是已修复）
2. `git log --oneline -5` 查看最近提交，确认没有其他人已修复
3. 如果任务涉及删除文件，必须先 `Read` 文件确认内容
4. 任务描述中的"问题"和"修复方向"必须基于实际代码，不能基于记忆

**执行方式**：
- 派单前在任务文件中记录核实命令的输出结果
- 例如：`核实：grep -c "order_no" dashboard.service.ts → 3（确认问题存在）`



> **自检表引用**：派单前必须逐一勾选 docs/verify-five-defense.md 节点A的6项检查，未勾选不得派单。节点B（任务完成提交前5项）、节点C（端到端验收前4项）同理必查。完整命令清单详见 `docs/verify-five-defense.md`。

### 防线5：端到端集成验收（轮次闭环制）

**规则**：每个轮次完成后，必须在真实部署环境做端到端验收。

**验收清单**：
1. **官网**（www.onepan.cn）：首页加载、导航链接、下载链接全部点击验证
2. **工作台**（admin.onepan.cn）：登录 → 仪表盘数据加载 → 侧边栏菜单跳转 → 商品列表 → 各功能页
3. **超级后台**（saas.onepan.cn）：页面加载 → 登录 → 租户管理
4. **移动端**（m.onepan.cn）：登录 → 首页数据 → 各 tab 页面
5. **API后端**（api.onepan.cn）：登录 API → 核心业务 API（dashboard/products/orders）

**验收标准**：
- 每个页面的核心功能必须实际操作一遍
- 每个 API 必须返回 200（无数据时返回空数组/零值，不返回 500）
- 浏览器控制台无 JS 错误
- 网络请求无 401/500 错误

**执行方式**：
- 凌舟在每个轮次结束后执行端到端验收
- 验收结果记录在任务文件中
- 发现的问题立即写入下一轮任务，但不标记当前轮次为"已完成"

## 十三、必读文件管理规则（2026-07-29 新增 — 最高优先级）

> **背景**：随着轮次增多，任务文件越来越长，早期的必读要求被淹没。团队成员如果不读关键文档就开工，根本不知道有哪些问题需要解决、有哪些规则需要遵守。
> **核心原则**：任务文件的**最顶部**必须始终维护一份「必读文件清单」，凌舟每次更新任务文件时同步更新此清单。

### 1. 必读文件清单的位置

- **唯一位置**：`docs/tasks/current-tasks.md` 文件的**最顶部**（在所有轮次内容之前）
- 每次更新任务文件时，凌舟必须同步检查并更新必读文件清单
- 禁止将必读文件清单放在任务文件的其他位置

### 2. 必读文件分类

#### 永久必读（长期有效，不移出）

| 序号 | 文件 | 原因 |
|:----:|------|------|
| 1 | `docs/项目统一标准.md` | 项目统一执行标准（v1.5），涵盖文档开发到测试验收各环节闭环，包括代码使用标准 |
| 2 | `docs/项目规则.md` | 项目全部规则的唯一权威来源，含五道防线 |
| 3 | `docs/tasks/current-tasks.md` | 唯一任务文件，含必读文件清单 + 当前轮次任务 |
| 4 | `docs/踩坑日志.md` | 避免重复踩坑，每次任务前必读 |
| 5 | `docs/API接口文档.md` | API 契约文档，前后端对齐的唯一真相源 |
| 6 | `docs/数据库变更清单.md` | 数据库变更清单，确认表是否存在 |
| 7 | 各成员自己的记忆文件 `docs/memories/姓名-记忆.md` | 恢复上下文，避免遗忘（详见第十四章） |

#### 临时必读（问题解决后移出）

- 当凌舟创建了新的问题分析文档、改进方案文档时，该文档立即加入临时必读清单
- **移出条件**：文档中描述的问题**彻底解决**并经凌舟验证确认后，才可从必读清单移出
- **移出流程**：凌舟在任务文件中标注移出原因和日期，然后将该文件从必读清单删除
- **当前临时必读文件**：

| 序号 | 文件 | 加入日期 | 移出条件 |
|:----:|------|----------|----------|
| T1 | `docs/问题循环根因分析与改进方案.md` | 2026-07-29 | 五道防线全部落地 + R67 全部完成 + 端到端验收通过 |

### 3. 必读文件清单格式（写入 current-tasks.md 顶部）

```markdown
## 必读文件清单（每次任务前必须逐一阅读）

### 永久必读
1. `docs/项目统一标准.md` — 项目统一执行标准（v1.5），涵盖文档开发到测试验收各环节闭环
2. `docs/项目规则.md` — 项目全部规则（含五道防线第十二章）
3. `docs/tasks/current-tasks.md` — 本文件（含必读清单 + 当前轮次任务）
4. `docs/踩坑日志.md` — 避免重复踩坑
5. `docs/API接口文档.md` — API 契约文档
6. `docs/数据库变更清单.md` — 数据库变更清单
7. `docs/memories/姓名-记忆.md` — 你的个人记忆文件

### 临时必读（问题解决后移出）
- [T1] `docs/问题循环根因分析与改进方案.md` — 五道防线改进方案（移出条件：R67全部完成 + 端到端验收通过）
```

### 4. 执行纪律

- **凌舟**：每次更新任务文件时，必须同步更新必读文件清单；创建新文档时立即加入清单
- **全体成员**：每次开始任务前，必须逐一阅读所有必读文件；未读必读文件的成员不得开始任务
- **验收标准**：凌舟在审查提交时，可通过提交信息或代码内容判断成员是否已读必读文件

## 十四、记忆文件管理规则（2026-07-29 新增 — 最高优先级）

> **背景**：团队成员跨任务执行时容易遗忘上下文——前面做的事后面就忘了。个人记忆文件是恢复上下文的唯一手段，必须严格维护。
> **核心原则**：每位成员在 `docs/memories/` 目录下维护一份个人记忆文件，每次任务完成后必须更新。

### 1. 记忆文件位置与命名

- **目录**：`docs/memories/`
- **命名格式**：`姓名-记忆.md`（如 `阿澈-记忆.md`、`阿坚-记忆.md`、`墨-记忆.md`）
- **禁止**：在项目根目录或 `docs/` 根目录创建 `MEMORY.md`、`WORKING-MEMORY.md` 等通用记忆文件

### 2. 记忆文件内容结构

每个记忆文件必须包含以下章节：

```
# 姓名 · 完整记忆

> 创建时间：YYYY-MM-DD
> 最后更新：YYYY-MM-DD
> 职责：[成员职责]
> 技术栈：[成员技术栈]

## 一、个人职责与定位
## 二、历史任务总览（按轮次记录）
## 三、核心技术沉淀
## 四、提交前自查清单
## 五、必读文件清单（与 current-tasks.md 顶部同步）
## 六、当前关注的问题（未解决的问题才记，解决了就删除）
## 七、迁移后恢复上下文（操作步骤）
```

### 3. 更新时机（必须严格执行）

| 时机 | 操作 |
|------|------|
| 每次任务完成后 | 更新「历史任务总览」、补充「核心技术沉淀」 |
| 每次踩坑后 | 在「核心技术沉淀」中记录坑和教训 |
| 每次必读文件清单变化时 | 同步更新记忆文件中的「必读文件清单」 |
| 发现新的未解决问题时 | 在「当前关注的问题」中记录 |
| 问题彻底解决后 | 从「当前关注的问题」中删除 |

### 4. 「当前关注的问题」章节规则

此章节是记忆文件中最重要的动态内容：

- **记录什么**：当前未解决的系统性问题、正在进行的改进方案、需要持续关注的风险点
- **不记录什么**：已解决的 Bug、已完成的任务（这些放在「历史任务总览」中）
- **格式**：
  ```
  ### [问题编号] 问题标题
  - 状态：关注中 / 处理中 / 等待验证
  - 关联文档：`docs/xxx.md`
  - 关联任务：R67-xx
  - 摘要：[一句话描述问题和当前进展]
  ```
- **当前需要记录的问题**：
  - 问题循环根因——五道防线改进方案（关联 `docs/问题循环根因分析与改进方案.md`，R67 全部完成且端到端验收通过后删除）

### 5. 执行纪律

- **每位成员**：任务完成后如果不更新记忆文件，等同于任务未完成
- **凌舟**：审查成员提交时，检查记忆文件是否同步更新；未更新的要求补更
- **新任务开始前**：必须先读自己的记忆文件，再读必读文件清单中的所有文件

## 十五、总结

问题循环出现的本质不是"同事不努力"或"标准有问题"，而是**标准缺少执行保障**：

- 有任务格式，但没有**完成验证标准** → 修复无法落地
- 有 API 文档，但没有**API 契约约束** → 前后端不对齐
- 有迁移脚本，但没有**执行跟踪** → 数据库状态不可控
- 有踩坑日志，但没有**派单前核实** → 基于过时信息派单
- 有任务文件，但没有**端到端验收** → 问题积累到部署才爆发

五道防线建立后，每个修复都必须经过"代码验证 → 构建验证 → 测试验证 → 凌舟复核 → 端到端验收"的完整闭环，确保修过的问题不会再出现。
