## 一、权限：一个判定核心，不复制

### 1.1 唯一核心
- 通用服务：**`OfficeAclService`**（`src/rag/office-acl.service.ts`）
- 判定顺序（**不可颠倒**）：
  1. **租户优先**（跨租户一律 none，平台身份例外）
  2. **owner / 平台** ⇒ admin
  3. **ACL** 命中 user/role/employee ⇒ 取**最高** perm
  4. **无 ACL 行 ⇒ 默认拒绝**（不做"无行即公开"）
- 主体类型：`user` / `role` / **`employee`（数字员工与人类同权）**
- 资源泛化：`{ resourceType, resourceId }` ⇒ doc / todo / approval / schedule 共用一套逻辑
- ⇒ **任何域需要权限 ⇒ 调用它，绝不复制一份判定逻辑**

### 1.2 防架空的三层防线（按强度排序）
| 层 | 做法 | 强度 |
|---|---|---|
| **① 结构上防架空**（最强） | 工具构造**只依赖 ACL 服务**，拿不到仓储 ⇒ 想绕也绕不过（文档工具采用） |
| **② 库层隔离** | 当必须注入仓储时（如按 assignee/status 查询）⇒ **把 ACL 可见集作为库查询条件**（`WHERE tenant=? AND (id IN(:granted) OR created_by=:me OR assignee=:me)`）⇒ **不是先查全量再内存过滤** |
| **③ 纵深防御** | 取回后**逐行 `resolveResource`** 再确认一次 |
| **④ mutation 守住** | 反测：绕过/收窄库条件 ⇒ 用例**必须红** |

⚠️ 空集合陷阱：`grantedIds` 为空时用 `['-1']`（避免空 `IN ()` 导致条件失效返回全量）

### 1.3 存在性即信息
- 无权 ⇒ 返回**"不存在"**口径（与真的不存在**同一文案**）⇒ 不泄露"存在但无权"
- mutation：改成"存在但无权" ⇒ 用例红

## 二、写操作防重：按语义选机制（四种）

| 场景 | 机制 | 防什么 |
|---|---|---|
| **重复入库**（如 create） | 幂等键（业务唯一键，如 `(tenant, content_hash)`） | 重复创建 |
| **并发覆盖**（如 update 改内容） | **乐观锁** `expectedVersion`（**必填**） | 静默覆盖他人修改 |
| **重复操作**（如 archive / complete） | 幂等键 + **原子 UPDATE 判定**（`UPDATE ... WHERE status<>'done'`，affected=0 ⇒ 回放，**不先读后写**） | 重复执行 |
| **重复业务动作**（如 cancel 销售单） | 业务键幂等（`billNo`） | 重复取消 |

⇒ **先判断"防的是什么"，再选机制**——不要一律用幂等键，也不要一律加乐观锁。

### 2.1 关键边界：【互斥终态操作不可回放】
> **幂等不是无脑回放 —— 要看"回放的结果是否仍然成立"。**

| 情形 | 可否回放 | 理由 |
|---|---|---|
| **无歧义终态**（`complete` 完成、`archive` 归档） | ✅ **可回放**（返回既有结果 + `duplicate:true`） | 完成就是完成，无歧义 |
| **互斥终态**（审批 approved / rejected） | ❌ **不可回放 ⇒ 明确失败 + 如实告知当前状态** | 并发者可能做了**相反**决定；把"重复审批"回放成成功 = **撒谎** |

- 实例对比：
  - `aiTodoComplete`：完成=完成 ⇒ 重复调用 ⇒ 回放 ✓
  - `aiApprovalApprove`：并发可能已 `rejected` ⇒ 重复调用 **明确失败并告知"当前已是 rejected"**（不回放）✓
- ⇒ 工具注释与 spec 都要写明"为什么这里不回放"（否则后人会"统一改成回放"而引入误导）

### 2.2 唯一键含【可空列】时必须有业务层兜底
- MySQL 与 sqlite **都允许多个 NULL**（含 NULL 的唯一键**不判重**）
- ⇒ 幂等键若含可空字段（如 `due_at` / `related_biz`）⇒ **必须配业务层幂等兜底**，并在注释注明**哪层承重**（DB 层只是并发竞态的第二道）

## 三、结构性保证优先于约定

> 把正确性变成**默认路径**，而非"记得做"。

| 目标 | 约定性（弱） | **结构性（强，采用）** |
|---|---|---|
| 必经 ACL | "记得调 ACL" | 工具只依赖 ACL 服务 |
| 乐观锁生效 | `expectedVersion` 可选 | **必填**（parseArgs 拒空） |
| 幂等生效 | 靠调用方传键 | 工具声明 `idempotencyKeyFields` |
| 状态变更不绕过幂等 | "约定不改 status" | **update 不接受 status 字段** |

## 四、泛化/重构的两条硬教训（本批踩过）
1. **先确认"拿谁来比"** —— 泛化时最容易写成自比恒真（如 `resource.tenantId !== sameResource.tenantId`）⇒ **守卫失效但 lint 抓不到**。必须：
   - 用**上下文的** tenantId（`ctx.tenantId`）比
   - 配 **mutation**：换回自比 ⇒ 用例红
2. **构造参数顺序是隐式契约** —— 改服务签名（如 `(aclRepo, docRepo)`）必须同步所有调用方与 spec；否则桩打到错误仓储上（症状：查询条件不对但不易定位）。
3. **新服务注册进哪个模块，先做两项检查**（本会话三次踩坑，AI-39 最典型）：
   - ① 目标模块的 **spec 是否有"精确结构断言"**（如 `providers).toHaveLength(12)`）⇒ 有则**不能**注册进去（否则撞红线"既有断言零修改"）
   - ② 目标模块**是否会引入循环依赖**（如 ToolsModule → ProactiveModule → BrainModule → … ⇒ DI 红）
   - ✅ 正解：**新建独立小模块**（`imports` 所需能力模块，由 `AppModule` 导入）——
     文件留在其**架构归属域**（如提醒服务留在 `proactive/`），但注册链独立 ⇒ 既守架构一致、又零改既有断言、又无环

## 五、验证伦理

- **mutation 不看"替换生效"，看"目标用例变红"**（否则可能是空转：替换了但用例恒绿）
- mutation 前**先断言目标串存在**（避免替换了别处）
- **形状断言必须断言到"关键内容"**（实例：只断言"where 有三支 OR + 各支含 tenant" ⇒ 把 ACL 授予支清空也不会红；
  必须再断言"授予支的 `id IN` 值 === granted 集合"，mutation 才真红）
  - ⇒ 写完断言先自问：**"如果这一支的数据被换成空/错值，我的断言会红吗？"** 不会 ⇒ 漏测
- **mutation 后确认"测试真的跑了"**：既不能"替换生效却全绿"（空转），
  也不能 **`Tests: 0 total`**（替换文本破坏了语法结构 ⇒ 根本没跑，看起来"没通过"是假象）
  - 实例：替换文本里带 `// MUT` 注释 ⇒ 注释掉后续实参 ⇒ 语法错 ⇒ `0 total` ⇒ **无效 mutation**
  - ⇒ **替换文本必须无注释、且不改变语法结构**；跑完先看 total 是否为预期值
  - ✅ **正确做法**：用**正则（格式无关）变异**，且替换文本保持原语法形状
    （本会话三次踩坑：改语法致 `0 total`、prettier 重排致"未命中"、单行目标仍不稳）
- **未变红的 mutation 不写成"已验证"**（如实说明"该层不承重，属纵深防御"）
- **半成品不报完成**：实现无 spec / spec 无 mutation ⇒ 不算验收完成
- **桩必须与真实库语义一致**（否则同时制造两类假象）：
  - **假绿**（桩太宽松：绕过了真实约束，测了个寂寞）
  - **假红**（桩太严/算子错：功能没错却报失败）
    - 实例：把 TypeORM `LessThanOrEqual` 的 `type` 写成 `'lte'`（实际 `'lessThanOrEqual'`）
      ⇒ 过滤退化 ⇒ 用例假红；不跑则只在真实查询里以"查不到数据"出现
  - ⇒ 桩里的算子/语义要**照抄真实库**（并在桩内注释说明照抄了什么）

## 六、验收红旗（出现即不合格）

| 红旗 | 说明 |
|---|---|
| ✅ 但功能坏了 | 假绿（空转 / 桩宽松 / 断言恒真）|
| ❌ 但功能没错 | 假红（桩与库语义不一致）|
| 实现完成但无 spec | 半成品，不算完成 |
| mutation"替换生效"却全绿 | 空转，该 mutation 无效 |
