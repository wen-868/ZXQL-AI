## 1\. 项目概述

### 1.1 背景

现有系统已实现：AI 驱动软件执行层、固定突出对话框、任务进展工作台、数据展示面板、审阅决策入口、云端+本地混合大模型、数据本地保存（后续规划云端部署）。

本方案在此基础上，将 AI 底座中的 Agent 升级为"数字员工"，形成一套可组织、可协作、可管理的 AI 组织系统。

### 1.2 核心理念

1. **数字员工即虚拟团队**：每个数字员工是有身份、有专业、有记忆、有权限的虚拟成员，而非一次性工具。
2. **按真实公司组织架构运转**：部门、岗位、汇报关系、协作流程全部对齐真实企业。
3. **每个员工独立工作台**：员工本身就是独立对话框，完整展示其全部工作内容。
4. **双模式协作**：单聊（一对一派活）与群聊（多员工协作）并存。
5. **项目主管全局可见**：主管可进入任何员工的工作台，查看项目内所有人的工作内容。
6. **人机分工明确**：AI 给方案，人做决策，关键节点必有审阅入口。

### 1.3 系统定位

> 从"带 AI 功能的软件"升级为"由 AI 员工组成的虚拟运营公司"。

## 2\. 总体架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────┐
│  第五层：管理视图层                               │
│  项目主管工作台 / 全局监控 / 审批中心              │
├─────────────────────────────────────────────────┤
│  第四层：协作交互层                               │
│  单聊 / 群聊 / 项目看板 / 任务派发                │
├─────────────────────────────────────────────────┤
│  第三层：数字员工层                               │
│  员工A工作台 | 员工B工作台 | 员工C工作台 ...      │
│  每个员工 = 人设 + 能力包 + 数据权限 + 记忆库     │
├─────────────────────────────────────────────────┤
│  第二层：能力与工具层                             │
│  工具插件 / 业务API / 数据访问 / 执行引擎         │
├─────────────────────────────────────────────────┤
│  第一层：数据层                                   │
│  世界模型（业务关系网络）/ 全局数据 / 员工记忆     │
└─────────────────────────────────────────────────┘
```

### 2.2 核心概念模型

|概念|定义|
|-|-|
|数字员工|一个具备岗位身份、专业能力、独立记忆的 AI Agent|
|工作台|员工的工作空间 = 对话窗口 + 工作内容 + 数据面板 + 审阅入口|
|组织架构|部门-岗位-员工的层级关系，决定汇报与协作路径|
|项目|需要多员工协作完成的目标单元，含群聊 + 任务看板|
|任务|可执行的工作项，有负责人、状态、进度、产出|
|审阅点|需要人工确认的决策节点，AI 在此暂停等待|
|记忆|员工的跨会话长期知识（偏好、历史、经验）|

## 3\. 组织架构设计

### 3.1 组织树

```
运营公司（虚拟组织）
│
├── 总经办
│   └── 项目主管（用户本人视角）/ 项目组长（协调型数字员工）
│
├── 商品部
│   ├── 选品官
│   └── 采购专员
│
├── 运营部
│   ├── 运营员
│   └── 客服专员
│
├── 内容部
│   ├── 内容策划
│   └── 剪辑师
│
└── 财务部
    └── 财务员
```

### 3.2 部门与岗位定义

|部门|岗位|职责|汇报对象|
|-|-|-|-|
|总经办|项目主管|全局统筹、决策审批|—（最高）|
|总经办|项目组长|任务拆解、跨部门协调、进度汇总|项目主管|
|商品部|选品官|商品分析、竞品调研、选品定价建议|项目组长|
|商品部|采购专员|供应链对接、补货计划|项目组长|
|运营部|运营员|价格调整、上下架、库存管理|项目组长|
|运营部|客服专员|售后、评价、投诉处理|项目组长|
|内容部|内容策划|短视频脚本、文案、素材策划|项目组长|
|内容部|剪辑师|视频剪辑、发布调度|项目组长|
|财务部|财务员|利润核算、成本分析、风险预警|项目组长|

### 3.3 汇报与协作关系

* **汇报线**：员工 → 项目组长 → 项目主管
* **协作线**：员工之间可横向协作（如选品官 → 运营员传递商品清单）
* **审批线**：敏感操作（改价、采购、发布）→ 触发审阅 → 项目主管确认

### 3.4 岗位职责矩阵（RACI 简化版）

|场景|选品官|运营员|内容策划|财务员|项目组长|
|-|-|-|-|-|-|
|商品上架|建议|执行|—|审核利润|协调|
|价格调整|建议|执行|—|审核|审批|
|内容发布|—|—|策划执行|—|审批|
|竞品监控|负责|参考|参考|—|汇总|

## 5\. 员工工作台设计

### 5.1 工作台布局

```
┌──────────────────────────────────────────────┐
│  \[1] 员工信息卡（头像/姓名/岗位/部门/状态）     │
├──────────────────────────────────────────────┤
│  \[2] 对话窗口（核心交互区，固定突出）           │
│      历史消息 / 当前对话 / 输入框              │
├──────────────────────────────────────────────┤
│  \[3] 工作内容面板（该员工所有工作项）           │
│      进行中 / 待开始 / 已完成                  │
├──────────────────────────────────────────────┤
│  \[4] 数据面板（该员工专业领域数据）             │
├──────────────────────────────────────────────┤
│  \[5] 审阅决策入口（待确认事项）                 │
└──────────────────────────────────────────────┘
```

### 5.2 各模块详细设计

#### 员工信息卡

* 显示：头像、姓名、岗位、部门、在线状态、当前负载
* 交互：点击可查看员工完整档案（能力、权限、历史绩效）

#### 对话窗口

* 固定突出，不隐藏（用户明确要求）
* 支持：文本对话、文件上传、@其他员工、引用消息
* 每个员工独立会话，独立记忆
* 显示"正在思考/正在执行"的实时状态

#### 工作内容面板

* 按状态分组：进行中 / 待审阅 / 待开始 / 已完成
* 每个任务可展开查看：步骤进度、每步依据、产出物
* 支持时间线视图和列表视图切换

#### 数据面板

* 展示该员工专业领域的关键指标
* 数据与任务联动（点任务跳数据，点数据看关联任务）

#### 审阅决策入口

* AI 结论 + 依据并排展示
* 操作按钮：确认执行 / 修改方案 / 取消
* 高风险操作红色标注

## 6\. 交互模式设计

### 6.1 单聊模式

**场景**：给单个员工单独派活

**流程**：

```
用户进入员工工作台 → 对话窗口输入指令 → 员工接收 → 执行
→ 工作区展示进度 → 完成后对话通知 → 用户确认/验收
```

**特点**：一对一、独立记忆、全过程可追溯

### 6.2 群聊模式

**场景**：多员工协作项目

**流程**：

```
项目主管创建项目群聊 → 拉入相关员工 → @分配任务
→ 各员工接单并同步进度 → 员工间横向协作 → 项目组长汇总 → 主管验收
```

**群聊消息类型**：

|类型|说明|
|-|-|
|任务分配|@员工 + 任务描述|
|进度汇报|员工主动汇报|
|协作请求|员工间请求配合|
|审阅触发|需主管确认时@主管|
|结果汇总|项目组长汇总|

### 6.3 项目协作模式

**项目生命周期**：

```
立项 → 任务拆解 → 派发 → 执行 → 协作 → 审阅 → 验收 → 归档
```

**项目数据模型**：

|字段|说明|
|-|-|
|project\_id|项目ID|
|name|项目名|
|members|参与员工列表|
|tasks|任务列表|
|status|状态（进行中/已完成/暂停）|
|progress|总进度|
|owner|项目组长|
|created\_at|创建时间|

### 6.4 消息与任务流转

```
用户指令 → 意图识别 → 任务拆解 → 分配员工 → 执行
   ↑                                          ↓
   └──── 审阅确认 ←── 关键节点暂停 ←── 进度汇报 ←┘
```

## 8\. 协作机制

### 8.1 任务派发

|方式|场景|
|-|-|
|主管直接派单|@员工 分配任务|
|项目组长转派|组长拆解后分发|
|员工自主接单|群聊中主动认领|
|系统自动派单|触发条件自动创建任务|

### 8.2 员工间协作

* 横向请求：员工A 可向员工B 发起协作请求
* 数据传递：任务产出物自动流转给下游员工
* 依赖管理：任务间可设置依赖关系

### 8.3 冲突处理

* 资源冲突：项目组长协调
* 意见分歧：上报项目主管裁决
* 权限冲突：遵循最小权限原则

### 8.4 结果汇总

* 项目组长负责汇总各员工产出
* 生成项目总结报告
* 归档到项目历史

## 9\. 数据架构

### 9.1 数据分类

|类型|说明|存储|
|-|-|-|
|全局业务数据|商品/订单/库存/竞品|服务器共享|
|员工对话记录|每个员工的对话|员工工作区|
|项目协作记录|群聊、任务分配|项目空间|
|员工记忆|长期知识/偏好|员工本地（当前）|
|私有敏感数据|客户隐私等|本地|

### 9.2 存储方案

* **本地部署阶段**：SQLite / 本地数据库 + 本地文件
* **云端部署阶段**：服务器数据库 + 对象存储
* **关键设计**：数据访问层统一封装，本地/云端实现可切换（为后续上云预留）

### 9.3 权限模型

|角色|权限|
|-|-|
|项目主管|全部数据 + 审批权|
|项目组长|项目内任务数据|
|员工|本岗位专业数据（读/写按需）|

### 9.4 记忆机制

* 每个员工独立记忆库
* 记忆类型：短期（会话）、长期（跨会话）、技能（经验）
* 记忆更新：任务完成后提炼关键信息入库

## 10\. 技术实现

### 10.1 技术栈建议

|层级|技术|
|-|-|
|前端|Web / Electron（本地 exe）|
|后端|Python（FastAPI）/ Node.js|
|Agent 编排|LangGraph / DeepSeek Harness|
|大模型|本地 Ollama + 云端 DeepSeek API|
|数据库|SQLite（本地）/ PostgreSQL（云端）|
|实时通信|WebSocket（进度推送）|

### 10.2 Agent 编排

* 每个员工 = 一个 Agent 实例（独立人设 + 工具 + 记忆）
* 项目组长 = 调度 Agent（任务拆解 + 派发）
* 员工间通信 = 消息队列 / 事件总线

### 10.3 大模型混合策略

|场景|模型|
|-|-|
|简单对话/查询|本地 Ollama（省成本）|
|复杂分析/跨员工协作|云端 DeepSeek API|
|敏感数据处理|本地模型（数据不出本地）|

### 10.4 关键接口

* 员工对话接口
* 任务执行接口
* 进度推送接口（WebSocket）
* 审阅确认接口
* 数据查询接口

## 12. v0.2 修订（2026-09-05）：Capability Scoping 版 MVP

> 本节为 v0.1 的正式修订。依据：凌舟对 v0.1 的逐项拆解意见 + 用户三项交互定案。
> 修订原则：**采纳 v0.1 的产品蓝图与叙事，技术实现按"能力域工程（Capability Scoping）"收敛，砍掉全部组织性冗余。**

### 12.1 v0.1 主张逐条判定（凌舟意见，全部采纳）

| v0.1 主张 | 判定 | 本版处置 |
|---|---|---|
| 岗位级工具/权限/记忆隔离 | 🟢 真必要 | **保留为 MVP 核心**（岗位档案表 + employeeId 维度） |
| 任务流水线（长链路拆岗位，输入输出契约） | 🟢 真必要 | **保留**（子代理派发即流水线的一段；产出物用 task_artifact 契约） |
| 审阅点归属（谁提议、谁批） | 🟢 真必要 | **保留**（审阅卡挂员工署名；写全审核强制门全局生效） |
| 组织树/部门/汇报线/职级 | 🔴 不必要 | **删除**（部门字段仅作展示标签，不驱动任何行为） |
| 群聊（多员工自由对话协作） | 🔴 不做 | **删除**（成本炸弹+失控源；协作=结构化派发，不自由对话） |
| 8 个独立工作台 UI | 🟡 可替代 | **不做独立工作台**（对话框即工作台，见 12.2） |
| 头像/姓名/人设文案 | 🟡 感知层 | **保留但降级为展示字段**（不作为必要性论据，作为卖点叙事） |

**定位更名**：对内本方案更名为 **Capability Scoping（岗位能力域）**；对外产品叙事保留"AI 数字员工"。

### 12.2 三项交互定案（用户确认，2026-09-25）

1. **每个 agent 员工就是一个对话框**：新建员工自动进入对话列表（含名称/岗位/部门标签），打开即与该员工单聊。
2. **对话框内容就是员工的工作台**：不建独立工作台 UI。工作过程全部以既有卡片形态呈现在会话流内——执行计划卡、工具调用轨迹、任务产物卡、写确认卡（桌面端均已实现渲染）。
3. **上级数字员工派发任务给下级（异步任务交接 + 回传验收，非同步子代理）**：
   上级经 `dispatchEmployeeTask` 工具（或用户直接交办）把任务交给下级——**派发即返回**（上级收到"已派发"确认，不阻塞等待）；
   下级**在自己的对话框中**执行任务（独立的 Agent 会话轮：任务出现→执行→写确认→完成，全过程在下级会话留痕）；
   完成后**结果回传**到上级对话框（"任务完成回传"消息 + 任务表 completed），上级据此验收。
   失败时回传失败原因（任务表 failed），可重新派发。
   **调度关系模型（12.5 修订后定案）**：不建组织树——**指挥关系 = 员工档案上的"可调用员工列表"（边表）**。建员工 A 时设定职责岗位并勾选可调用的员工 B、C；组织树是该边表的自动投影（前端员工卡展示"可调用：B、C"），加员工/改指挥关系只改一条边。防失控三闸：派发深度上限 `MAX_DISPATCH_DEPTH`（任务记录携带 depth，默认 2）、环路由边表天然隔离（只能派给列表内员工）、下级执行同样过写全审核强制门。

### 12.3 MVP 架构（一张表 + 一个维度 + 一个工具）

```
t_ai_employee（岗位档案表——凌舟判定"系统真正需要的只有这张表"）
  = 岗位 → 工具业务域子集(tool_categories) + 数据权限(data_scope)
    + 人设(persona_prompt) + 审阅规则(全局写闸门+后续按岗配置)
    + 记忆命名空间(conversationId 前缀 emp_{uid})
    + 可调用员工列表(dispatch_uids 边表——组织树的替代，见 12.2 定案3)

t_ai_employee_task（下级会话工作留痕）
  = 任务描述 + 派发来源(user/上级员工) + 状态(running/completed/failed) + 结果摘要

employeeId 维度（贯穿 Orchestrator 单次执行）
  = 人设提示词替换默认 + 工具定义按 tool_categories 过滤
    + 审计记录署名 employeeId + 会话记忆按 emp_{uid} 前缀隔离
```

**验收标准（每条可执行）**：

### 12.7 MVP 首条流水线定义：补货流水线（mgmt 域）

> 选域理由：mgmt 域数据与工具齐备（库存/采购/商品 106 工具），验证岗位化机制成本最低；OPS 域流水线照抄本结构。

**岗位定义（种子，2 员工 + 1 条边）**：

| 员工 | 岗位 | 工具域子集 | 可调用 | 人设要点 |
|---|---|---|---|---|
| 库管家 | 库存管家 | inventory、product | [采购专员] | 稳健细致，先核实再建议 |
| 采专员 | 采购专员 | purchase、inventory | []（终端） | 务实精算，采购单必带依据 |

**流水线流程（示例话术触发，异步任务交接 + 回传验收）**：

```
用户（在库管家对话框）："查一下缺货的商品，给采购专员下补货任务"
  → 库管家调用 checkInventory → 发现低库存清单
  → 库管家调用 dispatchEmployeeTask（目标=采购专员，任务=按清单创建采购单预览）
      → 【立即返回】库管家对话出现"已派发给采购专员（任务#N）"，本轮结束
      → 采购专员对话框出现任务消息，系统异步触发采购专员的 Agent 会话轮
      → 采购专员在自己的会话内执行：生成采购单 → 写闸门挂预览（pending_write）
      → 用户在【采购专员对话框】确认 → 采购单真实创建 → 任务表 completed
      → 【回传】库管家对话框出现"任务#N 完成回传：采购单 CG…已创建，请验收"
  → 用户在库管家对话框验收（或追问细节）
```

**本流水线的验证点**：派发即返回不阻塞；跨员工任务留痕（两张对话框各有记录与回传消息）；边表校验；写闸门全链生效；失败回传原因可重派。

### 12.8.6 澄清事件「无参数写意图」真根因（2026-09-26 追加调查）

**上一轮结论是错的，此处更正。** 上一轮判断"未覆盖的只是 LLM 选择先反问而不调工具的行为分支，属提示词策略范畴，不是代码缺口"——**调查后证实是确定性代码缺口**。

**证据链**：

1. `createSalesOrder` 的 `parameters.required = ['items']`（`create-sales-order.tool.ts:179`）；
2. 缺 items 时 `parseArgs` 直接失败 → 返回 `{ success:false, error, suggestion }`，**不带 preview**（同文件 L194-199）；
3. 而 Orchestrator 的澄清分支写作 `if (toolResult.preview) { ...tryEnhance... }`（`orchestrator.service.ts` 原 L805）——**preview 为假，tryEnhance 根本不会执行**；
4. 结论：用户说"开单"但不给参数时，澄清事件**永远触发不了**，只剩一句自然语言反问。

**修复**：对"失败且是写操作"的调用补一次澄清判定——`needsWriteFailureClarifyCheck()`（纯函数，5 例单测）：
- 无 preview（有 preview 的由主流程处理，不重复）
- 且调用失败
- 且该工具是写操作

只产出 clarify，**不改 `execArgs`**（本次调用已失败，没有后续确认执行可供增强）。`tryEnhance` 内部先查 `docTypeForTool`，未映射的写工具立即返回、不产生 LLM 调用；非参数类失败（如后端不可用）通常不构成澄清条件，会自然落回原错误流程。

**为何优于上一轮提的两个备选**（提示词强化 / 强制选工具调用）：确定性（不依赖 LLM 遵从）、零新增业务规则（无需自造关键词 → docType 映射）、产出真实**字段级 issue**（`sales_order` schema 的必填 `customerName`、`items[].skuName` 由 `tryEnhance` 生成）。

**附带更正**：上一轮所列第 1 条理由（"写入字段抽取禁用正则，故不能做意图识别"）**表述不准**——`write-schema-registry` 禁正则的范围是**字段值抽取**，而**意图域判定**在本仓已有先例：`intent-detector.ts` 就是用关键词规则做业务域分诊（"规则快车道"）。只是本例并不需要走关键词路线，因为已有更确定的代码级缺口。

**遗留（非阻塞）**：「LLM 完全不调用工具、直接以自然语言反问」这一分支仍未覆盖，属提示词/策略范畴。若后续要收敛，建议优先改提示词（零开销）；不建议为它增加一次强制选工具的 LLM 往返。
