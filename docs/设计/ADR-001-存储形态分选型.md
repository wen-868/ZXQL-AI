# ADR-001：存储形态选型 —— 分形态（standalone 用 better-sqlite3 嵌入，connected 用 MySQL）

> 状态：**已采纳；spike（R101-AI-29）已验证：LibSQL 不可行 ⇒ 改用 better-sqlite3（实测可行）；待 A2 改造**
> 日期：2026-10-13（决策）/ 2026-10-14（据 spike 实证修订）｜决策人：凌舟（业主确认）
> 依据：《存储选型评审报告-多维加权-20261013.md》（ZXQL-MS 仓）+ spike 证据包 `scripts/spike-libsql/`（ZXQL-AI）
> 门禁基线：**153 套件 / 1683 用例**（本决策不影响，生产 MySQL 零改动）

---

## 背景

AI 底座当前**强依赖 MySQL + Redis**（云端多租户真源）。业主要求：
1. AI 底座**可独立运行**（不依赖管理系统/运营系统）
2. 桌面端**操作越简单越好** ⇒ 不额外安装/运维数据库服务
3. 支持 **10 名人类 + 10 名数字员工共享同一份数据**

## 决策

**分形态选型** —— 按 `INTEGRATION_MODE` 装配：

| 形态 | 存储 | 说明 |
|---|---|---|
| **standalone**（桌面端） | **better-sqlite3 嵌入**（`data/app.db`，WAL） | 单文件、零服务进程、零安装 |
| **connected**（共享/云生产） | **MySQL（不变）** | 多租户真源；代码零改动 |

Redis：standalone 走**内存 + 持久化**；connected 启用 ioredis。

> ⚠️ **据 spike 修订**：原定 **LibSQL 已出局**（见下），改用评审排序第二的 **better-sqlite3（8.45）**——spike 实测可行。

## LibSQL 出局的两条独立硬证据（spike，非推测）

| # | 证据 | 决定性 |
|---|---|---|
| 1 | **TypeORM 1.1.0 的 `DatabaseType` 不含 libsql**（含 better-sqlite3/sqljs/mysql…）；实测 `type:'libsql'` ⇒ `Wrong driver: "libsql" given` | ✅ **决定性**（与架构无关）|
| 2 | 本机 **win32/arm64** 无 libsql 原生绑定（上游仅 win-x64）⇒ `Cannot find module '@libsql/win32-arm64-msvc'` | 附加平台风险 |

⇒ 坚持 LibSQL 的唯一路径 = 自研 `options.driver` 适配层 + Windows 绑定与 Electron rebuild 双份风险 ⇒ **不推荐**（其"嵌入副本/远程同步"增值非当前需求）。

## better-sqlite3 可行（spike 实证，本机 arm64 全通）

- 建连/建表/读写 OK（better-sqlite3 12.11.1 / SQLite 3.53.2，与 TypeORM peer `^12` 匹配）
- 代表性实体：JSON 列往返 OK；复合唯一索引 `uk_ai_idempotency` 正确生成；**`datetime(3)` 毫秒保留**
- **幂等仲裁等价**：`ON CONFLICT(…) DO UPDATE` 连续命中同一行，累加同 MySQL；更优写法 `DO NOTHING` 冲突时 `changes=0` ⇒ **可无异常判重**（契合 AI-21 闸门）

## 架构影响（spike 新发现）

⚠️ **本机 ARM64**（`PROCESSOR_ARCHITECTURE: ARM64`、`node process.arch: arm64`）—— 影响桌面端需 **arm64 原生包**（或 x64 仿真），native 模块需 arm64 产物 + Electron rebuild 匹配。

## 必须计入的改造点（F1~F6，均实证）

| ID | 现象 | 改造 |
|---|---|---|
| F1 | `char` 不支持 | → `varchar` |
| F2 | `mediumtext` 不支持 | → `text` |
| F3 | `bigint` 主键 + AUTOINCREMENT 受限 | → `integer` |
| **F4** | 冲突错误码不同（SQLite `SQLITE_CONSTRAINT_UNIQUE`/errno undefined vs MySQL `ER_DUP_ENTRY/1062`）⇒ **现有 `isDuplicateKeyError()` 不命中** | **扩方言判重（关键）** |
| F5 | `ON DUPLICATE KEY UPDATE` 在 SQLite **语法错误** | 4 处写点 → `ON CONFLICT … DO UPDATE` |
| **F6** | `decimal(12,4)` 读回 **number**（MySQL string） | 金额点专项核查 |

## 迁移与工作量（乙案，推荐）

- **乙案**：桌面端**单基线**（synchronize 生成一次 → 固化 `migrations-sqlite/000_baseline.sql`）+ 增量脚本 ⇒ **0.5 人日**（甲案移植 17 个迁移 8~20h；丙案永远 synchronize 不建议）
- **总改造量 ≈ 3.5 ~ 5 人日**：实体 0.5~1 + 方言 F5 0.5 + 判重/数值 0.5 + 基线 0.5 + 双模式 1 + **arm64/Electron rebuild 0.5~1**

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 双方言长期维护 | 乙案单基线降桌面成本；生产 MySQL 零改动 |
| SQLite 单写队列 | 写批量化 + `busy_timeout` |
| **arm64 原生模块** | spike 已验证；Electron rebuild 纳入 A2 验收 |
| 幂等/判重语义 | `ON CONFLICT` 等效性有冲突输出；AI-21 反测 5 条须在 sqlite 形态复跑 |
| decimal 类型差异 | F6 专项（单价/用量/计费）|

## 后续

- **A2 改造单（待派）**：better-sqlite3 落地（F1~F6 + 迁移基线乙案 + 运行时双模式 + arm64 Electron rebuild）
- 完成后：AI-21 反测 sqlite 复跑 + 全量门禁（153 套件基线）+ 桌面端 standalone 启动验证

## 不做

- 不改云端生产存储（MySQL）
- 不做 LibSQL 自研 driver
- 不做分布式多主机同步（共享 = 单主机库）
- 编程能力后置，不在本决策范围

## 补充：打包形态 = 单包兼容（业主 2026-10-14 明确）

> **实施结论（R101-AI-30 第 1 步实证，待业主最终决策）**：
> electron-builder 26.15.3 **原生不支持 Windows 单包双架构**（`arch` 数组只出多个包；跨架构合并仅 macOS `universal`）⇒ "一个包"需自研 NSIS 层。
> 推荐**甲方案**：单安装器内含 `payload/x64` + `payload/arm64`（各含对应 Electron 运行时 + 对应 better-sqlite3 native），注入 `nsis.include`，安装时按 `${IsNativeARM64}`/`PROCESSOR_ARCHITECTURE` 选载荷。代价：包体 ≈2×（粗估 350~450MB）+ 自研 NSIS 维护 + x64 native 需 x64 工具链。
> **待验证的更优解**：Windows on ARM 的 x64 仿真能否加载 x64 native —— 若能，则 **x64 单包（~150MB）即可覆盖两架构**，甲方案双 payload 不必需。已令执行方评估（有依据给依据）。
> 双包仅作 fallback；"只做 x64 靠仿真且 native 不匹配"= 禁止（加载失败）。

## 补充：双形态门禁模型（R101-AI-30 实证，重要方法论）

**全局 `INTEGRATION_MODE=standalone` 跑既有旧套件不可能全绿**（实测 `1 failed, 1699 passed`）：既有断言硬编码 MySQL 方言（如 R101-AI-03 的 `VALUES(total_cost)`），且红线禁止改既有断言。

⇒ **正确门禁模型 = 二者分离**：
1. **connected 形态**：跑**全量**既有套件（生产路径，断言须逐字不变 ⇒ 当前 154 套件 1700 用例全绿）
2. **standalone 形态**：只跑 **standalone 专用 spec**（覆盖方言/装配/冷启动/对话闭环），不得用全局翻 env 方式跑旧套件

⚠️ 关联时序坑（已踩并修正）：TypeORM 装饰器在**模块加载期**求值 ⇒ standalone spec 取值须按"加载期形态"，不能按"运行时形态"。

## 补充：standalone 形态的进程启动约束（R101-AI-30 第 2 步实证）

**`INTEGRATION_MODE` 必须在进程启动前确定，运行期不可切换**（同一进程内实体元数据与数据库连接必须一致）。

实证：`database.module.spec.ts` 首版真建连用例报 `DataTypeNotSupportedError: Data type "char" in AiModelPriceEntity.currency` —— 非实体漏改（源码已是 `dialectColumnType('char','varchar')`），而是方言在**模块加载期（装饰器）**求值，用例在 `it()` 内才设 env ⇒ 实体早已按 MySQL 元数据加载。改用 `jest.isolateModules` 重加载才对。

⇒ **对下游的硬约束**：
1. **Electron 启动参数 / 冷启动脚本**：`INTEGRATION_MODE=standalone` 必须在 spawn 进程**前**设好，不能运行时改
2. **设置界面**：切换 standalone/connected 后**必须重启应用**（提示用户），不得热切换
3. **迁移基线**：`migrations-sqlite/000_baseline.sql` 在 standalone 首启执行（连接与元数据同为 sqlite 形态）

原 ADR 写「arm64 rebuild 成功并启动（不可行则报卡点，不静默降级 x64 仿真）」。
业主口径更新：

> 「在 A2 里同时要求产出 x64 与 arm64 双架构包；不用做双架构，做兼容包就好了。

⇒ **最终口径 = 单包兼容**：产出**一个**安装包（便携版同理），同时适配 x64 与 arm64（安装时按 `PROCESSOR_ARCHITECTURE` 装配对应 native 模块），**不做 x64 / arm64 两个 exe。

技术要求（写入 R101-AI-30 验收）：
- 单 NSIS 包内含双架构 native（better-sqlite3 的 x64 + arm64 产物）
- 安装脚本探测架构后装配对应 native
- **不靠 x64 仿真**（better-sqlite3 native 模块在 arm64 机器必须 arm64 产物，仿真 ⇒ 加载失败）
- 双架构实机验证：x64 机器 / arm64 机器各自启动 + standalone 完整对话可用
- 若 electron-builder 原生不支持单包双 arch ⇒ 报卡点由凌舟定（最终 fallback = 便携 MariaDB 8.10 或双包方案）
