# 运营域全量工具定义（Tool Registry 详设）

> 范围：在现有 AI 底座 `ToolRegistry`（24 个管理系统工具 + 模式 A/B）基础上，**补全运营系统（systemScope=ops）全量工具**。工具框架与 `scaffold/src/tools/tool.interface.ts`、`tool-registry.ts` 对齐。
> 微服务目录：**以 v2.0 文档第九节「微服务对接指南」的真实 14 微服务为准**（3001–3014）。其中 10 个 v2.0 已列 API；4 个（3001/3002/3011/3013）v2.0 未细化，本篇按「总后台共用、服务双系统」架构推断为运营内容域服务，**标注〔推断〕待总后台服务注册表确认**。

---

## 一、工具框架（与脚手架对齐）

### 1.1 ToolContext（每次调用的上下文）

```ts
interface ToolContext {
  tenantId: string;     // 租户隔离主键（来自 JWT，统一账号体系）
  userId: string;       // 操作人
  sessionId: string;    // 会话/任务（图状态 key）
  role: string;         // 角色（决定权限边界）
  systemScope: 'mgmt' | 'ops';  // 本篇全为 'ops'
}
```

### 1.2 ToolDefinition（注册元数据，供 LLM 选型）

```ts
interface ToolDefinition {
  id: string;            // 唯一，如 'ops.topic.generate'
  name: string;          // 中文名
  scope: 'ops';          // 仅运营域
  risk: ToolRisk;        // low | medium | high
  needsReview: boolean;  // 是否触发人工闸
  microservice: string;  // 下游微服务名（真实总后台目录）
  method: string;        // HTTP 方法 + 路径
  argsSchema: JSONSchema;// 入参
  output: string;        // 出参描述
  description: string;   // 自描述（给 LLM 读）
}
```

### 1.3 ToolRisk 分级 + 人工闸映射

| 风险 | 含义 | 是否需审核 | 对应确认点 |
|---|---|---|---|
| `low` | 只读/查询、无副作用 | 否 | — |
| `medium` | 生成草稿/本地计算，可撤回 | 否（落审计） | — |
| `high` | 对外发布/资金/不可逆写/涉客诉 | **是** | 发布审核 / 投流预算 / 高风客诉 / 对账差异 / 选品决策 |

### 1.4 执行链路

```
Orchestrator(graph) → ToolRegistry.execute(id, args, ctx)
   → 校验 scope==='ops' 且 risk 合法
   → ServiceClient(总后台) → 真实微服务(:port)   // 带 x-tenant-id
   → 返回 ToolResult{ data, needsReview?, reviewPayload? }
   → SSE: tool_start / tool_result（驱动工作区步骤流与工具面板）
```

- `needsReview=true` 时，ReviewClient 生成待审工单（映射现有审核流程），Orchestrator 冻结该节点，审核回调后续跑。
- 所有调用走总后台统一入口（含账号鉴权 + `x-tenant-id` 租户隔离），运营本地包不自建微服务。

### 2.3 运营工具 → 真实微服务 映射原则

- **重叠域**（订单/商品/财务/报表/客户/配送/库存/采购）→ 直接调真实中台微服务（order/product/finance/report/customer/delivery/inventory/purchase）。
- **纯内容运营域**（选题/脚本/成片/直播/投流/选品/复盘/市场情报/达人/出海）→ 调 2.2 推断的运营内容服务（3001/3002/3011/3013）。
- **审计/系统** → log(3014)/settings(3012) 由底座内部使用，不在运营业务工具暴露。

## 四、工具自描述（给 LLM 选型）

每个 `ToolDefinition.description` 用统一模板，供 Orchestrator 路由与 LLM 工具选择：

```
[ops.topic.generate] 生成短视频选题。下游 svc-create(3001)。入参：product(商品), angle(角度), count(数量)。
出参：选题列表(标题+钩子)。风险 medium，无审核。前置：需先有 product/市场情报。
```

- 工具间依赖在 `description` 中标注（如 `ops.distribute.publish` 前置 `ops.video.compose` + `ops.distribute.attach_cart`），供图节点排序。
- 风险 `high` 工具在描述末尾显式标注「**需人工审核：发布审核**」，引导 LLM 主动在确认点暂停。

## 五、与管理系统 24 工具的关系

| 关系 | 说明 |
|---|---|
| **复用框架** | 同一 `ToolRegistry`、`ToolContext`、`ToolRisk`、`ReviewClient`；仅 `systemScope` 不同（mgmt / ops） |
| **管理系统工具（24）** | 权限/主数据/订单(中台)/审核等，保持 `scope='mgmt'`，运营不调用 |
| **运营新增工具（本篇 ~30）** | `scope='ops'`，注册进同一 Registry 的 `scopeIndex['ops']`；下游指向真实总后台微服务 |
| **不重复建设** | 账号/租户/审核由总后台与现有流程提供；工具只做"调微服务 + 风险标注 + 出参" |

## 六、注册与执行（伪代码，对齐 scaffold）

```ts
// tool-registry.ts
register(def: ToolDefinition, scope: 'ops') {
  this.scopeIndex.get(scope)!.push(def.id);
  this.defs.set(def.id, def);
}
async execute(id, args, ctx: ToolContext) {
  const def = this.defs.get(id);
  if (def.scope !== ctx.systemScope) throw ScopeError;     // 跨域拦截
  const res = await this.serviceClient.call(def.microservice, def.method, args, ctx); // 带 x-tenant-id
  if (def.needsReview) {
    const ticket = await this.reviewClient.request(def.reviewPayload(args, ctx));
    return { ...res, needsReview: true, reviewPayload: ticket }; // Orchestrator 冻结
  }
  return res;
}
```

> 运营域全量工具定义完毕；LLM 经 Orchestrator(graph) 按 `description` 选型并串联，命中 `high` 自动进人工闸。微服务目录以总后台真实注册表为最终准（〔推断〕4 端口待确认）。
