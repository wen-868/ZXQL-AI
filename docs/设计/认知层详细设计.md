# 认知层详细设计（LT 长期记忆 / LN 自主学习 / SE 自主进化）

> 范围：对《AI底座全量改进详细设计》五/六/七节的骨架做**细写**。认知层是"全量开放"区别于旧底座的核心增量，使 AI **跨会话变聪明、从反馈学、随租户进化**。
> 对齐：`scaffold/src/memory/long-term-memory.service.ts`、`learning/learning.service.ts`、`evolution/evolution.service.ts`。
> 护栏前提：三项均**严格按 `tenantId` 隔离**；SE 强制门控（复用现有审核流程）；不跨租户、不碰核心权限、不删生产数据。

---

## 一、总览与定位

| 层 | 一句话 | 解决 | 风险 |
|---|---|---|---|
| **LT 长期记忆** | 跨会话持久化租户知识 | 忘性（旧底座仅 10 轮/1h） | 低 |
| **LN 自主学习** | 从成败反馈提炼经验回流 | 不会越用越准 | 中 |
| **SE 自主进化** | 优化自身 prompt/工具/工作流 | 不自演进 | 高（门控） |

协同闭环：

```
LT(记忆) ──提供背景──▶ Orchestrator 决策
   ▲                        │
   │                        ▼
LN(学习) ◀──成败反馈── 任务执行结果
   │
   ▼ 积累信号达阈值
SE(进化) ──提案──▶ 审核门控 ──批准──▶ 新版本 ──回流──▶ LT/LN
```

## 二、LT 长期记忆（详细）

### 2.1 四层模型

| 层 | 存储 | 内容 | 生命周期 | 读取频率 |
|---|---|---|---|---|
| 工作记忆 | Redis `ai:memory:{tid}:{sid}` | 当前会话多轮 | 1h（现有，保留） | 每轮 |
| 档案 profile | DB `ai_ltm_profile` | 租户/用户稳定事实：偏好、常用对象、品牌调性、禁区 | 持久 | 每次组装 Prompt |
| 情节 episodic | 向量库 `ai_ltm_episodic` | 历史交互摘要、成败经验（what/why/outcome） | 持久（配额限） | 检索相关 |
| 归档 archival | 向量库 `ai_ltm_archival` | 文档/知识沉淀（选品库、话术模板、复盘结论） | 持久 | 检索相关 |

### 2.2 写入管线（MemoryManager）

```
触发：会话结束 / 关键事件(发布成功·审核驳回·用户修正) / 定时压缩
  1. 抽取：LLM 从对话+工具结果抽取 (事实 / 经验 / 偏好)
  2. 分级：事实→profile；经验→episodic；文档→archival
  3. 摘要+压缩：长文本摘要，控制 token（防膨胀）
  4. 落库：带 tenantId；episodic/archival 向量化(Ollama embedding)入命名空间 {tid}
  5. 配额：单租户 episodic 上限 N 条，超出按重要性淘汰（LRU+评分）
```

### 2.3 读取管线（ContextBuilder）

```
组装 System Prompt：
  base(系统角色) + profile(稳定事实) + retrieval(episodic/archival top-k 相关)
 检索：embedding(query=当前任务) → 向量库 {tid} top-k → 重排(相关性+时效+重要性)
 注入：仅注入相关片段，控制总量（防噪声/超长）
```

### 2.4 压缩与配额（防膨胀/噪声）

- **摘要链**：episodic 超 30 天未命中 → 合并为更高层摘要，原条降权。
- **租户配额**：episodic 条数 / 向量体积上限，超阈告警 + 自动淘汰低分。
- **TTL 分级**：profile 持久；episodic 默认持久但可衰减；archival 持久。

### 2.5 Schema（增量表）

```sql
ai_ltm_profile(tenant_id, entity_type, entity_id, k, v_json, updated_at)
ai_ltm_episodic(tenant_id, id, summary, what, why, outcome, score, created_at, embedding_vec)
ai_ltm_archival(tenant_id, id, title, body, source, embedding_vec, created_at)
```

### 2.6 与 RAG 关系

LT 复用现有 RAG 向量底座（Ollama embedding）；episodic/archival 即租户隔离的 RAG 命名空间 `ai_knowledge_{tid}`。LT 是"会成长的 RAG"。

## 三、LN 自主学习（详细）

### 3.1 反馈信号源

| 信号 | 来源 | 权重 |
|---|---|---|
| 任务成功 | 工具全成功 + 无审核驳回 | 高 |
| 任务失败 | 工具报错 / 审核驳回 | 高 |
| 用户修正 | 用户改产物/改脚本/改参数 | 高 |
| 显式评分 | 用户对结果打分/评价 | 中 |
| 审核结论 | 人工审过/打回（含理由） | 高 |

### 3.2 经验结构化（Experience）

```ts
interface Experience {
  what: string;      // 发生了什么（如"挂车发布被驳回：未填类目"）
  why: string;       // 原因
  context: string;   // 触发场景（租户/域/任务类型）
  outcome: 'good' | 'bad';
  appliedTo: 'context' | 'tool_select' | 'routing' | 'prompt';
}
```

### 3.3 回流目标（租户内）

| 目标 | 形式 | 作用 |
|---|---|---|
| 上下文 | 写入 profile/episodic | 后续 Prompt 更贴租户 |
| 工具选择 | `tool_select_hint{tid}` | 减少试错（如"该租户投流必带类目"） |
| 路由 C9 | `routing_hint{tid}` | 按租户选模型/路径更准 |
| Prompt 片段 | 可进 SE 提案素材 | 为进化提供素材 |

### 3.4 应用点

- **ContextBuilder**：注入相关 episodic，使回答带"该租户经验"。
- **工具选择**：Orchestrator 选工具时参考 `tool_select_hint`（如优先用某模板）。
- **C9 路由**：LN 积累的 `routing_hint` 微调规则路由，后期可替代理规则。

### 3.5 采纳评估（闭环）

```
每次应用经验 → 记录 ai_learning_log(tenant_id, exp_id, applied_at, effect)
效果回采：该经验后续任务成功率↑ → 提权；↓ → 降权/废弃
```

### 3.6 隔离与安全

- 经验严格 `tenantId`，不跨租户；`tool_select_hint` 仅本租户生效。
- 不动生产数据，只写 AI 自有存储。

## 四、SE 自主进化（详细，门控）

### 4.1 进化对象

| 对象 | 示例 |
|---|---|
| prompt | 系统提示/域 Agent 提示优化 |
| 工具定义 | 工具 description/参数微调（不改风险分级） |
| 工作流(图) | 运营闭环节点顺序/条件微调 |
| **tool（新建工具）** | 注册一个**全新 ToolDefinition**，包装既有总后台微服务 API，使 AI 可直接调用该能力（**不新建后端/微服务**，仅暴露既有能力） |

### 4.2 提案生成

- **触发**：① LN 信号达阈值（同类经验 N 条一致）；② 运营人员主动提议。
- **提案结构 Proposal**：

```ts
interface Proposal {
  target: 'prompt' | 'tool' | 'graph' | 'newtool';
  current: string;          // 现版本快照（newtool 时为 null）
  proposed: string;         // 建议 diff（newtool 时为完整 ToolDefinition JSON）
  rationale: string;        // 依据（引 LN 经验 id）
  expectedEffect: string;
}
```

### 4.3 门控状态机

```
proposed ──▶ review(生成待审工单, 复用 C5 审核流程)
   │
   ├─ rejected ──▶ 归档(留痕)
   └─ approved ──▶ gray(灰度) ──▶ rolled_out(生效) / rollback(回滚)
```

- **冻结**：proposed → review 期间不生效，现有版本继续服务。
- **灰度 gray**：仅对提出进化的租户 + 部分 session 生效，观测指标。
- **回滚**：异常一键回滚到上一 `rolled_out` 版本（快照）。

### 4.4 版本化（ai_evolution）

```sql
ai_evolution(tenant_id, id, target, version, diff, status, snapshot_prev,
             proposed_by, reviewed_by, created_at, rolled_out_at)
```

- 每次进化一个 `version`；`status ∈ {proposed,review,gray,rolled_out,rejected,rolled_back}`。
- `snapshot_prev` 保证一键回滚。

### 4.5 安全边界（强制）

| 禁止 | 说明 |
|---|---|
| 改核心权限 | 不碰账号/租户/角色定义 |
| 跨租户 | 进化仅在提出租户内生效 |
| 删生产数据 | 不删业务表；只改 AI 自有配置 |
| 改风险分级 | 工具 `risk`/`needsReview` 不可由 SE 自动降（须人工） |
| 绕过审核 | 所有 SE 必过审核门控，无免审路径 |
| 新建工具越界 | newtool 仅包装既有微服务 API；不得臆造路径/新建后端/跨域写操作 |

### 4.6 与审核流程对接

- SE 提案 → `ReviewClient.request`（同 C5 待审工单）→ 现有审核流程 → 回调 `approved/rejected` → 状态机推进。
- 复用 `ai_audit_log`（加 `scope/evolution_id` 字段），全留痕。

### 4.7 自动新建工具（newtool，详细，强门控）

#### 4.7.1 含义与边界

SE 的「新建工具」**不是**创造新后端能力，而是：基于 LN 积累的反复成功模式，把"一次 LLM 临时拼装的多步调用"**固化为一个标准 ToolDefinition**，使其后续可被 LLM 直接点名调用、行为稳定可审计。

- ✅ 允许：包装**既有总后台微服务**的已有 API（如把"查订单→筛异常→生成催付话术"固化为 `ops.cs.urge_pay`）。
- ❌ 禁止：新建微服务/端点、直连数据库、调用未授权 API、扩大风险面。

#### 4.7.2 触发

- LN 信号阈值：同一组合动作被临时拼装执行 ≥ N 次且成功率 ≥ 阈值（如 8/10）。
- 运营人员主动提议（"把这个流程存成工具"）。

#### 4.7.3 新工具结构（必须完整 ToolDefinition）

```ts
interface NewToolDef extends ToolDefinition {
  id: string;            // ops.<domain>.<verb>，全局唯一
  name: string;
  scope: 'ops';
  microservice: string;  // 必须指向 2.1/2.2 真实目录中的既有微服务
  method: string;        // 必须对应微服务既有 API（不得臆造路径）
  risk: ToolRisk;        // 默认从中评级起评（见 4.7.5）
  needsReview: boolean;  // 默认 true（新建默认保守）
  argsSchema: JSONSchema;
  description: string;   // 含入参/出参/前置依赖/审核标注
}
```

#### 4.7.4 注册流程（经门控）

```
LN 命中阈值 / 人工提议
  → SE 生成 Proposal{ target:'newtool', proposed: NewToolDef JSON, rationale }
  → 静态校验：microservice/method 必须存在于总后台目录；否则直接 rejected
  → 门控状态机：proposed → review(待审工单) → approved → gray → rolled_out
  → rolled_out：ToolRegistry.register(newDef, 'ops') 写入 scopeIndex['ops']
  → 回滚：从 Registry 注销该工具（snapshot_prev 记录原状态）
```

#### 4.7.5 安全约束（强制，叠加 4.5）

| 约束 | 说明 |
|---|---|
| 仅包装既有 API | `microservice`+`method` 必须命中总后台真实目录；臆造路径一律 rejected |
| 默认风险保守 | 新建工具 `risk` 默认从中/高起评、`needsReview` 默认 true；**不得自动降为 low** |
| 降级须人工 | 若后续要降风险/免审，必须走一次新提案 + 审核，SE 不自降 |
| 不扩大能力面 | 新工具不得调用它本域外的写操作；不得串联高风险写操作绕过单点审核 |
| 租户隔离 | 新工具注册在提出租户内；不跨租户可见/可用 |
| 全留痕 | 新建/启用/回滚均入 `ai_evolution` + `ai_audit_log`，含 proposed_by/reviewed_by |
| 可观测 | 灰度期统计调用次数/成功率/审核触发率；异常自动回滚 |

#### 4.7.6 示例

```
LN 观察：租户 A 的客诉流程中，"查 order(3004) → 筛未付 → 生成催付话术" 被拼装 10 次、成功 9 次
SE 提案 newtool：
  id: ops.cs.urge_pay
  microservice: order(3004) + customer(3010)   // 仅既有 API
  method: GET /list + GET /search
  risk: medium, needsReview: false（只读组合）
  description: 生成催付话术。前置：订单查询。无审核。
→ 审核通过 → 灰度(租户A, 20% session) → 成功率达标 → rolled_out
→ 后续 LLM 直接调 ops.cs.urge_pay，行为稳定、可审计
```

## 五、三者协同闭环（端到端示例）

```
用户：「给红星商行做五粮液短视频挂车」
  → Orchestrator 读 LT(profile:品牌调性, episodic:上次挂车被驳回原因)
  → 执行 graph；发布命中 high → 审核门控 → 通过
  → 结束：MemoryManager 写 episodic(成功) + profile(偏好)
  → LN 提炼："该租户挂车需先填类目" → tool_select_hint
  → 同类信号达阈值 → SE 提案："分发工具 description 补'必填类目'"
  → 审核门控 → 灰度 →  rolled_out → 回流 LT/archival
下次同租户任务：直接带类目，少一轮试错
```

## 六、与 scaffold 接口对齐（签名草稿）

```ts
// long-term-memory.service.ts
class LongTermMemory {
  async load(ctx): { profile; episodicTopK; archivalTopK }
  async saveEpisodic(ctx, exp: Experience)
  async upsertProfile(ctx, k, v)
}

// learning.service.ts
class LearningService {
  async absorb(ctx, signal: FeedbackSignal)   // 写 experience + hint
  async getHints(ctx): { toolSelect; routing } // 给 Orchestrator/路由
}

// evolution.service.ts
class EvolutionService {
  async propose(ctx, p: Proposal)             // target ∈ prompt|tool|graph|newtool
  async registerNewTool(ctx, def: NewToolDef) // newtool 审核通过后写 Registry
  async unregisterNewTool(ctx, toolId)        // 回滚时注销
  async rollback(ctx, evolutionId)
  // 状态机推进由 ReviewClient 回调驱动
}
```

## 七、风险与护栏

| 风险 | 护栏 |
|---|---|
| LT 膨胀/噪声 | 摘要链 + 租户配额 + TTL 分级 + 相关性重排 |
| LN 误学(错误经验) | 信号加权；采纳评估回采；坏经验降权 |
| SE 行为回归 | 强制审核 + 灰度 + 快照回滚 + 安全边界禁改 |
| 租户串味 | 全链路 `tenantId`；向量命名空间 `{tid}` |
| 进化绕过门控 | 无免审路径；`ai_audit_log` 强留痕 |

> LT/LN 可在 P1/P2 上线释放价值；SE 作 P3 门控后期，不阻塞前两阶段。
