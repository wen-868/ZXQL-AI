# 基于现有 AI 底座（:3016）的全量能力 + 复制到运营系统方案（修订 v2）

> 修订说明：原方案为「共享底座 + systemScope 能力开关 + 按系统限制能力」。据用户最新指示修订为：**底座全量开放能力（长期记忆 / 自主学习 / 自主进化），先在管理系统(3016)完善，再复制部署到运营系统**。本版据此重写，原 systemScope 受限思路作废。
> 依据：《智享全链 AI 底座 开发文档 v2.0》。

---

## 一、结论先行

1. **全量开放，不做能力限制**：管理系统 AI 先具备长期记忆 + 自主学习 + 自主进化，显得更聪明。
2. **完善后复制部署到运营系统**：同代码、两份形态——一份作为总后台侧 server 微服务（:3016），一份**内嵌进运营系统本地包**（前期不独立部署服务器）；两套系统**共用一个总后台**完成账号与微服务对接。
3. **三项能力平台早已具备，AI 底座继承与对接（非新建）**：统一账号体系、多租户隔离、审核流程——AI 底座正确对接总后台即可，不另起炉灶。
4. **部署节奏**：运营系统前期本地打包、不占独立端口；仅使用量过大时，再将内嵌副本外置为独立 server 微服务（平移，非重构）。

---

## 二、能力范围（全量 = C1–C11 + 认知层）

在既有 C1–C11 之上，显式补「认知层」三件套：

| 能力 | 含义 | 现状 |
|---|---|---|
| **C1–C11（全量）** | 编排/多Agent/工具/治理/记忆(短时)/本地+外部/流式/路由/验证 | 底座已部分具备，需补齐多Agent/人工闸 |
| **LT 长期记忆** | 跨会话、跨时间持久化；替代现有 Redis 10轮 / 1h TTL 短时记忆 | ❌ 需新建 |
| **LN 自主学习** | 从交互/反馈提取经验，回流到租户隔离的记忆/知识，改善后续决策 | ❌ 需新建 |
| **SE 自主进化** | Agent 随时间优化自身 prompt / 工具 / 工作流 | ❌ 需新建（最高风险，须门控） |

## 三、拓扑：单总后台 + 复制 = 同代码（一份在总后台侧，一份内嵌运营本地包）

### 3.1 核心约束（用户明确）

1. **共用一个总后台**：管理系统与运营系统共用同一总后台；总后台是**账号系统 + 微服务**的统一对接点（14 个中台微服务 3001–3014 及账号服务在此聚合）。
2. **运营系统本地打包**：运营系统以本地打包形态运行（如桌面/本地运行时），**前期不独立部署服务器**，连总后台拿账号态、调运营微服务。
3. **按需独立部署**：仅当后续使用量过大，才把运营侧 AI 引擎独立成服务器部署（届时才有独立端口需求）。

### 3.2 拓扑图

```
                        总后台（server，共用）
        ┌───────────────────────────────────────────────┐
        │  账号体系 + 中台微服务(3001–3014)            │
        │  管理系统 AI 底座 :3016（server 微服务）       │
        └───────────────┬───────────────────┬───────────┘
           统一账号认证(JWT→tenantId)         统一账号认证(JWT→tenantId)
              + 微服务调用                        + 微服务调用
                │                                  │
        ┌───────▼────────┐              ┌──────────▼───────────┐
        │ 管理系统(Web 客户端)│            │  运营系统(本地打包客户端) │
        │ 用 :3016 AI 底座   │            │  内嵌 AI 底座引擎副本    │
        └────────────────┘              │  (本地运行时, 前期无端口) │
                                        └──────────────────────┘
                  ↑                                  ↑
          同一套底座代码（全量能力：C1–C11 + LT/LN/SE）
```

### 3.3 要点

- **「复制」语义修正**：不是「同代码双 server 实例」，而是「同代码、两份形态」——一份作为总后台侧 server 微服务（:3016，服务于管理系统），一份**内嵌进运营系统本地包**（前期不占独立端口、不独立部署）。
- 每个形态单系统（mgmt / ops），故原 `systemScope` 隔离维度**不再必需**；多租户隔离在每个形态内仍强制（由总后台账号体系保证）。
- 两形态可共享同一 Ollama / 模型端点，或运营本地包用本机 Ollama（配置决定；本地打包天然契合「本地优先」）。
- **按需独立部署**：运营用量过大时，将内嵌副本外置为 server 微服务（临时端口如 :3015 / :3018），届时再接总后台——架构无需推倒重来，只是「本地内嵌 → 独立服务」的平移。
- 联邦学习服务（:3017）顺延为**未来按需**项：跨租户/跨实例经验聚合，仅在用量与价值到位后独立部署，前期不占资源。

## 四、管理系统 AI 完善路径（先做实，再复制）

| 阶段 | 范围 | 工时(1人) |
|---|---|---|
| **P0** | 全量基础能力：补齐 C1–C11 缺口（多 Agent 图、人工确认闸、RAG 全量、路由/验证） | 4–6 周（在 3016 上增量） |
| **P1** | **长期记忆**：持久化记忆存储（DB/向量），租户隔离，替代短时 TTL | 1–2 周 |
| **P2** | **自主学习**：反馈提取 → 租户知识回流 → 上下文/工具选择优化 | 2–3 周 |
| **P3** | **自主进化（门控）**：prompt/工具/工作流自优化，人工审批 + 版本化 + 回滚 + 审计 | 3–4 周 |
| — | 管理系统完善合计 | **≈ 10–15 周** |

> P1/P2 即可让管理系统 AI 明显变聪明且可控；P3 自主进化作门控后期阶段，不阻塞前两阶段价值释放。

## 五、运营系统接入（本地打包，前期不独立部署）

1. 打包同一底座 artifact，**内嵌进运营系统本地包**（作为本地运行时的一部分，前期不占独立端口、不独立部署服务器）。
2. 工具 / 微服务接线改为运营域：选品 / 脚本 / 直播中控 / 订单打单 / 智能客服 / 复盘 / 效果归因 …（沿用现有 ToolRegistry 模式，仅 `systemScope='ops'` 工具集不同）。
3. 账号与租户：运营本地包连**总后台**完成统一认证（JWT→tenantId）与多租户隔离，不自带账号体系——印证「共用一个总后台」。
4. 能力全量相同（含长期记忆 / 学习 / 进化门控）；多租户隔离 + 审计 + 进化人工闸同套机制（机制在总后台账号体系下统一生效）。
5. **按需独立部署**：仅当使用量过大，才把内嵌副本外置为 server 微服务（临时端口 :3015 / :3018），届时仍接同一总后台——属「本地内嵌 → 独立服务」平移，非架构重构。
6. 工时：同代码内嵌打包 + ops 工具接线 **1–2 周**（不含认知层，认知层已在 3016 完善后一并带入副本）。

> 复制后总工时 ≈ **12–17 周（1 人）/ ≈ 7–9 周（2 人）**，高于"受限共享"，因新增认知层（LT/LN/SE）。但隔离/账号/审核三项平台既有，无需从零建设，实际落地只需"对接总后台 + 全量能力 + 认知层 + 本地内嵌复制"。前期零服务器增量成本。

## 六、三项平台既有基础能力（AI 底座继承/对接，非新建）

用户已明确：以下三项平台早已具备，AI 底座**直接继承与对接**，不另起炉灶、不作为新风险建设。

| 既有能力 | 平台现状 | AI 底座的对接方式 |
|---|---|---|
| **统一账号体系** | 两套系统共用一套账号/身份管理 | AI 底座 `TenantContext`（JWT→tenantId）直接消费统一账号体系；复制部署到运营系统时，两实例认证同一套账号体系，tenantId 语义一致 |
| **多租户隔离** | 早已是基础功能（数据层行级隔离 + `x-tenant-id` + TenantContext） | AI 自有存储（记忆/向量/审计）统一带 `tenantId`，对接平台既有隔离；认知产物（学习/进化）同样按租户落，不跨租户 |
| **审核流程** | 管理系统早已实现审核/审批工作流 | AI 的「人工确认闸」（含自主进化、不可逆写操作）**映射并触发现有审核流程**，而非新建独立审批机制 |

> 说明：「全量开放能力」指能力**广度**全开；上述三项是平台**既有基础能力**，AI 底座正确对接即可。自主进化复用现有审核流程（含版本化/回滚/审批），无需重复造轮子。

## 七、风险与诚实提示

| 风险 | 对策 |
|---|---|
| 自主学习/自主进化是前沿能力，80% 风险与工时集中于此 | P1/P2 先上线（可控、收益高）；P3 门控后期 |
| AI 自有存储漏带 tenantId → 租户串味 | 记忆/向量/审计统一带 `tenantId`，对接平台既有隔离（非新建隔离机制） |
| 自主进化引入行为回归 | 复用现有审核流程（版本化 + 回滚 + 审批），不新建审批 |
| 长期记忆无限增长 → 成本/噪声 | 记忆压缩/摘要 + 租户配额 + TTL 分级 |
| 两实例配置漂移 | 同一 artifact + 配置即代码（config 区分 mgmt/ops 接线） |

---

## 八、落点

- 本方案**替代**「systemScope 受限共享」与「采纳 Mastra 新建」两条旧思路：以现有 3016 自建底座为基座，全量能力，复制到运营系统（本地内嵌形态）。
- **总后台是唯一的账号 + 微服务对接点**：管理系统与运营系统共用，AI 底座两份形态均连它完成认证与多租户隔离，不自建账号体系。
- OSS（ollama-agent-harness / Mastra）仍仅作**模式参考**（Governed Loop、Mycelium 路由、记忆结构），不引框架。
- 下一步可产出：① 长期记忆存储设计、② 学习回流设计、③ 自主进化门控设计；或先落地 P0 全量基础（在 3016 上补齐多 Agent + 人工闸）。
